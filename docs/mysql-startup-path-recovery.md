# MySQL 目录定位故障恢复

## 故障和修复边界

2026-09-09 开机后工作台无法访问：MySQL 启动报告 `Failed to set datadir`、`OS errno: 2 - No such file or directory`，3306未监听；启动器因此未继续启动后台和Web。

原库仍位于项目 `.mysql-data/`。旧 AppData 数据目录是指向原库的联接，在交互环境可访问，但开机启动的 MySQL 进程无法访问配置中的路径；同一用户目录下还能看到打包应用的 LocalCache 映射。修复使用工作区外固定英文目录中的联接，绕开旧路径的进程环境可见性差异，不把“找不到目录”等同于数据库丢失。

本次只更改本机启动配置与恢复副本，不修改业务代码、平台凭据、数据库密码、退款权限、消息发送或人工待办发布开关；不恢复旧备份覆盖数据，不重建空库，不移动原数据文件。

## 固定运行路径

本机配置和联接现位于项目父目录下的 `lds-aftersales-runtime/`。这只是本机部署路径，其他电脑应选择自己有权限访问、无中文且不依赖 AppData 重定向的稳定目录：

- `my.ini`：MySQL 启动配置，`datadir` 指向该目录下的 `data`。
- `data`：目录联接，指向原项目 `.mysql-data/`，不是数据库副本。
- `mysqld.err`：MySQL错误日志目标；守护启动带 `--console` 时，同时查看工作区 `.runtime/mysql-autostart-error.log`。
- `.runtime/module1-autostart.json` 的 `MySqlDefaultsFile` 指向新配置。
- `.runtime/mysql-defaults-backup.ini` 同步保存新配置；原配置缺失时，既有启动脚本会从该副本恢复。

本地配置、冷备份及数据库均不提交GitHub。不删除正在使用的联接或其目标；不要对联接执行递归删除。迁移电脑或调整目录时，必须先停库并重新核实目标，不照抄另一台电脑的路径。

## 安全恢复与核验步骤

1. 检查3306/8000监听、MySQL进程、启动日志及原数据目录；如果MySQL仍运行，不直接拷贝运行中的数据文件作为冷备份。
2. 确认原库位置和身份、数据文件日期及业务表目录；不能误选更早的测试库。MySQL停止后，备份完整原库、启动配置与日志到Git忽略目录，核对文件数量和总字节数。
3. 在经过核实的空英文路径创建联接，只指向原库；不移动、不初始化原库。新配置保持原端口、仅本机监听、原服务版本等设置。
4. 备份后更新本机JSON中的配置路径，以及配置恢复副本。执行MySQL的 `--defaults-file=<新配置> --validate-config` 校验。
5. 使用既有入口启动，不重复安装或创建另一套守护任务：

   ```powershell
   & .\scripts\module1-autostart.ps1 -Action Run
   & .\scripts\module1-autostart.ps1 -Action Status
   Invoke-RestMethod http://127.0.0.1:8000/health/ready
   ```

6. 核实实际 `@@datadir` 和 `@@server_uuid` 对应原库，迁移版本正确；检查首页、前端资源、订单接口及原业务开关。已有未核验发送任务不能因恢复网页而重置或盲目重发。

## 登录守护增强

用户进一步要求解决反复重启打不开的问题，本节记录在首次路径恢复后对 `scripts/module1-autostart.ps1` 的增强；前面的配置修复不等同于这些脚本保护已经存在。

证据表明本机登录启动项会启动守护，故障发生在 MySQL 目录解析，不是完全没有自启动入口。保留原有启动项，不修改系统自动登录、全局启动延迟、平台凭据或资金权限。

### 安全恢复与状态

- 安装时验证并登记 `MySqlDataDirectory`、`MySqlDataSourceDirectory`、`MySqlServerUuid`，然后保存 `.runtime/module1-autostart.backup.json`。已有实例升级时也需在核对真实 `@@datadir`、UUID和联接目标后登记，不能猜测这些字段。
- JSON缺失、语法损坏或关键字段不合法时，后台可从有效副本恢复；损坏的原JSON保留为 `.invalid.<唯一编号>`。Status只读查看，不执行恢复。
- MySQL配置丢失仍从 `mysql-defaults-backup.ini` 恢复；数据联接丢失则先核对原库UUID和必要数据文件，再只创建指向登记原目录的联接。已有错误联接、错误UUID、原库文件缺失、未核实的include配置均报错停止；绝不移动、删除、初始化或回滚原库。未登记身份的旧实例不自动创建联接。
- MySQL启动后先尝试Web，再尝试业务后台；某一项失败不会阻止另一项尝试，最终分别汇总失败原因。未改动业务后台的安全停止和资金幂等机制。
- 独立Watch的配置读取置于重试循环内，失败后30秒复查，成功后按原 `WatchdogMinutes`（本机5分钟）复查；既有计划任务Run模式仍保持其原5分钟调度。原MySQL单次启动检查最多3次启动尝试保持不变。
- Watch和一次性Run分别使用独占文件锁；锁文件存在不等于被锁定，进程退出后操作系统会释放文件句柄，不需要人工删除锁文件。Watch自己登记PID，启动器不覆盖PID。
- `.runtime/module1-autostart-status.json` 记录最近检查时间、检查进程、`checking / healthy / failed`及错误原因，`-Action Status`会展示。这里的healthy只表示基础服务已就绪，不代表所有退款或同步任务都成功。

### 更新与验收

脚本修改后，当前Watch需要重新加载。只停止守护，不停止数据库、网页和业务后台：

```powershell
& .\scripts\module1-autostart.ps1 -Action StopWatch
& .\scripts\module1-autostart.ps1 -Action Status
# 确认旧守护已经自然退出后，再启动；不强杀仍在执行检查的进程。
& .\scripts\module1-autostart.ps1 -Action StartWatch
& .\scripts\module1-autostart.ps1 -Action Status
```

无需重复安装多个启动项。若本机Windows登录启动项被用户或安全策略禁用，应由用户确认后恢复，不绕过策略；若采用计划任务Run模式，没有必要额外启动Watch。
