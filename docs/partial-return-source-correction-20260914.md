# 部分售后数量来源与历史少退纠偏

本次补齐之前“只保护新记录、旧验货异常仍显示”的缺口。

## 数量口径

拼多多售后详情同时包含购买数量 `goods_number` 与部分售后字段。对 `part_after_sales_type=1`，读取 `part_after_sales_value` 作为本次申请件数，要求为不超过购买数量的正整数。该口径已经与本次平台详情、用户确认及原销售关联的 ERP 实收交叉核验；不通过退款金额或单价倒推数量。

同步保存 `aftersales_items.purchased_quantity` 和 `quantity_source`，`applied_quantity` 为本次申请数量。未提供明确部分售后字段时仍保留购买数量并标识 `PDD_GOODS_NUMBER`，沿用数量待核实保护。未知类型或无效数量进入同步隔离，不猜测。平台接口入口：[售后单详情](https://open.pinduoduo.com/application/document/api?id=pdd.refund.information.get&permissionId=13)。

数据库迁移 `20260914_0028` 仅新增两个可空字段，不猜测回填旧订单；部署必须先备份、迁移，再启动新 Worker。回退旧代码时保留新增列。旧 Web 查询兼容新增列，可直接显示修正后的申请数量和仓库状态。

## 历史纠偏

模块2异常待办阶段在生成新待办之前，独立扫描当前范围内最多500条系统 ERP 失败记录，包含已经有成功待办的订单。只处理明确系统来源、单一售后/收货/运单、正常实收是购买明细真子集、且备注严格符合旧纯少退模板的记录。

- 有明确申请数量时，还须申请型号、颜色和件数全部等于实收，才撤销旧少退结论。
- 数量来源未知的，改为数量待核实，不宣称匹配或质量合格。
- 错型号/颜色、真正少退、人工质检或附加质量结论、多收货/共享运单均不自动撤销。
- 原失败结论、操作人、时间、订单异常和商品状态保存在收货备注的“数量纠偏原始审计”中；当前验货改为 PENDING，原系统误写的 DEFECTIVE 撤为未知，不写 PASS。
- 原来的成功外部待办保留，不伪造撤回；未发出的旧错误待办继续由发布前保护取消，禁止因为纠偏再发送。
- 独立质量验收、退款后财务核账、实收分配及资金幂等仍分别验证；纠偏不调用外部资金或消息接口。

预演只读，重复执行不会重复写审计。正式运行每个业务周期沿用原模块2阶段，无新定时任务。500条上限是单轮保护边界，大规模历史修复须分页维护，不宣称无限扫描。

## 部署与验收

以正式机当前发布源码创建候选，仅替换模型、拼多多映射/同步仓储、数量保护和模块2旧异常纠偏文件。持守护周期锁，等待业务周期自然结束，完成一致性备份和数据库迁移后切换发布指针，继续使用隐藏守护启动。个案原始接口、ERP明细、数据库前后状态及发布清单保存在 Git 忽略的 `.runtime/audits/`。

验证覆盖部分数量、来源持久化、非法字段隔离、真实异常不被覆盖、旧成功待办也能纠偏、旧待办不重发、只读预演、重复执行，以及模块2、拼多多同步和企微回执恢复回归。
