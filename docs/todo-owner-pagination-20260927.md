# 人工待办长期待发送：原销售业务员核验修复

## 原因与处理

拦截通知核验超时后会生成给原销售业务员的人工待办。发送前必须重新核实收件人；客户销售历史超过原20页上限，或者原销售编号带字母后缀时，旧归属查询会一直失败。任务未领取发送、尝试次数仍为0，但页面只显示“待发送”，无法区分正在排队与归属受阻。

- 仅原销售业务员查询的完整分页上限调整为200页，逐页检查页号、页数、30行完整性和重复页，最后复查首页。必须精确匹配平台订单、唯一客户及原销售业务员，不读取第一页就放行、不回退客户档案默认业务员。超过上限、读取失败或原销售归属冲突仍等待核验。
- 仅业务员查询允许“数字+字母后缀”的原销售编号，保留原始编号，不截掉后缀合并。商品数量仍须有限、非负且目标订单至少一行正数，零数量行的业务员也参与一致性检查。
- 整包裹范围、商品数量及退款核验继续原20页和原销售编号规则；识别业务员不授予自动拦截或资金权限。
- 尚未尝试发送且归属不可读/未匹配的人工待办，页面显示“等待业务员归属核验”和现有阻塞原因；真实任务仍留在原待办队列。已尝试、结果未知或已有外部回执的记录不被改写为“尚未发送”。
- 新建和未发送的超时待办改为“待原销售业务员核实”，不再提前称为“已转”。正文明确先查看快递群是否已手工发送、核实符合整包裹拦截条件后及时处理，避免重复通知。已发送正文、时间、回执保留。

## 运行与防重

沿用原后台周期、原业务员分派、5分钟归属重查及发送队列，不新增定时任务。修复上线后由原队列到期重新读取原销售归属；归属核实后按业务员分派，同包裹有不同业务员时分别通知。旧未知收件人任务转为已取消并记录替代任务ID，不清空尝试次数、不重复重建已发送任务。

发布开关与未知结果只读回查规则继续生效。页面展示“已发送”须由原正常发布流程确认，不能通过手工改状态消除积压。修复不恢复已经取消的快递群拦截任务；业务员仍须根据待办核实包裹和群内记录。

## 验证与部署

相关197项本地回归通过，覆盖85页完整读取、末页业务员冲突/缺失、页数变化/重复/缺页、上限、首尾一致性、字母后缀、原资金核验规则、待办分派防重和页面历史记录保护。正式机只读预演已定位并核对积压待办涉及的原销售记录；真实样本和证据仅保存在 Git 忽略的 `.runtime/audits/`。

采用当前worker/web发布副本分别增量更新，隔离测试后等后台结束当前周期、验证备份，再切换发布；独立揽收提醒不变。真实发送结果、正式周期及最终版本以验收记录补充为准。回滚只恢复发布指针，不覆盖期间新增发送回执或业务记录。
