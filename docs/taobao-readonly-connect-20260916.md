用户要求先接入现有可用部分、保留失败项后续处理。本次接入的是后台只读核验及工作台结果展示，不是开启自动退款或ERP写操作。

## 已接入与未开启

- 原有淘宝售后同步、归因、退款金额统计继续运行。
- 模块2新增独立实收核验：实时核对卖家、订单、售后、完整SKU及全额数量金额；根据原销售核对客户正式TH或完整退货暂存列表。该核验不需要原发货物流接口，不把缺失物流伪装成未发货。
- 模块1/退回核账、模块3继续使用严格的既有只读预演条件。缺少物流、客户归属、SKU或余额证据时阻断，不能为接入而跳过。
- 所有模块 `execution_ready=false`；不创建资金/认领任务，不写业务表，不标记质检通过或售后闭环。平台退款、ERP认领/补单仍未开启，原有资金白名单不扩淘宝。
- 多订单多包裹仍按[整批核验规则](customer-multi-parcel-return-verification.md)人工核验，不自动分配实收或开启复杂包裹退款。

工作台入口：**接入能力 → 淘宝 → 对应店铺**。各模块显示“核验已接入·执行未开”，附最近核验的订单、时间和具体阻断原因。没有结果、报告过期或服务错误会明确显示；页面不是所有失败订单的完整历史列表。退款权限单独显示“未开启·写权限待验”，不把查询成功等同资金权限。

## 调度与开关

接在既有多平台同步周期末尾，仅在本轮包含淘宝且原淘宝同步开启时运行；没有增加计划任务或第二套Worker。单独运行原多平台同步命令时也会遵守同一开关和跨进程锁。

使用运行资料目录中的 `.runtime/taobao-checks/enabled.json` 显式启用，内容必须恰为 `{"mode":"read_only"}`。缺失、格式不对或淘宝同步停用则不执行。停用时移走/备份此开关文件即可，不需要停掉其他平台。开发机不放此启用文件，仍不启动业务数据库或Worker。

最多每15分钟执行一批3笔，尽量覆盖三个模块并按上次核验时间轮转。只选最近30天更新的有效淘宝店铺售后；超过500笔整体停止检查并提示调整分页，不悄悄漏查。每笔需最近30分钟无错误同步记录。报告显示每笔实际检查时间，过期结果不能当作当前结论。

独立MySQL连接使用READ COMMITTED及 `SET TRANSACTION READ ONLY`，禁用autoflush、结束回滚。与同步写会话完全隔离。沿用只读平台方法白名单和ERP同源/路径限制，不调用showlist、搬单、草稿、资金接口。

报告原子保存到 `.runtime/taobao-checks/report.json`；包含内部ID、订单号及检查结论，仅保存在运行机，不进入Git。失败保留原因等待轮转重查，既有同步水位不回退；本检查出错不使其他平台已成功同步变成失败。报告失效不显示为已通过。

## 正式预检与真实限制

已在独立候选目录用正式数据按三个模块各取1笔只读核验：

- 模块1与模块2样本：中转返回的退款号、父订单号均匹配，但订单详情缺少 `seller_nick`；卖家查询本身能返回身份。这是**缺少交叉核验证据**，不是已经证明订单属于其他店，仍不能放行。
- 模块3样本：同父订单或包裹存在其他售后，转整批核验，不自动整单平账。
- 前轮查询已确认 `taobao.logistics.orders.get` 返回 `isv.permission-api-package-limit`。独立模块2实收核验不再依赖这个接口，但不能越过卖家归属等其他检查。

本次没有成功核验并执行的实单，不能宣称平台退款权限已验证。恢复缺失证据后由后台重新检查；要开启资金执行仍需完成相应写适配、幂等/占用/质检与实单验收。

## 发布与恢复

从正式Web/Worker当前版本分别复制独立候选目录，只覆盖已核对基线的本轮文件和上一轮只读依赖。Worker/Web源码原本存在差异，因此按角色分别选文件，不把整份开发源码覆盖正式环境。前端沿用原产物，无schema迁移，无 `.env` 或其他平台配置变化。

启用前等待Worker周期自然退出、正常退出Web并做校验备份；切换两个代码指针和只读标记，再由原交互会话守护恢复。失败在激活前回退指针/本轮标记，不强杀资金请求。审计保存在 `.runtime/audits/taobao-connect-20260916/`。

如需恢复旧版本，先安全停止周期再恢复审计保存的旧指针，并停用淘宝只读标记。保留正式数据库、资金账本、认领记录和检查报告；不清理或重发其他平台资金操作。
