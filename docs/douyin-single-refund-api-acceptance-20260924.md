# 抖音单笔退款 API 验收（2026-09-24）

## 范围与结果

在用户明确授权的一笔退货退款上，完成官方 API 单笔实际同意退款测试。平台写请求仅一次，返回 `code=10000`、目标售后 `status_code=0`；随后详情确认 `after_sale_status=12`、`refund_status=3`、实际退款金额与本次授权一致，且有真实 `refund_time`。未传操作留言，未调用备注接口。

这是当前应用、一个已授权店铺、一笔待商家收货的退货退款实测，不证明所有店铺、所有售后类型都具备可执行权限。**没有开启抖音模块1/2自动退款，也没有修改常驻代码、发布指针、全局写开关或现有只读客户端白名单。** 模块1已发货仅退款、模块2批量候选、自动ERP认领/补单仍须各自适配和验收。

真实订单、客户、运单、平台响应及个案脚本仅存 Git 忽略的 `.runtime/audits/douyin-refund-20260924/` 与正式资金账本，不上传仓库或 Notion。

## 已核实的接口约定

- 官方接口为 `/afterSale/operate`，签名方法名 `afterSale.operate`。[官方 API 文档](https://op.jinritemai.com/docs/api-docs/17/560)
- 退货退款 `after_sale_type=0`、待商家收货 `after_sale_status=11` 使用 `type=111`；不是仅退款使用的 `201`，也不是第一次同意退货申请的 `101`。[官方操作码说明](https://op.jinritemai.com/docs/guide-docs/1258)
- `items` 只放本笔售后，传 `aftersale_id` 和刚读取的 `update_time`，由平台校验售后版本。省略 `remark`、`reason`、`evidence` 等非必要字段，不发送留言。
- HTTP 成功和审核回执不等于退款已完成；必须再次只读查询详情，核实身份、实退金额、资金状态和退款完成时间。

## 本次资金与实收保护

执行前完整读取客户原销售、正式退货、税点及收款账，追溯平台订单，逐项确认完整型号、颜色、实收数量；同客户七笔原销售相关订单逐笔查询售后，排除重复售后、共享退货和已占用实收。显示舍入后的单价乘数量不能冒充精确退款金额，实际金额另与平台支付、申请及原收款核对。

先只读预演，再实时复查平台与 ERP。写请求前在主数据库同一事务提交永久 `PLATFORM_REFUND` 幂等记录和本笔实收分配记录，唯一键限制重复提交；不创建虚假的一对一仓库质检通过记录，不解除其他平台或通用流程的限制。

平台写 HTTP 禁止自动重试和跳转。超时、异常、平台拒绝或回查不明都保留原账本，只读核实，不清除失败凭证再退款。本次成功后回写真实平台资金状态，不以平台退款成功伪造 ERP 闭环。

## ERP后续核账结果

平台退款成功后，原 ERP 仍没有目标退款流水且累计应收为负。检查原 ERP `AliController::executeDeleteProdlist` 的抖音分支：`actionid=1` 先查询抖音详情，只有平台已退款才进入原订单账务和补单流程；并检查启用/编辑冲突以及是否已存在相同售后退款流水。未使用有批量处理副作用的 `showlist` 作为只读查询。

按用户既有的“核对一致后补开退款单”授权，先预演及实时复核，再持久化独立 `ERP_REFUND` 幂等记录，单次调用原补单入口。随后只读回查确认新增唯一退款流水：售后号、ERP原销售号和金额均对应，客户累计应收归零且无欠货。未再次向平台退款，未重新认领/新开退货单。工作台保存平台成功及ERP资金账本证据，不将尚未接入的抖音自动工作流伪报为已开启。

本次验证包括单笔平台和ERP只读预演、各一次真实写请求、实际资金和账务回查、脚本语法检查；不是四店全类型批量回归或无人值守生产验收。

现有抖音解析/只读白名单及资金防重相关回归33项通过。首次测试遇到系统临时目录访问拒绝，改用本次审计目录下全新的独立 pytest 临时目录后全部通过，未删除或改权限覆盖系统临时目录。通用验收与四店同步说明已同步 Notion；本次提交仅含这两份文档，不包含个案脚本或其他工作区改动。

## 后续接入前的边界

单笔验收脚本不是自动化入口，不可复用历史订单或历史 `apply` 命令进行下一笔资金操作。后续需明确模块范围、店铺授权与开关，设计相应类型的物流/退货核验、持久化实收分配、防重、异常隔离、ERP核账及合成测试，逐阶段只读验收后再发布。

同步客户端继续只读；模块3的其他候选工作不因本次实单测试而自动部署或开启。实际执行权限应读取正式发布和配置，不能仅凭本记录或开发分支判断已上线。
