# 1688揽收提醒状态处理

## 问题与规则

1688实际返回的 `waitbuyerrepayment` 未在提醒读取器中识别，导致订单列表第二页报错，整批同步回滚、游标停在2026年9月29日22:21:03（北京时间）。这属于店铺同步异常，不是ERP客户端登录失效或消息发送失败。

只读实单表明该状态也出现在已发货、商品已取消的订单上。因此仅将其加入已识别的非终态，不能直接当成未付款、未发货、交易结束或全额退款。仍核验绑定商家、完整分页、详情商品、真实包裹时间与实退金额：

- 仍履约的商品及包裹继续进入普通20小时无物流核验；部分退款不排除剩余履约。
- 明确取消、已收货或退回的商品沿用原排除规则，不形成催揽收提醒；不虚构全额退款、交易关闭或ERP平账完成。
- 缺包裹、商家不符、金额不一致、未知状态及分页不完整仍保留异常。没有扩大到任意未知状态，也没有跳过失败窗口。

## 运行、发布与恢复

入口仍为 `scripts/shipment-watch-run.py`，计划任务 `Leedis Shipment No Trace Reminder` 每5分钟触发。输入是各平台普通订单增量与包裹详情；输出为监控账本及满足条件时给ERP原业务员的提醒。20小时阈值、消息防重、原写开关和ERP客户端登录依赖不变，无新增环境变量或资金权限。

本次源文件仅 `alibaba_1688_shipment_source.py`。生产候选从正式独立提醒 `erp-client-shipment-20260930` 完整复制，再更新这个文件；不能用修复分支整棵源码覆盖正式源，避免丢失客户端登录及内部共享会话修复。其余174个源文件逐一核对哈希。

发布须待原独立提醒周期自然完成，短暂停止该任务的新触发并取得其数据库互斥锁，原子更新 `.runtime/shipment-watch-release.json`，随即恢复原任务。业务后台、网页、客户端、环境配置和任务规则不变，不重启电脑。下一正常周期从原失败游标续读；禁止手工推进游标、清空错误或删除通知账本来消除告警。
