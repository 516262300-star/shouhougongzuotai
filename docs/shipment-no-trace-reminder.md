# 发货20小时无物流信息提醒

2026-09-19 用户授权：拼多多、天猫订单发货满20小时仍无物流信息，向对应业务员发布原管理系统人工待办。20小时为固定业务规则，相对发货后24小时提前4小时；不是平台违规判定，也不覆盖可能更早的订单承诺时限。

## 范围与判断

- 使用拼多多 `pdd.order.number.list.increment.get`、天猫 `taobao.trades.sold.increment.get` 同步普通订单，不要求订单申请售后。首次回溯最近72小时的订单修改记录，之后按独立游标持续增量；不承诺覆盖启用前72小时外且此后未变化的历史订单。
- 从平台订单详情读取真实发货时间，满20小时（含）后查物流。已超过24小时的漏提醒订单也补入，并写明已超24小时。
- 物流来源复用快递100。只接受已校验的正常“查询无结果”业务响应；网络超时、鉴权失败、身份不符、解析失败或不明空响应保留本地错误并重查，不发送无物流提醒。已有任何轨迹（包括下单/待揽收轨迹）不符合本次“无物流信息”规则；曾观察到轨迹后不因后来空响应重新提醒。
- 天猫逐包裹查询。多包裹须能唯一关联子订单发货时间，否则保留核验错误，不借用另一包裹的发货时间。拼多多以订单详情返回的原发货运单为监控对象。
- 平台订单关闭、已签收或包裹信息变化时，发布前重新判定。全额退款成功的订单不再催揽收，不受发货是否已满24小时限制；部分退款、退款申请中仍按原物流规则监控。拼多多以实时退款详情成功状态及退款金额（分）等于订单实付金额（元）核验；天猫核对整单全部子单退款成功、唯一退款单身份及合计退款金额等于整单实付。金额、身份、状态矛盾或接口失败保留核验错误，不据此发送提醒。初查、业务员归属查询之后及ERP最终提交前均复核。提醒不调用退款、拦截或ERP资金操作。
- 业务员从ERP原发货销售订单读取；归属缺失、冲突、查询失败保留本地待办，恢复后重查。不使用客户档案归属兜底。

## 发布、防重及查看

待办文字包含店铺、平台订单、运单、发货时间、剩余时间/已超时和“联系仓库或快递核实交运、催促实际揽收并回传轨迹”。业务员在原管理系统待办事项查看。工作台“人工待办”也统一展示普通订单揽收提醒，可搜索平台订单号或运单号，按“发货20小时无物流提醒”、业务员、发送状态及日期筛选；详情显示完整内容、业务员、发货时间、运单、发送确认时间及ERP待办ID。不要求订单先申请售后，不伪造售后单，不为展示重新发送待办。

两类账本在查询时合并后统一排序、计数和分页。`SUBMITTING`/`UNKNOWN` 显示“结果待确认”，不能当作已发送或可重试；发布前发现物流轨迹的普通订单提醒仅保留后台核验记录，不进入人工待办列表、数量统计或业务员筛选，即使此前已经形成提醒也不显示“已取消”。全额退款核验通过后，未发送提醒记为 `REFUNDED` 并排除展示；已经发送的提醒保留原状态、发送内容、确认时间和ERP编号，在载荷补记退款依据后从本类人工待办排除，不能声称原ERP待办已撤回或完成。原请求结果不明的仍保留“结果待确认”供回查，并明确不再催揽收，不重发。其余已发送提醒及原售后任务按原规则展示。普通订单提醒的日期筛选按最近核验/发送确认时间，售后任务仍按生成时间；页面称“待办记录时间”，详情注明来源口径。旧提醒账本未单独记录首次创建时间和尝试次数的显示为空/未单独记录，不推算补造。页面仅查询本地账本，原ERP实际待办不因查看页面而修改。

工作台“接入能力”页面提供“发货20小时无物流提醒”概览及每店对应能力列。概览显示开启店铺、监控订单、确认发送、待发送、结果待确认、核验异常及同步异常数量，并展示最近进度和最近完整巡检时间。点击“刷新状态”读取最新数据。配置已开启和近期运行记录分别展示；未启用、店铺未登记、发布开关关闭及账本不可读均显示原因。超过30分钟没有进度提示检查任务，不将无记录当作正常或零异常。该页面仅查询本地配置与账本，不发起平台/ERP请求。

同一业务员、标准化后的同一快递公司及运单合并为一条包裹提醒。同批先准备订单，再逐笔复核退款、发货和业务员归属，正文列出相关订单并按最早发货时间计算期限。后续发现同包裹的其他订单，关联已有提醒，不再重复发布；ERP已发正文不自动改写，工作台关联订单补充展示。不同业务员或不同快递公司不混并。逐单防重键仍保留，已发送订单的业务员变化不重发。发布前复核订单、物流和网页人工待办总开关；请求之前写入 `SUBMITTING`，断线、超时、崩溃或保存结果不明保留 `UNKNOWN`，后续仅回查原待办，不自动重新提交。查询确认存在才标记 `SENT`。不要删除账本恢复发送。

新关联记录记为 `MERGED` 并引用主提醒，人工待办按主提醒统一筛选、计数和分页，每个相关订单均可搜索。历史同包裹多次发送可合并展示，但各条原状态、正文、ERP编号和发送时间仍保留，详情明确列出历史发送事项及编号，不伪称原ERP记录已合并或撤回。包裹中某单全额退款后仅移除该单的日常监控，其他未全额退款订单继续展示；全包裹退款后按退款排除规则隐藏。

业务员正文只显示“【揽收提醒】”及店铺、订单、运单、发货时间和处理要求，不包含内部哈希编号或运单后面的平台快递公司数字编号（例如384）。快递公司仍在后台用于查询及防重。账本防重键继续保留，ERP回查使用正文中已有的店铺、订单及运单组合，并兼容旧哈希前缀、带快递编号的旧正文及同批其他订单身份，改文案不重发旧任务。结果不明请求按新旧正文身份只读回查。工作台查询历史内容时隐藏旧哈希前缀和平台快递数字编号，数据库仍保留原始发送正文和ERP待办ID。原ERP当前待办页面只有完成、删除操作，未发现正文编辑入口，已发ERP历史正文暂保留，不以删除重建方式清理文字。

继续遵守 `ERP_WRITE_ENABLED` 和网页“人工待办自动发布”开关；关闭后仍可同步及保留本地待办。这个独立提醒是用户新授权的规则，不修改原售后“连续无轨迹不发给业务员”的分流规则。

## 运行、配置与恢复

入口：`python -m aftersales_workbench.workflows.shipment_watch_cli`。不带 `--publish` 只进行平台/物流/ERP归属只读查询及本地记账；带 `--publish` 才尝试发布。`--status` 只读取游标、数量和错误；`--max-windows` 控制每店追赶窗口数，`--limit` 控制单轮核验数。拼多多窗口28分钟加2分钟重叠，天猫窗口20小时加2分钟重叠，均完整分页后才推进。

沿用已有拼多多七店、天猫六店、快递100与ERP凭据，无需新增密钥。正式运行机独立发布指针 `.runtime/shipment-watch-release.json` 需要 `enabled: true` 及限定在 `.runtime/releases/<版本>/src` 的 `source_path`。开发机不启用。

```powershell
# 先完成数据库迁移20260919_0029及正式只读预演，再安装
.\scripts\shipment-watch-task.ps1 -Action Install
.\scripts\shipment-watch-task.ps1 -Action Status
# 停用后当前周期正常结束；立即禁止新发布可关闭网页人工待办开关
.\scripts\shipment-watch-task.ps1 -Action Disable
```

计划任务 `Leedis Shipment No Trace Reminder` 每5分钟触发，复用正式守护账户的登录身份，通过 `pythonw.exe` 无窗口运行。运行中不启动第二份实例，数据库命名锁也禁止跨进程/机器并发。单轮平台限流、追赶积压或接口耗时会延后提醒，不能承诺精确到20小时整。

巡检队列优先处理已发货满20小时、尚未满24小时的订单；组内按应检查时间轮转，接口失败重试不会清掉其他订单的排队时间。超过24小时的历史订单继续补查。正式入口每轮最多核验200笔，降低历史大批次占用时间；历史回溯完成不等于每笔物流已检查，不得用“游标已追平”替代待检查队列是否及时的判断。

运行输出：`.runtime/shipment-watch.log`、`shipment-watch-status.json`、`shipment-watch-error.log`。`lagging_shops` 表示增量落后超过10分钟；`sync_errors`、`order_errors` 必须处理，不能当作无待办。首次72小时回溯完成前不代表覆盖已追平。

数据库新增 `shipment_watch_cursors`、`shipment_watch_orders`、`shipment_no_trace_notices` 三张表；原数据库完整备份自动包含这些表。备份及代码打包脚本同时保存独立发布指针和对应代码；迁移恢复必须保留这三张表及原待办ID。回退只关闭独立任务或指向兼容代码，不删表、不清游标、不覆盖业务数据。
