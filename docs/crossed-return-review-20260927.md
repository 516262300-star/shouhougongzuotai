# 多订单退货单号交叉填写：识别、核验与纠偏

## 行为与边界

此前模块2只对同一运单关联多笔售后触发整批核验；不同运单交叉填写会沿单票比较，产生少退/错退误判。新入口在按单票登记失败或核账前，读取客户完整销售退货账页，沿退货行原销售ID追溯平台订单，识别实际包裹与平台填写运单不同的情况，相同SKU也检查原销售关联。

确认交叉后按原销售—实际包裹扩展范围，并包含同一原销售出库单中的其他退货退款订单，不以同客户或相同SKU合并全部历史订单。不受当前候选页、ID下限及候选数量截断；每轮只修改本轮选中的订单。

- 型号、颜色、数量及原销售归属一致才保存逐单实收分配。稳定退货行只能占用一次，已退款订单的实收也占用；有独立差异的订单不消耗实收，不妨碍其他有完整独立证据的订单。
- 未退款或对应ERP退款流水未核实，保留实收分配、转人工核验；不创建虚构的一单一收货、不生成质检PASS、不调用平台退款或ERP补单。
- 已退款且逐单退款流水、原销售及商家应收等证据完整时，沿用整批退款后核账结论，明确不是质量验收。
- 客户/店铺冲突、重复售后、原销售不唯一、未知资金结果、人工争议、分页不完整、实收占用冲突，继续待核，不放宽保护或自动重试资金操作。

## 历史系统误判

允许原系统ERP核对产生的FAIL再次进入核验。只有原始系统文案可重现、收货单号/运单/商品与ERP实际包裹一致、没有人工质量结论或证据附件，且整批商品可唯一分配时，才撤销单票错配结论。

历史FAIL只补查交叉包裹，不回落单票重验。没有交叉证据、客户归属不唯一或整批证据不完整时，保留原状态及原验货结论，将待核原因写入轮询记录；真实ERP连接故障仍报告执行失败，不掩盖故障。

原收货登记、平台填写单号和实际商品均保留；质检状态回到PENDING，原结论追加在收货备注的“跨包裹纠偏原始审计”中，不变成PASS。人工失败和真实数量/商品差异不能借此撤销。

已发送待办保留原文、外部回执和发送时间，只追加纠偏事实；工作台显示“单票错退判断已撤销”。这不等于远端待办已办结，也不重新发送。未尝试、无回执的原误判通知才可取消；已发起或结果未知的通知不能盲目重发。

## 运行、审计与恢复

沿用现有模块2轮询、启用店铺及平台范围，不新增计划或开关。完整客户数据仅在本轮缓存；查询失败记录具体原因，下一轮重查。短摘要不超过数据库50字符，完整原因保留在轮询记录。

审计和唯一分配保存在 Git 忽略的 `.runtime/audits/module2-shared-returns.sqlite3`，个案调查、预演和部署证据保存在 `.runtime/audits/`。复核后以订单锁定读和仓库快照排除期间变更，再持久化分配及业务事实；SQLite占用先于业务状态落账，故中断时只能核对已有占用后幂等恢复，不能删除占用重做。

部署使用当前正式机发布副本，隔离测试后安全停止当前周期、备份，再切换worker和仅含待办事实展示变更的web发布。回滚代码保留分配、原记录与纠偏审计，不伪回滚已发生事实。
