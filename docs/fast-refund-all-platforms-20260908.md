# 跨平台“快速退款未入 ERP”规则

## 业务定义

根据用户确认，拼多多、天猫、淘宝、1688、京东、抖音都可能出现平台退款先完成、订单未导入 ERP 的情况。最终业务归属应落到业务员或快速退款未入 ERP；查询失败/未完成是过程状态，不是新增最终业务类别。

本次去掉快速退款分类中的拼多多店铺限制，后台归属只读同步采用所有启用店铺范围，与资金动作的天猫试运行开关、起始 ID 解耦。平台同步范围、平台退款权限、ERP 补单/认领及人工待办发布开关均未改动。页面无缓存时，支持的启用平台显示等待查询，不再因为属于京东/淘宝/1688/抖音就标为“归属查询未接入”。

## 统一条件与证据不足

所有平台均要求：仅退款、明确未发货、平台退款已成功、没有发货运单、ERP 查询成功且没有客户结果、本地没有已知客户。查询异常、已有客户但缺业务员、已出包、发货未知、交易仅关闭、退款未完成不能自动归类。

非拼多多不借用拼多多的旧数字退款成功码，必须具有 `refund_financial_status=SUCCESS`。旧非拼多多映射可能在取消/锁定/缺资料时默认生成 `UNSHIPPED`，因此分类额外要求原始状态明确表达未发货；不修改这些旧订单的发货字段来强行放行。

当前可识别的明确状态包括 `WAIT_SELLER_SEND_GOODS`、`WAIT_BUYER_PAY`、`TRADE_NO_CREATE_PAY`、`waitsellersend`、`waitbuyerpay`、`WAIT_SELLER_STOCK_OUT` 及明确未发货文字。关闭、取消、锁单、缺失以及尚未验证含义的数字状态保留待核验。规则覆盖抖音不代表其所有历史数字状态已完成核验；当前没有启用的抖音店铺及真实样本，不能声称已做抖音生产验收。

平台状态资料参考：[阿里官方订单状态定义](https://developer.alibaba.com/docs/api.htm?apiId=42526)、[京东官方订单接口示例](https://help.jd.com/oapihelp/question-470.html)。这些资料不能证明某笔关闭订单之前从未发货。

## ERP 查询能力

已读取管理系统 `Customer::get_customer_by_initial`：长平台订单号通过 `resolveCustomerByOid` 反查客户，入口不限定拼多多。工作台网页适配器声明支持六个平台；旧数据库直连查询仍固定拼多多前缀，只声明拼多多支持，防止不支持的平台空查造成错误分类。本次不改 ERP 源码。

后台总批量及失败优先名额沿用原设置（默认20笔、到期失败优先10笔），不会按平台倍增请求量。正常归属缓存默认每日复查；分类结果仍保留售后记录，不等于平账闭环。

## 命令和部署

全部启用平台只读预演（不改本地缓存）：

```powershell
.\.venv\Scripts\python.exe -m aftersales_workbench.integrations.erp.sales_owner_cli --all-platforms --limit 20 --dry-run
```

可加多个 `--platform-order-sn <订单号>` 限定目标。去掉 `--dry-run` 只更新客户归属缓存，不执行退款、补单、认领或消息发送。旧 CLI 不加 `--all-platforms` 时保留原平台筛选参数的语义。

无新环境变量、数据库迁移或前端构建要求。先备份数据库与日志，等待旧后台当前周期自然结束，再重启后台和 Web。不要重置退款权限、删除动作任务或将未核实历史单批量改成快速退款。独立自动守护此前未恢复，本次不得声称已完成24小时运行保障。

测试包括六平台共用规则、明确原始状态、退款失败/未知、有运单、错误空结果、停用店铺、数据库适配器范围和跨平台只读缓存。真实业务标识保留在本地忽略目录 `.runtime/audits/`，不上传 GitHub。
