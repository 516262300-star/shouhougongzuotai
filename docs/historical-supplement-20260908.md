# 历史资料隔离补查（2026-09-08，第三批）

## 目标与边界

补齐历史售后页面需要的买家实付金额、ERP 客户和归属业务员，不让补资料等同于重新启动旧售后动作。

新入口是 `python -m aftersales_workbench.services.historical_supplement_cli`。它不是原 `pdd-backfill-refund-amounts` 的别名：原命令会重新分类流程并取消部分退款遗留任务；新入口完全不调用这些流程函数。

本命令不调用平台同意退款、企微发送、ERP 认领或补单接口，不修改同步游标、上线水位或 `.env`。没有新增定时任务；每次只运行操作者指定的有限批次。`--apply` 只表示写本地资料和独立检查台账，不代表允许对外写入。

## 补查类型

### `pdd_paid`：拼多多历史买家实付

- 仅选当前仍为 `PENDING_CHECK`、平台明确退款成功、缺少买家实付的拼多多记录。
- 指定的 `--max-order-id` 必须早于当前 `MODULE2_ERP_INTAKE_MIN_ORDER_ID`，避免触碰正在自动接入验货的新单。
- 已发货仅退款的在途单不纳入，避免补金额后重新进入拦截通知候选；未发货单仅在商家应收仍缺失时纳入。
- 读取同一店铺的 `pdd.order.information.get`，精确核对平台订单号，以订单接口 `pay_amount` 的元单位金额补入 `platform_order_amount`。不使用申请退款金额反推买家实付；无金额、非正数、非有限值、超范围或超过两位小数时拒绝补写。
- 若订单详情返回 `50001`（订单不属于当前店铺或不存在），只允许同店铺售后详情兜底：售后 ID、平台订单号必须全部一致，最新售后状态必须为 `10`，使用 `order_amount` 的整数分换算为元。授权、限流、网络等其他错误不兜底，不跨店找金额，不改变所属店铺。售后申请金额 `refund_amount` 不能替代订单实付。
- **只补买家实付这一个字段**。商品额、优惠拆分、商家应收、财务结果、流程状态、动作任务都不变。历史未发货单的商家应收缺失闸门继续保留，不能因此自动补开 ERP 退款单。
- 平台未明确退款成功的记录不纳入，需要另行核实该售后，不能用批量补查解除其限制。

### `tmall_owner`：天猫历史客户归属

- 仅选 `TMALL_MODULE123_MIN_ORDER_ID` 之前没有本地归属缓存的天猫记录；排除仍有待执行、执行中或失败动作任务的订单。
- 不修改天猫水位，不扩大平台退款或 ERP 动作范围，已匹配的缓存不覆盖。
- 复用 ERP 网页只读客户查询，使用旧系统 `PlatformService` 已定义的 `tmx` 前缀加完整订单号。按源代码，该方式走订单索引并跳过姓名、地址和旧名的模糊查询兜底。
- 单一客户、单一业务员才记为匹配；未找到或有归属冲突如实保存，不猜经办人。接口异常或客户不唯一时不修改旧缓存。
- 只写客户、业务员、缓存状态及本次查询时间。没有开退货单、认领、平账或发布待办。

### `tmall_status`：点名补回历史退款成功事实

- 必须提供 `--record-ids`，不允许默认全量扫描。上限同样必须早于 `TMALL_MODULE123_MIN_ORDER_ID`。
- 只选本地 `UNKNOWN` 且两项平台状态文字均为空的历史天猫仅退款；要求流程仍为 `PENDING_CHECK`、本地未发货且无发货单号，并排除存在任何动作任务（包括已成功任务）的记录。
- 使用对应店铺关闭写权限的客户端，只读取售后详情。接口返回的售后 ID、父订单号、退款金额须与本地完全一致；必须明确返回 `status=SUCCESS`、`order_status=TRADE_CLOSED`、`has_good_return=false`，否则不补写。
- 只补 `refund_financial_status`、`platform_after_sales_status_text`、`platform_order_status_text` 三个字段。售后接口的 `payment=0` 不覆盖买家实付，`modified` 不冒充退款完成时间，不重新判断发货状态，不更新业务时间、流程、客户归属、金额、同步游标或动作任务。
- **交易关闭不等于退款成功，也不能单独证明未发货。** 本命令以售后成功结果补财务事实，不是“无需 ERP”判定器，不能用它认定售后已平账闭环。
- 沿用逐条比较更新、连续3次失败停止与固定脱敏错误；检查台账范围为 `history_tmall_status`。失败会记下24小时后的建议复查时间，但本入口强制点名，`--record-ids` 按既有规则可绕过该间隔，须由操作者核实后再运行，不应把命令循环执行。已补成功的记录退出候选。没有新增后台调度或扩大历史自动化范围。

```powershell
# 本次已独立核对的三个本地主键；默认只读预演
.\.venv\Scripts\python.exe -m aftersales_workbench.services.historical_supplement_cli tmall_status --max-order-id 3348 --record-ids 2439 2469 2475 --limit 3
# 备份并确认预演结果后，加 --apply 只更新本地三个状态字段
```

## 使用方式

先确认数据库已完成第一批迁移（`20260908_0020`），并为正式补写建立本机备份。`--max-order-id` 是本地售后表主键上限，不是平台订单号。以下数字是本次核对出的历史边界，迁机后须按实际水位重新确认，不能照抄以扩大范围。

```powershell
# 只读小样本，不写资料或检查台账
.\.venv\Scripts\python.exe -m aftersales_workbench.services.historical_supplement_cli pdd_paid --max-order-id 1533 --limit 3
.\.venv\Scripts\python.exe -m aftersales_workbench.services.historical_supplement_cli tmall_owner --max-order-id 3348 --limit 3

# 验证、备份后补写本地资料；每批最多500条
.\.venv\Scripts\python.exe -m aftersales_workbench.services.historical_supplement_cli pdd_paid --max-order-id 1533 --limit 500 --apply
.\.venv\Scripts\python.exe -m aftersales_workbench.services.historical_supplement_cli tmall_owner --max-order-id 3348 --limit 500 --apply
```

拼多多每次读取使用关闭写权限的客户端、单次尝试；两种查询均在请求前间隔250毫秒，正常同步不暂停。进度每10条输出一次，结果只输出汇总及异常记录的本地主键，不输出客户姓名、凭据或第三方异常原文。

## 失败、并发与恢复

- 候选范围在数据库 `LIMIT` 前过滤。正式补写时用独立 `automation_poll_states` 范围 `history_pdd_paid`、`history_tmall_owner` 记录检查时间与固定诊断；本次错误记录24小时内不重复查。
- 24小时仅是**再次手工运行该命令时**的重查资格，不代表后台已经安装了自动重查任务。已匹配/已补金额的记录会自动退出候选；本命令曾查过的天猫未找到或冲突记录，时间到后可重查。
- 连续3次查询或数据校验失败时停止本批，保留已成功结果；检查外部接口后再运行，未检查的后续记录不会被前面的失败项挡住。
- 每条记录独立事务，外部请求期间不持有数据库事务。补写前再次比较原始身份、状态和相关字段；后台已更新则不覆盖，计入 `skipped_changed`。业务 `updated_at` 不被补查伪装成新售后，检查时间保存在独立台账。
- 数据库错误会回滚当前记录并停止，已经提交的记录保留。不能以恢复资料为由整库覆盖正在变化的业务库；需要回退时，从本机备份逐条核对、只恢复本批修改字段。
- 明确核对过的个案可以用 `--record-ids` 指定本地主键立即复查，只绕过检查间隔，仍保留平台、历史水位、退款事实与并发保护。金额补查不会因后台单独刷新业务员缓存而覆盖或重写该缓存。

## 验证与遗留项

专项测试覆盖只读不落库、身份与金额校验、未发货商家应收保持缺失、流程和任务不变、排除在途仅退款/新单、并发不覆盖、失败脱敏与轮转、历史归属重查。完整测试应在独立测试数据库执行，不连接生产 ERP 或平台写接口。

天猫仍缺实付的6条售后对应两笔订单，本次只读复查均返回 `isv.trade-not-exist`。此错误不能区分订单不可见、已超查询范围或授权不足；不假定平台支付为零，也不使用退款申请金额填充。需进一步核对店铺授权与可查询范围。
