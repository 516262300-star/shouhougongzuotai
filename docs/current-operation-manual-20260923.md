## 一、先记住三个区别
1. **快递群消息已发送，不等于快递已经拦截成功。**系统允许在特定条件下先退款，仍有拦截失败的业务风险。

## 四、模块1：已发货仅退款拦截
### 1. 哪些订单进入拦截
必须是已发货、具有明确发货运单、仅退款，且申请的是全额退款。类型、发货事实、金额、店铺状态或接口字段不明确时，暂停自动处理。
全额按买家优惠后实付比较，不按商家应收比较。例如虚拟订单：买家实付9元，平台补贴1元，商家应收10元；买家申请退9元仍可属于全额退款。平台补贴与商家让利必须分别识别，不能猜测。
部分退款通常是配件、差价或补偿：保留售后记录，不因这一笔部分退款触发拦截。天猫同一交易有多个子单分别申请仅退款时，不能仅凭单笔金额小于整单实付排除；需从平台实时枚举全部子单，逐笔核对退款身份、有效状态、完整SKU和数量，全部有效仅退款金额合计等于整单实付且发货包裹唯一，才按整单纳入拦截核验。已签收或已进入退回流程的不补发拦截。原逐笔金额保持，合并拦截资格不授予逐笔自动退款权限；退款原因文字不能替代金额和状态核验。
### 2. 发送快递群
生成本地通知任务后，先核对整个包裹的订单及退款范围，再检查物流、群映射和已有发送凭证，通过后才发到已配置的快递群。同一快递公司、同一发货运单合并通知，防止同包裹多笔售后重复发群。
已经发货、有明确运单且满足有效全额仅退款和整包裹保护时，正常查询无轨迹、尚未揽收或连续多次无结果，都不能单独取消快递群通知。当前实际自动通知范围仍为拼多多和天猫。真实签收/退回证据按终态规则处理；超时、鉴权失败、身份不符等技术异常保留未发送，等待重新核验。正常无轨迹可以满足通知条件，但本身不是自动退款依据。
当前消息格式：
> 【售后快递拦截】
	发货运单号：实际发货运单号
	处理要求：请尽快拦截并退回发件方；如已派件，请先反馈当前状态。
快递群不发送店铺名、平台订单号、售后号或内部任务编号；这些信息留在工作台便于内部查询。快递公司与群名必须按已核实的精确映射对应，未配置不能猜群发送。

## 五、模块1：平台退款之后怎样闭环
主流程为：平台退款成功 → 持续核对仓库退货单 → 确认归到正确客户 → 核对型号颜色数量 → 核对对应ERP退款流水和累计应收 → 售后已闭环。
退款完成后即建立ERP跟踪任务，无需等物流显示“退回签收”才查仓库单。物流停在某一天不代表仓库没有收货，应以最新ERP实收和账务证据核验。
### 查找顺序
1. 用平台订单确定唯一客户与原销售关联。
2. 优先查客户名下正式退货单，再查退货暂存列表，完整读取相关分页。
3. 核对完整型号、颜色、实收数量及原销售关联；同运单多笔订单须合并查看并保留逐笔唯一分配。
4. 还需平台明确退款成功、本订单唯一ERP退款流水与应退款口径一致、无欠货、累计应收实际为零。仅有退货单或客户总余额为零，不能证明某笔已经闭环。
### 天猫六店已开启的限定认领与补单
天猫第1—6店（含适家）已开启模块1原暂存单认领和ERP补单。当前限定独立客户、单原销售、单子单、单包裹、唯一单行TH退货；原收款、平台实际退款、SKU、数量、价格和应收均须符合专用核验。
系统逐步处理原暂存单搬入草稿、填写客户、保存，再回查原TH正式进入正确客户名下。保存响应或草稿消失只表示等待正式入账，不能立即登记平账。正式归属核实后，如确实缺本笔退款流水且负应收等额，单次补开退款单，再核对唯一退款流水、无欠货和零应收。
多订单、多包裹、部分退款、优惠或运费差额、其他收退款、价格不明、客户/SKU不符或未保存草稿冲突仍转待核验。认领的整张TH、账号占用与资金请求均持久化；断电或结果不明只回查，不重复搬单、保存或补退款单，不清理陌生草稿。
### 需要人工认领的情况
超出上述限定范围的暂存单继续按证据人工处理。在退货暂存列表找到正确运单行 → “修改”核实客户与订单 → 明细“修改” → “单价（点击刷新）”并核对金额 → 确认修改 → 保存。缺少客户关联时，通过原销售追溯订单，输入订单号取得客户候选后再核实选择；不能因名字相同就认领。
保存后回到客户档案，确认原退货单已正式入账且原销售、型号、颜色、数量、金额正确，再核对退款流水和累计应收。
拼多多继续现有已适配的核账及补单流程；天猫按专用适配执行。淘宝当前只读核验，京东、1688等未接入本项资金执行。具体订单资料不全时保留原因等待核实，不能用其他平台页面或补造单据放行。

### 标准退货与部分退货数量
- 平台按成品、ERP按部件记账时，先沿退货行追溯本订单原销售。完整型号、颜色、数量和唯一关联一致的，保留平台型号记法核对，不直接报少退/错退或退款后申诉；仍须独立质检和资金核验。详见 `docs/return-original-sales-identity-20260923.md`。
- 标准一对一退货：客户名下正式单和暂存都查。实收与本次有效申请一致、独立验货及其他条件通过，才进入自动退款核验；暂存实收不等于已认领或已平账。
- 购买数量不等于本次申请退回数量。拼多多有明确有效的部分售后件数字段时读取该字段；没有明确申请数量时保留待核实。天猫退款接口的num按购买数量保存，不能直接用于认定少退。
- 对拼多多和天猫，正常实收型号、颜色属于购买明细，实收件数较少但本次应退数量尚未明确时，显示“本次退货数量待核实”，不制造“少退”失败验货、外部误报或退款后申诉，也不自动退款。禁止用退款金额除单价倒推件数。
- 已退款天猫个案经用户明确数量并核实平台、原销售和唯一实收后，可保留确认数量；业务快照变化即失效。普通同步不会用购买数覆盖仍有效的确认，但这不是自动推断数量。
- 明确申请数量后的真正少退、错型号、错颜色、多退、质量异常或包裹争议继续核验。纯系统旧少退误判符合严格条件时可纠偏，原结论留审计；质检恢复待核验，不能冒充质量通过或财务闭环。历史已发待办保留，未发错误待办在提交前拦截。
### 退款后追货与共享退货包裹
平台已提前退款仍继续核对退货、实收和账务；有真实异常再按规则提醒业务员处理申诉，不再退第二次款。
同一退货运单关联多售后时，已接入整批只读核验：读取客户完整销售/退货分页，沿原销售扩展本批全部相关订单和实际包裹，逐项核对完整SKU、颜色、数量及唯一实收占用。平台填错或交叉填写运单时，不能只查目标售后的那一票，也不能仅凭总件数或总金额相同放行。
拼多多已经明确退款成功且唯一实收、对应ERP退款流水、无欠货和零应收均通过的，可记录整批退款后核账结果；这是财务核验，不能当作质检通过。未退款或其他平台仍保留独立核验/人工范围。多客户、多订单、多包裹无人值守自动退款尚未开启。
人工整批核验发现独立、无争议的可退款订单后，需有明确资金授权才实际处理；授权范围固定，执行前再次复核平台状态、金额、SKU和实收占用。已退款及已占用数量不能再分配，资金结果不明只回查，不重试。
### 历史异常不补发
模块2异常待办沿用已确定的新记录起点：本地收货记录ID从666起才进入新增待办范围，之前记录不因后续退款或升级再补发。本起点与自动退款起点分别控制；旧记录仍可查询和核验，不表示旧异常已解决。不要把起点重置为0。
## 七、模块3：未发货退款与“快速退款未入 ERP”
未发货仅退款常由平台先行极速处理，因此看不到待商家同意的未发货售后是正常可能情况，工作台仍需记录平台退款事实。
### 已经进入ERP的订单
拼多多沿用现有未发货履约与ERP补单核验。天猫六店已开启专用未发货平账：必须平台退款成功、实时明确未发货、独立原订单、单子单整单等额，并核对客户、SKU、原收款、欠货及已有资金请求；缺本笔退款流水才单次补开，回查唯一流水、无欠货和零应收后登记结果。
交易关闭、缺少发货时间或物流查询无结果，都不能单独证明从未发货。多订单、部分退款、金额或客户冲突仍阻断。模块1和模块3共用资金防重，不因换模块重复补单。已出包订单按原人工流程核实，当前没有覆盖所有打包台的自动锁包能力。
### 快速退款未入ERP的订单
“快速退款未入 ERP”是所有平台都可能出现的业务情况，但不能仅凭页面标签认定无需补单。
2026年9月10日新增拼多多模块3分流：本地明确未发货、仅退款、平台资金成功、无运单和历史物流、无已知ERP客户关联，再核对ERP唯一退款事实的售后号与商家应收、系统订单号为空、已归档、无任何待处理动作，以及平台订单反查客户明确为空，才显示**“无需 ERP 补单”**。
这类售后保留记录，不再误计为ERP查询失败，不因此生成业务员误报；每天复查一次，后来进入ERP或出现待处理动作时重新核验。不会伪造ERP取消订单成功、退款单号、余额为零或售后已平账。
真实超时、权限错误、重复记录、金额不符、仍有待处理报价单/补单动作等继续待核验。旧异常逐笔重查，不批量清空。
## 八、人工待办怎样发给业务员
收件业务员从对应订单的ERP原发货销售单“归属业务员”读取，普通模块1/2/3、同包裹事项和揽收提醒均适用。客户档案只用于定位客户，不能用档案默认人员替代原销售归属。
同订单多行的业务员须一致且非空。缺失、冲突、分页不全或查询失败时保留本地原因，发布前不领取发送、不消耗发送次数，通常冷却5分钟后在下一后台周期重查。ERP修正资料后重新核对，不猜人发送。只查业务员时允许同单存在合法零数量历史行，但须有正常正数商品行且全部归属一致；这不放宽商品数量或退款核验。
### 发送与防重
成功匹配后发布到原管理系统待办事项，只有回查确认远端存在才登记已发送并保存ERP待办ID。同包裹按业务员合并；收件人改变只修正未发任务，已发记录保留原收件人、正文及凭证。
事项文字说明订单、具体差异和处理要求，不显示内部模块编号、无用哈希或平台快递公司数字编号。完整明细和审计仍在后台保留。旧成功待办不因文案升级重新发送；退款后真实异常申诉有独立业务身份，不把普通待办与申诉混为一条。
“自动发布给业务员”开关控制后续发布；关闭仍可生成本地待办，既有人工锁保持。已经开始提交的请求仍可能完成。请求结果不明只读回查，不删除重建或盲目重试。
常见事项包括同包裹部分退款、拦截失败、派件/签收阻止退款、暂存待认领、真实实收差异、应收差额和确需人工核实的ERP异常。仅等待仓库开单或技术查询失败，不自动描述为业务员操作错误。
### 普通订单：发货20小时无物流提醒
拼多多7店、天猫6店、京东2店已开启，共15店；淘宝暂未开启。此项不要求先申请售后，独立任务每5分钟触发，初次读取最近72小时修改记录，之后持续增量。
按平台真实发货时间逐包裹计时，满20小时且经过有效查询仍无任何物流信息时，提醒原销售业务员联系仓库/快递核实交运、催促揽收并回传轨迹；超过24小时的漏单也继续跟进。20小时是内部业务阈值，相对24小时提前4小时，不等于各平台统一处罚或订单承诺时限。
- 任何有效物流节点（含下单、待揽收）均不属于本项“无物流信息”。已有轨迹、已完成/取消等结束订单和全额退款成功订单排除；部分退款、申请中仍继续监控。退款完成状态不明时留待核验。
- 天猫额外核对原生轨迹；快递公司、运单和平台身份必须一致。顺丰缺少逐运单电话验证时，查询无结果不能证明未揽收；未知快递编码、超时、权限或接口异常保留后台重查，不发无物流误提醒。
- 同包裹、同快递公司、同业务员合并为一条。无其他相关订单时，正文为“【揽收提醒】 店铺，订单主单号，运单运单号。”；多个不同订单合并时，再追加“相关订单：主单号、关联单号。发货满20小时仍未查到物流信息”。不再发送发货时间、剩余分钟、超时提示及联系仓库/快递的长说明。已经发出的原ERP凭证不重写、不重发；内部编号和快递公司数字编号仍不进入正文。
- 在“人工待办”筛选“发货20小时无物流提醒”，可用订单或运单搜索；“接入能力”查看每店开启、同步及核验异常。发现轨迹、全额退款或订单结束的记录按本类规则退出日常列表，后台原发送凭证继续保留；结果不明仍供回查。
这项提醒只创建业务员待办。客户已发货后申请有效全额仅退款时，是否发快递群另按第四节判断，不能套用“有轨迹就不催揽收”来阻止必要拦截。

## 十一、售后归因、报废及尚未完成部分
### 售后归因
按平台、店铺、型号/SKU、原因及日期查询。申请金额与明确成功退款金额分开；同一售后多SKU不能重复累加退款金额。原因分类只用于分析，不替代退款安全条件。
当前缺少完整同期销量分母，不能把售后申请占比叫作真实退款率。缺失的型号、材质、颜色或金额应显示缺失，不为凑齐多级看板虚构字段。
### 退货报废
读取ERP退货行，颜色以“报废”开头作为自动识别线索。原ERP行与人工核定分层保存；原销售/退货单价不是损失成本。原因、核定损失和复核信息齐全后才计入已确认损失。
报废率当前分母是同期ERP全部退货数量，不是全部发货数量。当前功能是只读同步与本地核定，不会自动新开ERP报废单、向供应商扣款或改ERP原单。
### 仍需独立完善或验收
- 抖音售后同步未开启；淘宝只读核验未开启执行，京东及1688未接入自动拦截/退款及ERP资金流程。京东普通订单揽收提醒已经单独开启。
- 淘宝普通订单揽收提醒仍受物流接口权限限制；顺丰需要可靠的逐运单电话验证，查询错误继续待核验。
- 天猫六店已有专用的限定ERP认领、补单与核账；复杂多订单、多包裹、部分金额/数量及关联冲突仍不自动放行。其他未适配平台不能套用拼多多或天猫资金流程。
- 暂存退货单全范围自动认领、跨客户跨包裹无人值守退款未开启；已有共享运单只读核验和特定已退款核账不授予新退款权限。

- 当前没有完整多用户认证与权限体系，不应直接开放公网。
- 当前工作区还有其他开发中的改动；一次Git提交号不代表所有本机未提交功能都已经备份或可直接部署。
## 十二、启动、停机、换电脑和排障
### 日常开机
常开执行电脑要有正确运行环境、数据库、配置和企业微信登录。现有登录启动/守护会尝试拉起MySQL、Web和后台；开机后检查首页、运行监控和最近同步时间。登录启动不等于未登录Windows时就能操作企业微信。
网页打不开时，先分清Web、后台和MySQL哪个没运行，不要反复重装或初始化非空数据库。维护人员可在项目目录检查：
```plain text
.\scripts\module1-worker.ps1 -Action Status
.\scripts\module1-autostart.ps1 -Action Status
```
需要维护时，先停止守护，再请求后台安全结束当前周期：
```plain text
.\scripts\module1-autostart.ps1 -Action StopWatch
.\scripts\module1-worker.ps1 -Action Stop
```
维护完成并核对原开关后恢复：
```plain text
.\scripts\module1-autostart.ps1 -Action Run
.\scripts\module1-autostart.ps1 -Action StartWatch
```
以上为维护命令。仅停止业务后台不足以停止独立揽收提醒；需要停写或迁移时还应按维护清单停止该任务及其他写入来源。资金请求进行中不要强杀后台，重启不会解除未核验发送账本。本次说明更新仅只读核对正式配置，没有执行这些启停命令。
### 常见提示
- **物流闸门查询失败：**没取得足够可靠的物流结果，需要查具体错误；不等于已经证明未揽收。
- **待核实：**缺少或存在冲突证据；不能仅凭“平台已经退款”补造其他状态。
- **待接入ERP：**可能是该平台对应动作适配尚未完成，不一定是账号密码错误。
- **快速退款未入ERP：**平台先退、ERP无原订单关联的分类；还需独立核验是否“无需ERP补单”。
- **正常同步已推进，异常单已隔离：**正常数据继续推进，异常记录等待重查；不是整个店铺完全停止。历史订单也可能因平台修改时间进入增量结果。
- **未配置快递群：**检查当前标准快递公司映射；是否发过必须查通知任务和发送账本，不能只凭群名字段判断。
