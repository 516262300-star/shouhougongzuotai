# 运行周期失败与 ERP 退货任务范围修复

2026-09-23 新正式机运行监控出现“最近周期存在失败”，但三个模块均显示正常。核查原始周期与任务后，发现两处问题。

1. 模块1拦截退回查询仅适用于“仅退款”，却按共用的 `ERP_MATCH_RETURN_ORDER` 动作类型读取了模块2退货退款任务。模块2使用退货运单及原有仓库/退款流水核验，部分任务缺少原发货运单，被错误登记为查询失败，并优先占用查询批次。
2. 监控漏列 ERP 退货闭环查询等六个后台阶段，导致顶部失败提示与模块卡片不一致。

## 修复边界

- 模块1查询在数据库分页之前限定 `ONLY_REFUND`。模块2任务仍保持原状态及历史记录，由原有退货退款流程继续核验；不将退货运单冒充原发货运单。
- 不清除旧失败记录，不确认退款、仓库验货或财务闭环，不重发资金请求或企微消息。模块1真实缺少身份、服务异常等问题继续报错。
- 监控补齐其他平台同步、ERP 业务员归属、ERP 退货闭环查询、ERP 报废同步、人工待办生成和发布阶段。失败时所属模块显示“需要检查”，保留具体错误及明细入口；缺少可核实订单来源时明确说明，不展开无关历史订单。
- 保持原有运行周期、计划任务、店铺权限与资金保护。无数据库迁移。

## 验证与发布

本地通过 109 项相关测试及 Ruff：覆盖大量模块2积压不挤占模块1批次、只读/正常运行不改写模块2证据、真正模块1失败仍保留、服务熔断、闭环保护、天猫分组核验、监控阶段与失败定位。

部署以新机现有 Worker/Web 发布目录为基础，仅合并本次变更，保存原指针及文件哈希；Worker 等待当前周期自然结束后切换，Web 独立更新。部署后以新的完整周期和状态接口确认，不以历史日志删除或改写取得“正常”。审计证据保存在 Git 忽略的 `.runtime/audits/monitor-failure-20260923/`。
