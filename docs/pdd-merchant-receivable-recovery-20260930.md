# 拼多多人工待办“缺少有效商家应收金额”修复

## 状态与结论

2026-09-30 完成生产只读取证、代码修复和正式版本候选验证，**本轮尚未部署，未回填生产金额或修改既有待办**。正式环境仍使用 `residual-audit-20260930-145544-{worker,web}`。本修复不改变天猫自动退款、各资金执行开关、人工锁、历史水位及幂等保护。

该提示来自 ERP 补单入口的金额保护：预期商家应收为空或不大于零时，禁止补开退款单。保护本身正确，缺陷是历史金额字段未补齐，而后台直接使用缺失字段进入核验，没有先恢复平台金额事实。

## 修复逻辑与文件

1. `integrations/pdd/merchant_amounts.py` 新增只读金额核验器。使用原店铺配置，客户端强制 `write_enabled=False`，先校验实际授权商家ID，再查询售后和原订单。仅接受明确完整且非负的金额拆分；商家应收按**买家实付＋明确的平台补贴**计算，缺失补贴不得默认零。
2. 模块3自动恢复仅适用于平台当前已成功的未发货整单仅退款。售后身份、SKU、数量、申请金额、买家实付、本地已有金额必须一致；有发货/退货运单、历史实物流转、部分退款或事实冲突时继续阻断。金额条件更新比较原快照，避免覆盖核验期间的并发变化。
3. `workflows/module3_erp_refund.py` 在缺有效商家应收时先调用核验器，再执行原 ERP 只读核验；生产执行路径保存金额证据，dry-run 仅在内存使用核验金额。平台回查失败明确报“商家应收平台回查失败”，不伪报ERP数据不存在。恢复金额不等于ERP已平账，原核账、资金幂等、同步安全闸门及外部回查保持。
4. `workflows/module1_worker.py` 和 `module3_erp_refund_cli.py` 为拼多多路径接入上述核验器；按原批量上限与到期轮询逐笔处理，不扩量、不重置复查时间、不重放生产任务。天猫路径不改。
5. `integrations/pdd/amount_backfill.py` 的仅退款金额补齐覆盖未发货记录，按指定店铺在SQL层过滤后再取上限，逐笔验证原店铺及事实。新增未发货范围只恢复金额字段；原已发货且有运单范围仍执行既有退款范围复核。逐笔保存点避免单笔失败留下半截更新。

## 历史待办如何处理

金额恢复后仍须原履约任务重新核验。ERP仍有缺单、金额/商品不符等真实异常时继续转人工，不能把488笔都直接标成功。

未发送待办按原逻辑更新原因；只有核验结果确实解除异常后才取消符合条件的本地待办。已发送待办保留审计，不因本地金额修复伪造远端撤销，也不重复发布。结果未知的资金操作只读回查，不重发写请求。

本轮没有批量处理原488笔，也没有改13条待发送或1条已成功待办。尚未逐笔证明全部488笔都能恢复金额或完成ERP核账；8笔真实样本只证明该样本范围可恢复。
