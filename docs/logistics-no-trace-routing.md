# 快递100“无轨迹”分流与退款冻结

## 适用范围

本规则用于模块1的发送前物流预检和退款物流闸门。它只处理快递100正常响应但暂时没有可用轨迹的业务结果，不改变网络错误、HTTP错误、配置错误和响应格式错误的技术故障处理。

2026-09-22起，发送前预检与退款闸门分开：**已发货的有效仅退款订单，正常查询无轨迹仍须发送拦截通知，不再因连续达到6次取消通知**。所有平台统一遵守发送前整包裹核验：同包裹仅部分订单退款仍转原销售业务员，不发快递群；未适配完整核验的平台不绕过核验放行。详见[无轨迹拦截修复](no-trace-intercept-20260922.md)。

## 处理规则

- 同一运行周期内，相同快递公司、运单号和查询手机号只请求快递100一次，多笔售后共用缓存结果。
- “查询无结果”“暂无轨迹”“暂无物流”或成功响应中的空轨迹统一记为 `no_trace`，不再把整个物流闸门阶段判为失败。运行日志同时输出无轨迹售后数和去重后的无轨迹包裹数。
- 第1至第5次无轨迹继续按5、10、20、30、30分钟退避复查；没有有效单笔人工确认时，自动退款始终冻结。
- 发送前预检：连续第6次及以后正常无轨迹继续保留待发拦截任务、原失败次数和退避复查；物流保持 `UNKNOWN`、退款标记保持 `HOLD`。已有签收或退回证据、接口技术异常不能被当作本次无轨迹通知的依据。
- 发送后的退款物流闸门继续保留原无轨迹分流及独立风险规则；达到阈值可转 `MANUAL_PROCESSING`、冻结退款。这项资金保护不再作为取消尚未发出拦截通知的理由。
- 连续无轨迹本身不创建或发送业务员待办（2026-09-09 用户要求）；这不等于不发送快递群拦截通知。人工待办的候选及发布阶段继续排除仅无轨迹事项，不影响同包裹部分退款、拦截失败、ERP退货差异等其他待办。资金闸门原阈值分流保持；待发通知则重新查询，不再仅凭历史次数直接取消。
- 网络、HTTP、配置和返回格式异常仍计入 `failed`，用于运行监控告警；它们不会被误当成包裹无轨迹。

## 安全边界

- 无轨迹本身不是退款依据；只有文末说明的独立人工确认分支可在其他条件满足时放行。
- 转人工不会伪造物流、签收或退回证据。
- 平台退款请求仍禁止自动重试；结果不明时只做只读回查。
- 若人工修正运单或快递公司并需要重新进入自动链路，应先确认平台仍未退款，再由维护人员恢复合适的模块1流程状态并清理旧查询错误。

## 单笔明确未揽收确认

常规自动判断见[自动识别待揽收](automatic-uncollected-refund.md)：接口明确返回102且满足证据、发送与资金保护时，无需人工确认。102不是空轨迹，本文的无轨迹保护不因此解除。只下单/未知状态冻结退款并等待新证据；派件/签收的等待退回状态仍锁存。

2026-09-09补充：[人工确认刚发货未揽收退款](confirmed-uncollected-refund.md)允许在明确用户确认、已成功发出拦截、工作时间和平台实时核验通过后，登记单笔限时退款授权。仅支持拼多多；普通无轨迹、网络异常以及未经确认的其他订单继续沿用本文保护。不伪造有效物流或ERP闭环。
