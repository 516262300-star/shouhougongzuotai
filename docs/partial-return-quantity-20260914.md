# 部分退货数量与重复待办修复

## 问题与处理口径

拼多多同步器目前将 `goods_number` 存为 `applied_quantity`。该数据不能独立证明本次售后实际约定退回的数量。过去 ERP 实收少于购买数量时，模块2会直接生成“少退”的失败验收；平台后来退款成功，又生成独立的退款后申诉待办，造成同一数量误判的二次提醒。

从本次修复开始，对于拼多多 ERP 实收全部属于购买明细、型号颜色一致、数量为正整数且合计少于购买数量的情况，转为 **本次退货数量待核实**：

- 不用购买数量减实收数量认定少退，不写入新的失败或通过验货记录。
- 工作台保留人工处理状态，继续等待实际应退数量、整批包裹归属及独立质量证据；不自动退款、不自动平账。
- 不通过退款金额、优惠金额或单价倒推退回数量。即使退款金额等于订单金额，也要先核实实际应退数量。
- 型号错误、颜色错误、超过购买数量及人工仓库确认的质量异常保留原核验流程。本次保护不宣称这些差异已经完成整批归属核实。
- 天猫数量逻辑、共享运单整批分配、资金幂等保护和企微发送逻辑保持原有规则。

目前尚未新增可持久化的“本次应退数量及证据”录入流程。因此这类记录会继续处于人工核实状态，ERP 明细本身不能循环证明“应退多少”。后续数量确认和资金处理仍遵循[整批退货核验方法](customer-multi-parcel-return-verification.md)，资金操作需明确授权。

## 三处保护

1. `Module2ErpIntakeService` 在生成 ERP 自动失败验货前检查数量口径，新增 `quantity_reviews` 计数，详细核查提示进入轮询记录。
2. `Module2ExceptionTodoService` 对旧的系统 ERP 失败验货再次判断。命中后转本地人工核实，不生成新的普通待办或退款后申诉。历史收货记录和已发出的待办保留为审计事实，不伪造撤回或质检通过。
3. `ExternalActionExecutor` 在实际发布之前检查升级前已排队的相关模块2提醒。符合条件的 `PENDING` 任务取消并记录 `RETURN_QUANTITY_UNVERIFIED`，保留原任务内容，不发送外部请求。

旧记录必须明确由“系统ERP核对”产生且实收商品正常才适用重新分类；不能覆盖独立人工质检。已经成功发送的两个历史待办不会自动删除或重新发送。

## 验证与部署

测试使用虚构订单身份覆盖：购买51/实收27、退款前后、预演不写入、禁止生成通过或失败验货、分行数量汇总、退款金额不能推算数量、错型号/颜色/超量/质量异常、旧成功待办不派生误申诉、旧排队提醒在发布前取消。结合原模块2整批核验、独立质检与退款保护、动作执行及待办文案回归，共146项通过。

运行机以当前 Worker 发布源码为基础建立新候选目录，仅替换本次保护涉及的文件；保留企微原分辨率回执修复和原有退款确认逻辑。切换前持有守护周期锁、等待业务周期自然结束并做一致性备份，然后切换 Worker 指针并由正常守护恢复。无需数据库结构迁移，开发库不覆盖正式库。

个案证据和部署清单仅存于 Git 忽略的 `.runtime/audits/quantity-prevention-20260914/`；不将客户资料提交 GitHub。部署完成信息由实际验收后补充。
