# 天猫发货事实与模块3保护（2026-09-08，第五批）

## 修复结果与业务边界

平台退款成功、交易关闭、包裹是否发货是三个不同事实。旧天猫映射将所有未识别状态默认设为 `UNSHIPPED`，导致交易退款关闭后，原已发货单可能被降级为未发货。本批新增 `UNKNOWN`（发货状态待核实），不把资料缺失转化为自动取消排单的依据。

根据[淘宝官方交易接口说明](https://developer.alibaba.com/docs/api.htm?apiId=54&scopeId=12146)，`TRADE_CLOSED` 表示付款后退款关闭，`WAIT_SELLER_SEND_GOODS` 才是等待发货；[官方物流接口](https://developer.alibaba.com/docs/api.htm?apiId=235)提供独立物流状态、`seller_confirm` 等字段。本批还读取真实关闭订单确认：主单和子单可同时存在发货时间。因此不能仅凭关闭状态判断未发货。

不新增平台退款、企微通知、ERP 认领或补单；不修改 `.env`、自动化上线水位或计划任务频率。原有后台任务在迁移时安全暂停，随后按原配置恢复。源码参考目录 `daima` 和远端 ERP 系统均未修改。

## 新映射规则

- 明确已签收/交易成功，保留 `DELIVERED`；明确已发货/部分发货，或主子单存在有效发货时间，归为 `IN_TRANSIT`。
- 同一父订单其他子单已发货，也禁止将整笔 ERP 订单按未发货取消；不会因为一个子单签收，就把其余子单全部判为签收。
- 物流明确返回 `seller_confirm=yes` 可作为已确认发货证据。仅有运单号、物流关闭、物流列表为空，都不能单独证明实际发货或从未发货。
- `TRADE_CLOSED`、`TRADE_CLOSED_BY_TAOBAO`、空白、新未知状态，在没有发货证据时保留 `UNKNOWN`。不抛弃售后记录，不把未核实变成未发货。
- 只有明确的未发货状态且没有冲突证据，才映射为 `UNSHIPPED`。
- 同步更新保留已记录的 `IN_TRANSIT`、`DELIVERED`；退款关闭、缺字段或后来的“未发货”不能使其倒退。已锁包不会因“待发货”自动取消锁包标记。
- 订单详情增加读取 `consign_time`、`orders.status`、`orders.consign_time`。仅退款中发货状态未知的单据也尝试原平台只读物流查询；请求失败仍保留未知，不能降级为未发货。没有新增独立调度器，沿用原增量同步周期及每订单缓存。

## 模块3多层保护

1. 新任务筛选：天猫除原上线水位、财务成功、仅退款等条件外，必须具有明确未发货原始状态，且无本地发货运单；迁移前错误留下的 `UNSHIPPED` + `TRADE_CLOSED` 同样不会放行。
2. 旧任务执行：当前 `ErpWebUnshippedRefundClient.inspect/execute` 固定使用拼多多 ERP 页面，所以 `Module3ErpRefundService` 明确只处理拼多多。天猫不能借用该适配器，即使任务早已存在或通过命令点名也不行。后续支持天猫自动补单需要独立完成平台适配和验收，不能仅去掉过滤器。
3. ERP 回填：天猫模块3检查、取消、锁包、退款流水回填，在修改本地任务成功状态及创建下一步任务前，再验证发货事实。未知、关闭、已有运单或已发货时拒绝按未发货推进；`SHIPPED` 回填仍允许纠正为已发货，但不会生成取消任务。模块1的 ERP 退款回填不套用未发货保护。
4. 页面：待系统判定/部分退款的天猫仅退款，如果发货未知且没有更具体 ERP 闭环进度，详情备注显示“发货状态待核实”及阻止自动未发货处理的原因。退款成功标签独立保留。

原115个天猫 `ERP_CHECK_FULFILLMENT` 待执行任务保留原始台账，未伪造成功、未删除或重新发布待办；现有拼多多 ERP 执行器不会处理它们。保留任务不代表已完成，也不代表天猫模块3自动平账已正式接通。
