# 拼多多整包裹拦截前保护（2026-09-18）

## 业务规则

同一客户多笔订单共用一个发货运单，只有部分订单申请退款时，不自动向快递群发送整包裹拦截，不自动给申请单退款；通过 ERP 同包裹待办通知客户档案对应业务员核实。业务员联系客户确认仍需商品如何收货或部分退货，不能因其中一单退款影响其他正常订单。

用户案例审计保存在 Git 忽略的 `.runtime/audits/`，不在仓库记录客户、订单、运单和私有凭据。

## 自动化入口和状态

- 沿用正式机 `Leedis Aftersales Module1 Watchdog` 登录触发及每 5 分钟守护，后台通知阶段由 `DesktopNoticeSendService` 调用 `NoticePackageGuard`。没有新增定时任务、环境变量、数据库迁移或外部接口写权限。
- 当前新增保护覆盖拼多多桌面企微拦截。其他平台保持原路径，本次不宣称已实现跨平台自动合包核验。
- 在切换企微、搜索群和输入聊天消息之前，读取目标订单对应客户的 ERP 完整原销售分页，再用该店铺只读平台接口逐笔确认快递公司、运单和退款申请。规则、上限与[原退款保护](module1-shared-package-refund-guard.md)一致。已成功通知或结果未知的凭证保留原防重核验流程，不再发一次。
- 明确未申请退款、非有效全额仅退款等业务阻断：取消同运单及快递公司的 `PENDING` 拦截任务，订单转人工；沿用包裹、客户、业务员唯一键生成 `task_scope=shared_package` 待办。正文明确“不自动拦截整包裹”。既有包裹待办不重复生成，其他包裹继续处理。
- 读取失败、分页不全、跨店无权限、历史订单超过核验上限或证据过期：不猜测客户退款情况；通知仍为 `PENDING`，在任务 `notice_package_check` 保存失败原因及 5 分钟冷却时间，由后续周期自动只读重查。期间不输入消息，不创建猜测业务待办，不把整个桌面发送队列记为暂停。
- 通过后保存证据，真正输入前再次核对订单快照、任务状态、人工锁及证据不超过 80 秒。此时若发生变化，禁止输入，按现有发送前暂停机制处理，核实后重新完整检查，不能沿用过期证据。
- 监控通知阶段 `blocked_package` 统计本轮未放行的计划，包括业务阻断、冷却和非待发送任务；具体原因看任务 `last_error`/`notice_package_check`，不能把该数量直接当作客户数。
- 业务员缺失或待办发布开关关闭时，待办保留本地且仍然阻断拦截、退款。相关订单后来又申请退款也不自动解除人工锁。
- 退款回查若发现既有同包裹人工锁，保留专用人工原因，防止被普通退款失败覆盖后产生额外普通待办。不改已实际退款的成功事实、不自动重试资金请求。

## 历史消息与人工处理

本次不会撤回已发出的快递群消息，也不删除历史待办。过去已经发出拦截的包裹，需要业务员核对快递处理进度并协调是否撤销拦截；系统不能把“指令发出”当作“已完成拦截”或“已取消拦截”。

业务员在人工待办查看关联订单、原因和经办人。人工确认解决后按已有授权流程处理；不能删待办、清空发送账本或伪造收货来绕过保护。

## 验证和部署

新增测试使用内存数据库、模拟 ERP/平台及模拟企微，不发送真实消息或请求退款。覆盖合包部分退款、全包裹有效申请、所有未发送关联任务取消、待办去重和人工锁持久化、查询失败冷却、发送前快照变更/过期、已发送凭证保留、回查保留原人工原因。旧桌面状态机测试明确隔离外部包裹查询，新集成测试验证保护与原发送 hooks 一起工作。

部署仅基于正式机当前发布目录复制候选版本，校验原文件 SHA-256 后替换本次 5 个源文件，保留其他已上线修复。后台自然退出后使用 `scripts/office_verified_backup.py` 备份全部业务表、运行配置和发送账本，再原子切换 worker 发布指针并启动原守护；Web 指针不变。通过正式周期、队列、任务及待办只读核验，不用真实退款或重发消息验收。

旧版本缺少发送前保护。如需回退，应先暂停桌面自动发送，保留所有人工锁、待办、资金记录与发送凭证，再在停机窗口切回备份指针；不能恢复到旧代码后继续无保护发送。
