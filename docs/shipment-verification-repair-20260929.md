# 揽收提醒同步与核验修复

本次仅修复“发货20小时无物流提醒”的读取与判断。沿用独立计划任务 `Leedis Shipment No Trace Reminder` 每5分钟触发、逐包裹20小时阈值及原ERP业务员待办；不修改售后退款、仓库或企微拦截流程。

## 修复内容

- 1688兼容实际返回的 `send_goods_but_not_fund`，继续按真实包裹时间入队；不视为未发货或交易完成。保留商家绑定、完整分页和失败窗口不推进的检查。
- 1688明确 `type=2` 的无需物流记录，在关联子单完整且没有实际快递公司/运单冲突时不催揽收。缺少运单本身不能推出无需物流。
- 1688收到/退回商品（明确物流状态3/4）不再催揽收，兼容此时缺少商品交易状态；不写全额退款或ERP平账事实。
- 1688同一运单分商品行返回时，仅在快递公司、发货时间相同且商品子单互不重叠时合并为一个包裹。重复子单、身份不符、时间或公司冲突仍待核验。
- 天猫已完成/关闭交易先按交易结束停止催揽收，不再因退款编号缺失产生本项异常；活动交易仍按完整退款明细核验。交易结束不等同于全额退款成功。
- 抖音部分金额退款成功后继续核验剩余履约；不把子单“退款成功”误解为整单必须全额退款。实退汇总仍来自完整售后列表及对应成功详情；缺少成功明细、金额无效或超过实付仍阻断。
- “中通快运”映射为 `zhongtongkuaiyun`，与中通快递 `zhongtong` 区分。正式部署只把这一映射加到独立提醒副本，保留该副本其他源码，不覆盖正在运行的售后业务后台。

## 尚需资料的核验异常

电话验证码错误、顺丰无结果但缺逐运单电话、平台未返回运单/包裹等，不能视为实际无物流。现有授权响应没有可用的逐运单电话时继续待核验，不能用统一电话或猜测的号码替代。天猫物流列表为空、物流顶层“已签收”占位但无实际运单/轨迹时，不推断已经签收或无需物流。

“接入能力”的核验异常订单全部属于本提醒任务，计数不是消息发送失败数；同步异常计店铺游标或周期同步错误。配置“已开启”不代表同步正常。当前页面有每店统计，尚无逐单核验异常入口；“人工待办”只展示已经形成的提醒任务，不能完整代替核验账本。

## 验证、部署与恢复

本地及正式候选先运行相关离线回归；生产候选测试禁止外部网络及子进程，使用隔离SQLite。真实预演只调用平台和物流读取接口，不创建测试待办，不执行资金操作。异常只能由重新核验自然消除，不能直接清空 `last_error`、删除订单或重建发送记录。

候选以当前正式独立提醒发布为基线，仅更新4个源文件。使用新完整发布目录及 `shipment-watch-release.json` 原子切换；不改 `.env`、Web、业务后台、计划任务规则或运行入口。进行中的旧周期自然结束，下一周期读取新版本并从原失败游标续读，补回阻塞期间的增量。保留所有 `SENT`、`SUBMITTING`、`UNKNOWN` 和ERP编号，未知结果只读回查、不重新发送。

发布前保存原指针、改动清单和哈希至Git忽略的 `.runtime/audits/shipment-repair-20260929/`；验收核对新周期完成时间、1688游标追平、同步错误、逐单重查结果及网页健康。回退只恢复该提醒原指针，保留账本；回退会重新暴露旧状态适配问题，不能声称旧版已解决同步阻塞。个案详情和凭据不写入本文、GitHub或Notion。
