# 天猫部分退货数量误报修复

天猫售后同步过去将退款接口的 `num` 直接用于应退数量比较。该字段为购买数量，部分退货实收较少时，不能据此认定少退。官方接口字段说明见[天猫退款单查询](https://developer.alibaba.com/docs/api.htm?apiId=33878&scopeId=11527)。退款金额受优惠、分摊及税费影响，也不能用金额除以单价推断本次件数。

## 通用行为

- 同步购买数量至 `purchased_quantity`，来源标为 `TMALL_PURCHASE_NUM`。兼容旧数据的数量字段保留购买数，但该来源不代表已确认申请数量。
- 模块2数量保护同时覆盖拼多多和天猫：正常实收为购买明细严格子集、型号和颜色一致时，先留在工作台核验本次申请数量，不生成“少退”验货失败或外部异常待办，不放行自动退款。
- 已存在的纯系统少退结论，按单一售后、单一收货记录、唯一退回运单等原有条件撤销，原结论存入收货备注审计。历史成功待办保留；旧错误待办在发送前拦截。天猫历史扫描仍遵守 `include_tmall`、订单/收货起点和店铺范围。
- 错型号、错颜色、多退、明确申请数量后的真正少退、独立质检失败、共享运单或多包裹争议，继续原核验流程。

## 已退款个案的数量确认

用户明确确认本次申请数量，且经平台最新退款状态、ERP 客户完整销售/退货页、原销售关联和实收唯一性核对后，可在维护事务中记录 `TMALL_CONFIRMED_RETURN`。本次没有新增自动确认流程或平台数量提取接口；所有个案身份与证据只保存在忽略的 `.runtime/audits/`。

该来源只在平台已为 SUCCESS 的单商品售后中保留。重复同步必须仍为 SUCCESS，店铺、订单、售后类型、申请金额、退回运单、原因、备注、SKU 和购买数量均保持一致；变更后确认失效，恢复为待核实的购买数量来源。已确认值不会因为普通同步被购买数覆盖，失效后也不会自动恢复旧确认。

数量一致仅撤销错误少退结论：收货质检恢复 PENDING，系统因数量差异误写的 DEFECTIVE 撤为未知，保留真实实收及旧审计。不写质检 PASS，不宣称 ERP 已平账，不再次退款，不自动办结/删除历史已发 ERP 待办。
