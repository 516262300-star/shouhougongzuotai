# 模块3：快速退款未入 ERP 的补单分流

> 2026-09-10 审计修复：资金请求防重、异常响应、独立质检和发送回执规则已有调整；以[安全修复与部署说明](audit-safety-fixes-20260910.md)为准。代码准备不代表生产已部署或已验收。

## 解决的问题

归属同步的“快速退款未入 ERP”是业务分类，不等于查询失败，也不代表已开退款单或客户已经平账。旧模块3在 ERP 原订单为空时仍强制按平台订单匹配客户，导致正常秒退反复显示“ERP 平台订单未唯一匹配待处理记录中的客户”。

本次补单分流仅接入现有拼多多模块3适配器。跨平台归属规则保持不变；不得把拼多多 ERP 页面空查结果用于天猫、淘宝、1688、京东、抖音。ERP 源码只作参考，不改管理系统。

## 判定证据

本地必须同时满足：已归类 `not_required`、仅退款、明确未发货、资金状态 `SUCCESS`、无发货/退货运单、无历史实物流转记录、无已知 ERP 客户/业务员关联，且仍在模块3待核验状态。标签或极速退款标记单独不足以跳过。

ERP 核验必须全部通过：

1. 待处理退货退款页面具有预期完整表头，且没有该平台订单的任何待处理行。删除报价单、未知动作等同样不允许跳过，不能仅检查“补开退款单”按钮。
2. 精确查询所有退款，唯一记录的售后号和商家应收金额匹配。金额仍使用 `merchant_receivable_amount`，不能用扣除平台优惠券后的买家申请额替代。
3. ERP 平台为拼多多、退款成功、系统订单号为空、操作记录明确为“移除”。
4. 按平台订单号重新查客户关联，接口成功并明确返回空列表。错误、空白页面、格式变化、未核验分页、重复记录均不能通过。

源代码 `AliController::showlist` 对无系统订单、未启用且无报价单的极速退款，在延迟后归档；也有其他归档分支，因此不能仅凭“移除”认定不需补单。当前平台待处理页返回全量数据，无服务端分页；若出现分页需适配后再判断。

## 结果、复查与审计

- 独立结果 `erp_refund_status=not_required`，运行汇总单独统计 `not_required`；不计入 `unavailable`，不生成模块3异常待办。
- 列表和详情显示“无需 ERP 补单”，处理记录保留核验理由、时间及证据。
- 原售后记录保留。履约检查任务保持 `PENDING` 用于每日一次复查，下一次到期时间落在 `automation_poll_states`。从普通30分钟补单核验改为86400秒低频核验，不会每个后台周期重查。
- 不创建 ERP 取消订单/退款流水的成功任务，不标记 `UNSHIPPED_AUTO_REFUNDED`，不填造收款单号、欠款为零或闭环完成。技术工作流仍为 `PENDING_CHECK`，页面根据最新有效核验结果展示“无需 ERP 补单”。
- 后续发现 ERP 订单、待处理动作、金额变化或查询错误时，覆盖旧豁免证据，重新进入对应核验/异常路径；不会永久跳过晚到的 ERP 订单。平台发货状态等发生变化时页面不再采用旧豁免。
- 本单从未发送的模块3误报待办可以取消；已发待办、结果不明的发送任务及模块1同包裹待办不由此分支撤销。

## 验证与部署

单笔只读预演（不加 `--apply`）：

```powershell
.\.venv\Scripts\python.exe -m aftersales_workbench.workflows.module3_erp_refund_cli --platform-order-sn "平台订单号" --details
```

预期符合条件的订单 `not_required=1`，`applied=0`、`unavailable=0`。`--apply` 沿用原权限并可能执行真实 ERP 补单，不能作为“仅更新标签”按钮使用。历史订单先逐笔核验，不批量清除旧错误。

后台入口、环境变量及外部写开关不变。无需数据库迁移和前端构建；安全停后台及守护后更新后端，重启 Web/后台并恢复守护。不要恢复企业微信未核验发送账本或重发历史消息。

专项测试：`tests/test_module3_unimported_refund.py`，覆盖金额/售后号错配、重复/未知/未归档记录、ERP 晚到、已有待处理、空页、分页、超时、幂等、无虚假平账、待办保护与页面显示。真实订单证据仅存 `.runtime/audits/`，不提交 Git。
