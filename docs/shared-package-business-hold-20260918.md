# 同包裹业务暂停与退款失败分开处理

同包裹仍有订单未申请全额仅退款时，系统按业务规则不执行自动退款。这是业务暂停，不能显示成退款失败，也不能再给业务员发布“退款失败或平台状态变化，需人工核验”的重复待办。

## 分类和通知

- `PackageRefundHeld` 在动作执行器中单独处理：核对存在同包裹人工锁、没有资金操作账本或请求开始凭证、平台未退款成功后，将该自动退款任务记为 `CANCELLED`，载荷标记 `execution_outcome=BUSINESS_HOLD`，保留同包裹原因。统计为跳过，不再累计退款失败，不自动重新执行退款。
- 同包裹专用业务员待办继续保留。普通待办查询在数据库 LIMIT 前排除这种无资金请求的重复失败提醒，发布前再次检查，避免已排队的旧提醒漏发出去。
- 有实际资金请求凭证时不按业务暂停隐藏，不覆盖或解除未知资金结果。其他实际退款失败、ERP异常、售后类型变化等保留原处理流程。
- 已分类为业务暂停的任务仍可做原有 30 分钟只读平台回查，平台后来由人工或其他途径退款成功时如实记录，不调用退款接口、不伪造到账时间。
- 历史误报修正须按明确订单范围，备份原任务、订单原因和待办凭证，实时只读核对申请状态、金额及包裹关系后仅修正本地分类；不删除已发送记录、不冒充业务员已完成正确待办、不再次发送通知。

## 验证、部署和备份

沿用正式机现有模块1守护、通知、退款结果回查及待办发布阶段，没有新增定时任务、环境变量、数据库字段或权限开关。基于当前正式发布 `notice-package-worker-20260918` 应用本次差异，保留生产与开发分支之间已有区别，不整目录覆盖。

使用模拟 ERP、平台、数据库测试业务暂停计数、普通待办生成和发送拦截、旧误报重新分类、取消任务继续只读回查，以及请求开始、UNKNOWN、CONFIRMED 资金凭证不能被当作未执行。部署前自然停止后台、使用现有已验证备份脚本备份数据库和运行文件，切换版本后检查正常周期、队列和指定旧任务。

正式机候选相关回归 **173 项通过**，Ruff 通过。扩大回归发现一项旧测试固定要求天猫第6店禁用，与现有正式配置不一致；确认相关配置和店铺源文件与部署前备份逐字节一致后，将该项明确排除，没有借本次修改天猫权限。保留一条既有 Starlette/httpx 弃用警告。真实数据只读预演确认指定两笔没有资金请求、同包裹专用待办已发布，并验证普通待办查询不会选中这两笔。

回退须保留 `BUSINESS_HOLD`、人工锁、资金记录和已发布待办凭证；旧版会再次把新业务暂停写为失败，应先暂停对应自动退款及待办发布，再排查。
