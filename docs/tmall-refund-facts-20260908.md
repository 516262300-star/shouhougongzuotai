# 天猫历史退款事实补查（2026-09-08，第六批）

## 处理范围

本批针对第五批之后仍为退款状态 `UNKNOWN` 的38条历史天猫售后，不是全量重放天猫同步。只读取对应店铺的售后详情和交易详情，不调用平台同意退款、ERP 认领/补单、企微发送或人工待办发布。

新增 `historical_supplement_cli tmall_refund_facts`，与原 `tmall_status` 分开：旧入口限定“本地未发货的历史仅退款”；新入口允许历史退货退款、部分退款，以及发货未知/已发货/已签收的记录。不能为了套用旧入口把发货未知改为未发货。

## 安全条件与写入内容

- 必须点名本地主键 `--record-ids`，并指定 `--max-order-id`，上限严格早于当前 `TMALL_MODULE123_MIN_ORDER_ID`；每批最多500条。新入口不接入常驻后台，不安装定时任务。
- 只选择天猫、财务状态未知、两项平台状态文字均为空、没有发货运单，流程仍为 `PENDING_CHECK` 或 `PARTIAL_REFUND_EXCLUDED` 的旧记录。只接受 `UNKNOWN/IN_TRANSIT/DELIVERED` 发货状态，并排除存在任何动作任务的记录，包括成功任务。
- 客户端明确关闭写权限，单次读请求尝试一次，请求前间隔250毫秒。同一父订单交易详情只在当前有限批次内缓存，缓存键包含店铺；不跨店借用授权或结果。
- 售后 ID、售后所属父订单、交易详情父订单须全部精确一致，退款子订单必须在交易详情中唯一匹配；退款类型须由平台明确布尔值与本地相符。
- 平台必须明确返回 `status=SUCCESS`，交易状态为可识别的关闭/已发货/已完成状态；退款金额必须为合法正数、最多两位小数，且与本地申请金额相同。不将订单关闭或未知售后状态推断为退款成功。
- 只补三项退款/交易状态字段，以及有肯定证据时的 `order_shipping_status`。对应退款子单的状态或有效发货时间才可补发货事实；父单完成、父单发货时间或兄弟子单签收不作为本子单已经发货/签收的证据。无证据不改发货状态，有证据也不使原已签收状态倒退。
- **本入口的子单事实核查，与常规同步用于防止整单取消的父订单级发货保护不同。** 不重放常规映射，不依据父级保护结果回填每个退款子单。父子单混合状态在常规同步中的展示仍需单独核查，不能把本批结果理解为完成了全量映射审计。
- 不更新买家实付、优惠、商家应收、申请或实际退款金额，不用 `modified` 冒充退款完成时间。不改业务更新时间、归属、退货匹配、工作流、自动化水位和同步游标。部分退款仍保留原排除拦截状态。
- **平台退款成功不代表退货已回仓，也不代表 ERP 已认领和平账。** `IN_TRANSIT` 在这次补查中只表示保留/补回已发货事实，不是新查询得到的实时快递轨迹。
