# 异常明细与运行监控分离

## 使用入口

- **异常明细**：独立左侧主导航。按未解决、人工跟进、已恢复、已停止或全部历史查询；
  保留平台、店铺、异常类型与关键词筛选、分页、处理建议、变化记录和精确查看订单。
- **运行监控**：查看运行器、最近完整周期、发送队列、模块开关和阶段执行统计。
  阶段状态为 `failed` 才显示失败原因与“查看失败明细”；点击后进入独立异常页，
  仍按该阶段、周期和可核实来源定位，不把所有历史问题混作本轮失败。
- 在定位页点“查看全部异常”，或重新点击左侧“异常明细”，恢复普通异常查询。

订单异常与模块执行失败分开表达：拼多多同步阶段为 `warning` 或 `acknowledged`，
且明确 `shops_failed=0` 时，表示普通订单同步已完成、个别异常单仍隔离重查；
运行监控按执行完成展示，独立异常页保留订单的真实未解决/人工跟进状态与原始原因。
缺少失败店铺统计、整店失败、未知状态、发送阻断不改写成正常。
普通业务异常数量和人工跟进文案不再嵌入模块行；扫描、新增、已执行等运行统计保留。

## 运行与发布

沿用现有 `/api/v1/monitor/status` 与 `/api/v1/monitor/issues`，15秒刷新频率不变。
运行监控接口只读取运行器、近期周期和必要的发送状态，不初始化异常服务，也不扫描
全部业务异常或写入监控异常台账。人工跟进状态核查只在独立异常页请求时进行，避免
每次进入运行监控或刷新都等待全量扫描及 SQLite 写锁。
不修改 worker、同步隔离、退避重查、退款权限、资金记录或待办发布规则。
人工知悉入口沿用本机同源与版本校验；独立页面不会自动提交处置操作。

本次只更新本机已有 web 发布目录的前端静态产物。发布前将 `index.html` 与
`.runtime/workbench-web-release.json` 备份到 `.runtime/backups/monitor-navigation-<时间>/`，
补齐新资源后替换入口，保留旧资源；更新指针中的前端版本及入口哈希。
无需重启 worker 或 web，刷新浏览器即可加载。回滚时恢复两份备份文件。
既有其他未提交功能不随本次发布。前端的 Sites 兼容包装保留，不发布业务数据到云端。

## 运行监控加载提速

页面拆分后的旧接口仍因同步提醒调用 `list_issues(stage_id=...)`，每次强制采集全部
异常来源并更新异常台账。移除 `/status` 对异常服务的依赖后，保留原运行快照和失败状态，
不使用缓存冒充实时数据。单独异常页的历史采集、人工跟进处置及防重保护保持不变。

提速更新仅发布 web 的 `api/routes/monitor.py`，发布前核对与工作区基线一致，备份
原文件及 web 指针，重启本机 web 加载；worker 无需停止或重新部署。
回滚时恢复备份的路由文件及指针，再重启 web。前端静态产物沿用页面拆分版本。

本机实测 `/api/v1/monitor/status`：修复前3次为2600、2762、5208毫秒，
修复后5次为18、11、10、9、11毫秒（仅代表本次本机接口采样，不含浏览器渲染）。
监控后端33项回归及相关文件 Ruff 检查通过；新增接口依赖隔离测试，确保异常服务
不可用也不影响运行监控，并确认原始同步提醒与整店失败快照不被改写。
计时证据保存在 Git 忽略的 `.runtime/audits/monitor-status-performance-20260912.json`。

## 退款失败明细定位修复（2026-09-12）

旧定位按任务更新时间推测本轮失败来源。退款前只读回查旧失败任务也会更新该时间，
可能出现“本轮失败1笔、候选却超过1笔”，为避免误列历史订单而清空明细。

外部动作执行器现在将实际失败的任务ID写入本轮 `failed_task_ids`，周期摘要保留该字段。
异常定位优先按这份名单和真实动作类型查找，不再把旧失败回查当成本轮退款失败。
平台退款执行阶段包含模块1和模块3的 `PDD_AGREE_REFUND`；模块2退货退款仍单独定位。

点击时携带的周期在现存 worker 日志末尾2MB中准确读取，避免下一轮完成后覆盖所选失败。
已回查成功或停止的任务仍展示最新状态；如果首次打开前已经恢复，也能按精确来源展示。
旧周期没有任务ID时保留严格的旧来源校验，来源不充分不伪造关联、不改写旧运行日志。
任务被删除、动作不符、任务ID格式或数量不一致时仍明确提示来源不足。

该改动只补充运行结果记录与只读显示，不执行退款、补单、消息发送或修改资金结果。
没有新增开关或定时任务。恢复仍按平台回查事实显示，不把“接口结果未知”当成确定未退款。

发布分别更新隔离 worker 的 `actions.py` 和周期摘要中的ID保留逻辑，
以及隔离 web 的 `runtime_issue_focus.py`、`runtime_issues.py`。
先备份指针及文件，暂停守护、等待 worker 完成本轮安全停止，再切换隔离发布并重启。
网页重启只加载后端显示修复，前端产物不变。其他工作区未提交功能不随本次发布。
回滚恢复备份的指针和显示文件并安全重启，保留监控历史、资金账本及运行日志。

验证覆盖旧失败回查干扰、模块3来源、恢复后首次打开、跨周期点击、非法ID/数量、
动作不符和周期摘要保留失败任务ID。说明随 GitHub 保存；个案证据留在 Git 忽略目录。

## 拼多多退款结果待确认显示（2026-09-12）

平台退款请求未收到明确成功响应时，执行器保留原失败记录和资金防重记录，
不能据此断言平台退款失败。运行监控现在在每次读取时，以本地资金账本和原任务
的严格关联区分“当前失败”“退款结果待确认”和“回查确认成功”：

- 同一任务、售后、店铺、平台订单和平台退款资金记录匹配，资金状态为
  `UNKNOWN` / `REQUEST_STARTED` 时，单独显示待确认统计及蓝色“待确认”状态，
  不将这些任务计入当前失败数，也不提供失败入口。
- 任务与原资金记录都已确认成功时，立即从当前失败数移除，无需等下一完整周期。
- 待确认与真实失败并存时分别计数，保留真实失败提示和入口；来源不完整、
  数量不一致或身份不符的失败记录不自动清除。模块2与模块1/3的来源分开统计。
- 待确认在后续没有新退款的周期中仍保持可见。异常明细保留在未解决筛选中，
  状态标签显示“退款结果待确认”，并展示已有的只读回查计划时间。
- 历史周期和原始失败原因保留；监控返回的 `execution_failed`、
  `execution_failed_task_ids`、`execution_error` 和 `last_cycle_execution_ok`
  可追溯原执行结果，当前状态不冒充原周期日志被改写。

本次仅修改 web 的只读状态投影和前端显示，不修改资金执行器、worker、回查频率、
权限或任务状态，不新增退款、补单、消息、定时任务或开关。查询仅覆盖未确认资金
和最近周期明确列出的退款任务，不调用平台接口、不全量采集异常台账。
现有后台按周期只读回查；等待时间取决于周期时长，页面15秒刷新不等于每15秒回查平台。

发布到办公室正式 web 的独立目录：从当前正式版本复制，核对基线哈希后加入
`refund_confirmation_view.py`、三份监控服务文件和前端产物，备份原 web 指针，
切换后只重启 web。保留旧静态资源以支持已打开页面；不改 worker 指针或其启停状态，
开发机不启动生产自动化。回滚恢复原 web 指针并重启 web。

回归覆盖未知响应、确认成功后及时恢复、真实失败混合、跨周期待确认、身份错配、
缺失来源、模块归属、异常标签/计划复查和业务库只读约束；正式发布再验证接口和页面。
