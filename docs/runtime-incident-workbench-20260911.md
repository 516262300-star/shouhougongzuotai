## 使用方式

在「运行监控」查看「异常明细」。默认显示所有尚未解决的异常项，不按售后申请日期截断；与下方「最近一轮运行结果」分开。每 15 秒刷新展示，也可以点击「刷新明细」。最近一轮正常不等于未解决异常清零。

支持按异常类型、平台、店铺筛选，搜索平台订单号、售后号、运单、业务员、任务号和原因，分页查看。数量按异常项计算，不是订单数；同一订单的物流和退款故障可能分别列出。

点击「查看订单」会打开准确售后详情，同时把订单列表设为「全部售后」、清除日期和状态等旧筛选，并保留该平台和店铺，避免被历史筛选挡住。点击「如何处理」可查看处理建议、运单、目标群（有凭证时）、任务号、首次发现、计划复查时间和变化记录。

尚未同步的售后、店铺级和阶段级故障可能没有可打开的订单，页面明确说明，不能猜测关联订单。阶段错误旁的「查看本项异常及处理建议」会进入该阶段的**当前告警定位**，不再只滚动到所有历史异常。定位后显示具体平台订单、店铺、原因和复查计划，只有一项时自动展开处理建议；通过「查看全部异常」返回完整历史。

定位入口重置旧搜索、平台、店铺及分页，不混用之前的总表结果。请求失败、旧接口不支持定位或来源不足时明确提示，不退回展示全量异常。每 15 秒只读刷新当前阶段；点击后若运行周期已变化，会提示正在展示最新核验结果。

拼多多同步定位核对当前启用店铺、隔离记录、失败游标和告警店铺数量；等待重查的有效隔离单仍属于当前告警。ERP/物流/平台退款等订单级失败须有对应动作/来源与本轮核验时间，不能仅按“ERP”大类捞取全部旧订单。生成阶段缺少具体单号、来源与汇总不一致或同周期多次物流查询无法区分时，不猜测订单，提示维护人员按原告警核对日志。店铺鉴权失败等没有唯一订单的情况仍以店铺级异常展示。

定位结果仅是原始异常账本的只读子集，不解除、删除或停止其余异常；阶段恢复不等于所有历史异常恢复。新参数为 `GET /api/v1/monitor/issues?stage_id=sync&cycle_finished_at=...`（周期时间可选），返回 `focus` 范围说明与精确异常键；全量查询接口及原筛选保持兼容。本次不改 worker、调度频率或退款/发送/补单规则。

## 处理和恢复规则

| 类型 | 处理方法 |
| --- | --- |
| ERP 查询失败 | 维护人员修复授权、网络、解析或缺失数据，后台重新查询通过后更新；不要为了去掉红字补单 |
| ERP 缺单或金额/商品不符 | 核对原销售、申请和已有单据，按现有业务授权处理，再复核；平台退款不等于 ERP 平账 |
| 快速退款未入 ERP | 后台确证无原订单、无待处理动作后显示无需补单；不能只凭页面标签强行完成 |
| 企微发送结果不明 | 核对原目标群完整运单和消息，提供证据后经既有维护入口确认；不直接重发 |
| 明确发送前失败 | 仍使用原运行监控的安全重试入口；它不适用于 PasteStarted/SendPressed |
| 平台退款失败/结果不明 | 回查平台最新结果与金额，必要时业务员核验；资金请求不盲目重试 |
| 物流查询失败 | 核对快递和运单、查询能力，等待有效轨迹或既有规则重新核验；查询失败不放行退款 |
| 店铺同步失败 | 修复对应授权或接口，等待该店铺/异常单复查；不影响正常店铺的历史记录查找 |

没有新增退款、补单、认领、清除错误、强制成功或发送确认按钮；本次新增接口只有 GET。刷新也不催跑外部任务、不改已有任务状态/重试次数、不改平台或 ERP 数据。人工待办已发布不等于业务问题已处理。

「已恢复」表示这项执行/查询异常有明确恢复结果，并非整笔售后完成闭环；「已停止（非成功）」表示原任务取消/异常按原流程移除，不冒充成功。缺少来源、未到复查时间或重试中的任务，不因本轮没有错误而自动清除。再次出现会重新进入未解决，并保留原观察历史。

## 数据来源与边界

- 只读已有 MySQL：动作任务及错误、ERP 核验结果、独立轮询记录、物流查询状态、同步异常和店铺游标，以及永久资金/包裹防重凭证；读取本机企微账本和最新运行周期日志。不调用平台、ERP 或桌面发送接口。
- 同一模块 3 查询和失败退款回查优先采用动作任务，避免与对应轮询进度重复展示；不同业务阶段仍可各有一项异常。
- 正常待仓库收货/待买家退货单号，满足明确等待条件时不当作新执行失败；物流已退回仍未提供所需信息等情况继续显示。明确双接口无轨迹的风险放行说明不是接口读取失败；这仅影响监控解释，不改变退款规则。
- 安全迁移批量建立、且原样未发生真实请求的历史资金保护占位，不当作一次新的执行失败。对应动作任务的错误仍显示，永久防重记录不改动。真正 REQUEST_STARTED/UNKNOWN 的请求、原任务已删除但包裹仍结果不明的记录继续保留。
- 只有汇总日志而无订单级来源的错误标为阶段问题，不用某一笔订单冒充整个阶段原因。

本机 `.runtime/monitor-incidents.sqlite3` 保存观察投影和状态变化，与金融账本分离；它不参与退款、补单、群发送决策，不是新的业务事实来源。无需修改 MySQL 表结构或切换后台执行版本。页面 GET 为构建监控投影会更新这一独立本地文件，但业务库只读；15 秒内复用完整快照，同一文件事务串行写入。任一来源读取失败返回 503，不用不完整数据覆盖历史，前端保留上一次结果并明确标注过期。

历史从此功能首次观察开始，无法补造此前未保存的每次错误；打开监控时每 15 秒观察，未打开时不新增独立定时任务。未解决状态本身来自既有持久化业务记录，下次打开仍可检出；尚未观察就发生并恢复的瞬时异常不保证有历史。历史文件迁移电脑时应一并备份，停写后复制，不能把删除这个文件当作解决业务问题。

错误文本仅输出必要字段，接口地址和常见凭据字段做隐藏，不回传原始响应、完整任务 payload 或店铺密钥。真实订单与截图证据只在 Git 忽略的 `.runtime/audits/` 保存。
