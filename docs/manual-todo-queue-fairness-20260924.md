# 人工待办等待任务让位（2026-09-24）

原发送器先按任务 ID 取前 N 条待发记录，再检查归属重试时间。前 N 条都在等待时，后面的正常待办无法进入这一轮；待办生成器刷新正文还可能清掉等待时间，使同一批旧任务反复占位。

## 当前行为

- 保留按任务 ID 的顺序，按 ID 继续分页读取。仍在 `owner_routing_retry_after` 等待期的人工待办不计入本轮处理上限，后面的到期待办可以继续进入批次。没有改成一次性发出全部积压，也不增加配置的每批处理上限。
- 到期记录仍须重新查询原销售业务员、核对发布开关及业务条件，领取原任务后再查重、发送和核实凭证。首次查询失败仍等待5分钟；如果本轮所有选中任务都刚刚查询失败，后续任务可在下一轮进入，不会因为重复选中冷却任务而持续饥饿。
- 刷新模块1、模块3普通待办和同包裹分派任务的业务内容时，保留尚未到期的归属重查时间；不会复用旧收件人或发送授权。模块2已有待办不会被生成器重写，统一由发送器处理等待时间。
- 时区偏移按实际时刻比较；旧的无时区重试时间按 UTC 解释。缺失或格式异常时重新核验归属，不据此直接发送。
- 等待中不领取任务、不消耗发送次数。已经成功、取消、运行中或失败的记录不因这次修复重新发送；平台退款、快递通知及资金防重规则保留原条件。

## 运行、检查与回退

沿用后台 `Leedis Aftersales Module1 Watchdog` 和既有后台循环，当前每批上限20条、完整周期结束后等待60秒；归属失败重查间隔5分钟。无新增配置、定时任务、数据库字段或迁移。ERP接口及发布权限不变。

`scanned` 表示本轮实际选中的任务数，不包括被让过的冷却记录；后台待发总数仍保留等待记录。因此 `scanned=0` 不单独代表待发队列为空。核对任务的状态、重试时间和最后原因，不能清空时间或删除记录来强行发送。

回归覆盖前40条等待而后3条正常时仍发送后3条、首次归属失败后的下轮推进、到期仍需复核、有效任务批量上限和顺序、其他动作不受归属等待字段影响、时间格式以及刷新文案保留等待期。全部使用隔离数据库和模拟接口，不发送真实测试待办。

基于新挂机电脑当前后台复制独立候选，只叠加本次取任务、重试时间与生成器保留字段的改动，先验证候选哈希和相关回归。通过现有停止标志等待完整后台周期自然结束，再原子切换发布指针并恢复守护，不强杀请求。Web、独立揽收提醒和运行配置不变。部署证据与原指针保存在 Git 忽略的 `.runtime/audits/manual-todo-queue-fix-20260924/`；回退同样等待周期结束，恢复原源码指针，不回滚数据、资金或消息账本。
