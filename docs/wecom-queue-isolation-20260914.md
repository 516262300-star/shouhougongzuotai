# 企微快递别名与待发队列隔离

## 原因

顺丰群白名单使用拼多多编号 `44`，天猫订单使用 `顺丰速运`。物流公司代码表缺少44到shunfeng的对应关系，群规划器因此不能复用既有顺丰群。任务实际尚未输入企微，旧日志却把“缺群对应关系”和“物流未预检”混为一条失败提示。

旧发送阶段还会因当前批次存在任一未就绪任务而整批退出；预览先截取固定数量，队首异常积压后，后面的正常任务也可能一直取不到。

## 修复行为

- 统一已知顺丰标识44、顺丰速运、顺丰快递、顺丰、shunfeng，复用用户原已配置的精确白名单群；不按群名字面猜测，也不新建群。显式物流映射优先；同一公司映射到两个不同群仍报错并关闭发送。
- 预览以任务ID每页100条向后查找，直到凑足本轮发送上限或队列结束；未通过预检和缺群的任务保留PENDING，详细原因分别计数，日志最多保存50条任务诊断，数量计数不截断。正常任务照常进入发送器。
- 剩余未就绪任务报告warning，显示预检等待数与缺群数；日志保留任务ID、公司原始标识及原因，不笼统报“企微发送失败”。日志摘要同时保存实际sent/reconciled数。
- 只隔离尚未输入的配置/预检问题。PasteStarted、SendPressed、安全验证及持久化包裹凭证仍按既有防重规则阻断桌面发送；发送前再次检查订单/同包裹任务，成功须连续群消息回执验证。
- 同一包裹多个售后继续使用发送凭证合并，不因为此次修复重发已成功的消息。物流无轨迹的通知仍按既有HOLD规则处理，不因此自动放行退款。

无需改数据库结构、资金开关或任务计划。以正式发布源码为基础替换物流别名、桌面预览、Worker三份文件；开发机未完成的快速轮询改动不混入正式版本。切换前按原守护锁与自然停机流程完成一致性备份，切换后核对群消息凭证和任务状态。
