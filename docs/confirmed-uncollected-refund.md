# 模块1：人工确认刚发货未揽收

2026-09-09更新：常规处理已增加[接口明确待揽收的自动判断](automatic-uncollected-refund.md)，无需逐单人工确认。本文保留的是无明确接口依据时、另行取得真实人工确认与资金授权的应急工具，不是自动流程前置，也不允许自动伪造人工确认。

## 边界

无轨迹不等于未揽收。仅在用户/操作负责人明确确认某一订单尚未揽收，并授权退款后，才登记单笔确认；默认不会根据快递100空结果自行推断、不会放开所有无轨迹订单。当前仅支持拼多多已发货全额仅退款，不扩大天猫等平台权限，不新增仓库界面。

确认与原有 `PDD_AGREE_REFUND` 任务、售后级幂等键共用，不新增第二个资金动作。记录放在任务 JSON 的 `uncollected_confirmation`，包含确认人、实际确认时间、证据引用、成功发送任务ID、店铺/平台订单/售后/运单/快递公司/金额/型号数量快照和平台发货时间。确认有效期固定30分钟；平台发货时间必须在24小时内、不能晚于确认时间。无法取得发货时间时不能使用此分支。

## 操作

先取得真实、明确的人工确认和退款授权；保存个案证据到 Git 忽略的 `.runtime/audits/`。不要把订单号、客户资料或证据内容提交 GitHub/Notion。

使用本机管理命令进行只读预演（以下是占位参数，不可原样执行）：

```powershell
.\.venv\Scripts\python.exe -m aftersales_workbench.workflows.uncollected_refund_cli `
  --order-sn '<平台订单号>' --notice-task-id <已成功的拦截任务ID> `
  --confirmed-at '<实际确认时间，ISO格式含+08:00时区>' `
  --confirmed-by '<确认人>' --evidence-ref '<本机授权审计文件路径>'
```

核对预演结果后，在同一命令末尾增加 `--apply` 登记一笔待执行退款任务。**这会使已启用的后台有资格真实退款，不是普通备注保存。** 此命令自身只读平台，不发群、不调用退款API；不覆盖既有退款任务，不因重新执行命令延长原确认有效期，不重新发送已成功的拦截消息。仅持有授权的本机操作者使用，不提供无鉴权HTTP入口。

后台每轮仍按原周期处理。退款前强制重新查询快递100：只有明确 `Kuaidi100NoTraceError`（正常无轨迹响应）且人工确认有效、发送记录匹配、客服工作时间满足时，才放行本次任务。网络超时、鉴权失败、数据解析错误不能用人工确认兜底。原始 `UNKNOWN`、无轨迹错误与重查时间保留；不伪造物流、拦截成功或仓库退货。

真正调用拼多多资金接口前，要求90秒内的本次无轨迹复核记录，并再查平台最新售后状态、类型、全额金额、型号数量、运单、快递公司及发货时间；请求前再次检查确认有效期、工作时间、同步异常及任务执行权。正常资金开关和店铺同步隔离继续生效。若出现有效在途/退回物流，转回原有常规闸门并保留人工确认审计；派件、签收按既有规则冻结。

## 失败、恢复与回退

- 未明确确认、确认超期、相关字段变化、发送未成功或该订单处于同步隔离：不放行。
- 超期/夜间/查询故障可取消尚未执行的任务；不能靠重新运行确认命令恢复或扩大授权。先查当前平台、物流和任务，再按真实新情况另行审核。
- 资金请求前持久化 `uncollected_request_started_at`；标记存在时禁止再次发起同一请求。已经进入资金请求的失败/超时/结果未知：任务保留 FAILED，仅只读回查，禁止自动重发资金请求。不要清空任务或重建第二个幂等键。
- 该分支不在ERP里开任何退货单，不代表售后闭环。退款后仍跟踪包裹实际归仓、退货单归属和ERP平账；若包裹实际未出库，需按真实仓储/财务处理结果核对，不能伪造退货事实。
- 无新增数据库迁移或全局开关。部署前暂停守护并让旧后台安全退出，更新代码后恢复原有后台及守护；不强杀进行中的资金任务。回退代码前先暂停并处理该分支待执行任务；不得留下旧版本不认识的放行任务继续执行。

README中的普通无轨迹保护继续适用；此文仅增加带明确人工证据的单笔例外，不替代其他物流规则。
