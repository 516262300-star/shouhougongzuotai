# 在途人工待办文案简化（2026-09-10）

## 对业务员显示什么

普通在途待办采用以下短文案（均为虚拟示例）：

> 【售后工作台 订单:示例订单号】 原因：退款失败或平台状态变化，需人工核验；店铺：示例店铺；发货运单：示例运单号（运输中）。

不再显示 M1、模块1、物流代码，平台订单号只在标题出现一次。退货闭环待办同样移除技术标题和重复订单号，但保留核对原因、金额差异和必要的退货明细。本次不重新判断异常原因，也不修改退款规则。

## 处理范围与防重复

- 新待办在 `Module1ManualTodoCandidate.task_payload` 生成短文案；已排队的旧普通在途待办，在发布请求构建时做同样整理。
- `origin`、`reason_code`、`reason_text`、物流代码、任务身份及本地幂等键不变。
- 新远端标识为 `【售后工作台 订单:平台订单号】`。发布前兼容 `【售后工作台 M1订单:平台订单号】` 和 `【售后工作台 M1:售后单号】` 两代旧标识；任一命中则复用远端ID，不再发布。
- 新提交成功时保存实际发送的短文案；复用旧远端待办不改写原历史内容。已成功任务不批量改写、不重发。
- 同包裹独立跟进待办保持原标识，不与普通在途待办合并；模块2/3模板不在本次调整范围。人工锁、退款、ERP补单、企微消息及待办发布开关不变。

## 运行与验证

仍由现有后台运行器调度，使用原ERP员工凭据、原网页开关与ERP总闸；未新增环境变量、定时任务、刷新间隔或重试动作。程序启动时加载模板；发布版本需按原维护流程安全结束后台当前周期后重启，不能强杀资金请求。若工作区有其他未验收改动，先完成对应发布检查，不把单次文案修改当作整套代码已验收。
