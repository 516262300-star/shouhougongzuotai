# 同步异常转人工与退款后核账修复

## 操作入口

运行监控 → 异常明细 → 单笔同步异常 → **已知悉，转人工跟进**。
填写跟进说明后，该项进入 **人工跟进** 分类，可按订单号检索。
这不是已恢复、退款成功、质检通过或财务闭环；不向 ERP 发布待办。

处置只保存到本机 `.runtime/monitor-incidents.sqlite3`，不会修改同步异常表的
`dismissed_at`、资金账本或退款任务。后台照常隔离、退避重查；同步成功自动进入
“已恢复”，异常原因或身份变化重新进入“未解决”。保留原始异常与处置时间线。
本机同源操作校验和状态版本校验用于防止外部页面或过期页面误处置。
资金结果未知、发送结果未知、整店失败不提供此入口。

仅当当前同步阶段所有已定位告警都转人工且没有未定位项，阶段显示“人工跟进”；
原始周期日志不改写，仍保留隔离事实。不是将后台执行状态伪造为成功。

## 已退款的退货核账

模块2原逻辑会将已经退款的明细匹配订单再次报为“质检后再退款”。
现在先判断平台成功事实：未退款仍保留独立质检闸门；已退款转为只读退货核账。

拼多多独立运单：校验客户名下 TH、完整型号颜色数量、售后身份、商家应收金额、
对应 SK 退款流水、无欠货、客户应收严格为零；核验成功清除本项轮询错误，
订单保持“客户名下已收到”并显示“退款后核账已核实（非质检结论）”。
证据保存在 Git 忽略的 `.runtime/audits/module2-post-refund.sqlite3`。
不创建验货 PASS，不改变平台退款或统一资金账本，不调用 ERP 补单。
每次现有模块2轮询仍重新核验，沿用30分钟轮询，不新增定时任务或开关。
暂存待认领、非零余额、缺失流水、金额或客户不符仍保留待核账提示；
多售后共运单、个案人工锁与实收不符仍保留原保护，天猫不借用拼多多流水接口。

## 验证与部署

相关验证覆盖：人工跟进持久化、重复提交、过期版本、同源限制、原因变化重新告警、
真实同步恢复、未知资金不可隐藏；退款成功后只读核账与未退款质检保护，
缺流水/非零余额/错客户/金额不符/共享运单不得误报核账成功。

沿用本机 worker/web 隔离发布目录：发布前备份两份指针及监控 SQLite，
停止守护、请求 worker 完成本轮后安全停止，再切换发布与重启网页。
不替换数据库、不改 `.env`、不部署既有未完成快慢线程和报表改动。
恢复时切回备份发布指针；保留监控与核账证据，勿清空资金或认领账本。
本次不发布云端；没有已提供的 Notion 页面目标，说明随 GitHub 保存。

已验证：工作区相关65项测试、正式隔离 worker 79项与 web 32项测试通过；
前端响应测试5项、Sites兼容打包测试4项通过。前端沿用 Vite 构建；
Sites 构建包装器在此 Windows 环境查找 npm 路径失败后，直接使用项目已有
Vite 入口及 prepare-sites-build 脚本完成相同产物，不安装或替换依赖。
隔离 worker 同时补入主线已有的 case_safe_order_filter 函数，供模块2候选保护使用；
不改其他阶段任务过滤规则。
