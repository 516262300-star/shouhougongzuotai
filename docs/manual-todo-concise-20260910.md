# 人工待办统一简化（2026-09-10）

## 对业务员显示什么

普通在途待办采用以下短文案（均为虚拟示例）：

> 【售后工作台 订单:示例订单号】 原因：退款失败或平台状态变化，需人工核验；店铺：示例店铺；发货运单：示例运单号（运输中）。

所有现有业务待办模板不再显示 M1/M2/M3、模块1/2/3，主订单号只出现一次。长商品明细、ERP单号、英文异常类型不再堆入事项，完整数据仍保存在本地任务载荷中。短原因保留，超过120字的原因保留完整首句或使用明确的差异类别，不硬截断型号、金额和否定条件。本次只改文案，不重新判断异常、退款资格、认领或补单。

## 各类通知保留哪些信息

- 普通在途：平台订单、店铺、原因、快递单号及中文状态。
- 退货认领/平账：平台订单、店铺、原因、已有应收差额及具体处理要求；不带ERP退货单号、长商品明细或整段内部处理提示。完整退货行和提示保留在任务载荷。
- 同包裹跟进：主订单只在标题出现一次；关联订单按原顺序去重并排除主订单，全部保留，不截断单号、不省略待联系订单；移除每笔订单的商品清单。保留“已暂停自动退款”及联系客户/核对后人工处理的要求。
- 退货验收异常：平台订单、店铺、简短异常原因及核实实物后人工决定退款的要求；原因过长时仍区分少退/未收到、多退/错退。
- 退款后退货异常：使用独立申诉标识，保留“平台已退款、立即申诉”的要求，不能因先前发过普通验收待办而抑制申诉。
- 未发货退款核对：平台订单、店铺、原因、核对商家应收/欠货/退款单的要求；去掉模块编号、重复订单号、英文异常类型及ERP订单号。完整异常类型、原始报错及ERP订单号仍留在载荷。

## 处理范围与防重复

- 各生成器和发送前均调用 `prepare_manual_todo`，使新待办和旧排队待办使用同一短文案规则。格式化不修改输入载荷。
- `origin`、`reason_code`、`reason_text`、物流代码、任务身份及本地幂等键不变。
- 新远端标识为 `【售后工作台 订单:平台订单号】`。发布前兼容 `【售后工作台 M1订单:平台订单号】` 和 `【售后工作台 M1:售后单号】` 两代旧标识；任一命中则复用远端ID，不再发布。
- 新提交成功时保存实际发送的短文案；复用旧远端待办不改写原历史内容。已成功任务不批量改写、不重发。
- 同包裹独立跟进待办保持原标识，不与普通在途待办合并。
- 未发货待办改为 `【未发货退款核对：平台订单号】`，兼容旧 M3 订单标识和售后标识。退货验收兼容旧 M2 售后标识；退款后申诉只查带申诉身份的标识，不使用普通验收标识。
- 人工锁、触发条件、退款、ERP补单、企微消息及待办发布开关不变；ERP技术故障是否触发待办的策略不在本次调整范围。

## 运行与验证

仍由现有后台运行器调度，使用原ERP员工凭据、原网页开关与ERP总闸；未新增环境变量、定时任务、刷新间隔或重试动作。程序启动时加载模板；发布版本需按原维护流程安全结束后台当前周期后重启，不能强杀资金请求。若工作区有其他未验收改动，先完成对应发布检查，不把单次文案修改当作整套代码已验收。

