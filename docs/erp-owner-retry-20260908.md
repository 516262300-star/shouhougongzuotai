# ERP 客户归属：到期失败单优先重查

## 问题与范围

原逻辑虽为失败记录设置 5 分钟后可重试，但只按缓存时间排序，大量从未查询或更早过期的历史单可能挤占全部 20 个名额。页面仅使用缓存，旧“查询失败”不能代表当前 ERP 仍故障。

本次只调整 ERP 客户归属查询的调度、结果分类及本地缓存刷新。不执行企业微信发送、平台退款、ERP 退款补单、暂存认领或闭环判定；不修改 ERP 源码。人工待办发送开关及其他自动化开关不变。

## 调度与权限

- 沿用 `ERP_SALES_OWNER_SYNC_ENABLED`、`ERP_SALES_OWNER_SYNC_BATCH_SIZE`（默认 20）、`ERP_SALES_OWNER_REFRESH_SECONDS`（默认 86400 秒）。无新变量、表或迁移。
- 已到期的 `unavailable` / `not_configured` 优先占半批，默认最多优先 10 笔；剩余名额给新单和普通过期单。任一类别不足时空位互补；批量 1 时优先到期失败单。
- 失败后最短 300 秒再次具备资格，普通结果默认每日具备资格；这是入队资格，不承诺第 5 分钟一定完成。实际时间还受当前周期耗时和积压影响。
- 失败缓存时间沿用旧版回拨用于调度的约定，并非真实查询时间。未批量改写历史时间字段。正常结果保存本次处理时间。
- 后续[跨平台更新](fast-refund-all-platforms-20260908.md)将后台归属只读同步扩展到全部启用店铺；资金动作的试运行范围不变。CLI 不加 `--all-platforms` 时仍保留原拼多多/天猫范围语义。
- 新代码使用 MySQL 8 的窗口排序分配名额，项目当前 MySQL 8.4 支持；不存在额外数据库写权限需求。

## 结果区分

| 页面提示 | 判断依据 |
| --- | --- |
| ERP 查询失败·待重试 | 超时、网络或 HTTP 异常、登录失败、空白或无法识别的响应；不能据此认定客户不存在 |
| ERP 未查到客户 | 查询返回合法空列表，当前未匹配到客户；可能未导入，不代表未发货或已平账 |
| ERP 客户未设置业务员 | 查询到了客户，但没有归属业务员 |
| 快速退款未入 ERP | 所有已接入平台共用：明确未发货 + 仅退款 + 平台退款成功 + 本次无客户结果，且本地没有已知客户；仅业务规则分类，仍定期复查 |

天猫等平台交易关闭、退款成功但发货未知时仍需补齐事实，不能仅凭关闭套用快速退款；这属于等待核验，不是第三种最终业务分类。客户存在但缺业务员、已知退款失败与旧成功整数矛盾、错误响应内容，都不转换为快速退款。保留全部售后记录，不把未入 ERP 作为忽略记录的理由。

网页登录查询失败写入本地后台日志 `ERP_OWNER_LOOKUP_FAILED`，只含平台订单号、原因类别及可选 HTTP 状态码，不打印凭据、Cookie、URL 参数、原始响应或原始异常。旧故障未保存这些信息，不能补猜当时原因。

## 指定订单刷新

只读预演，不写本地缓存：

```powershell
.\.venv\Scripts\python.exe -m aftersales_workbench.integrations.erp.sales_owner_cli --platform-order-sn <订单号> --dry-run
```

可重复 `--platform-order-sn` 指定多笔，数量不得超过 `--limit`（默认读取批量配置）。指定订单跳过本地缓存时间限制，但不绕过平台与天猫起始 ID 范围。`--include-tmall` 仅在天猫试运行配置已开启时有效。

新参数 `--all-platforms` 只查询所有启用店铺的归属，此模式与资金动作的天猫试运行开关/起始 ID 无关；仍受实际 ERP 适配器所支持的平台限制。可与指定订单及 `--dry-run` 组合。

确认后去掉 `--dry-run`，只更新指定售后订单的客户名、业务员、归属状态和缓存时间。**此 CLI 默认会更新本地缓存**，但所有 ERP 查询均只读，不会退款或补单。命令启动新进程使用新查询会话；页面刷新本身不调用 ERP。未查到订单或不在许可范围时 `scanned=0`，不代表查询成功匹配。
