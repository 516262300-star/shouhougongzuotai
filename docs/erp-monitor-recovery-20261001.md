# ERP 授权恢复及已退款待办复核

## 客户端资源常驻

ERP 桌面客户端的旧单文件包会把 Python、TLS 证书和界面资源解压到 Windows 临时目录。2026-10-01 排查确认，运行中的解压目录缺少证书及其他资源，导致客户端仍显示登录，但工作台申请临时授权时报网络错误。清理来源尚未确定。

临时恢复只能使用与正在运行的客户端 SHA256 完全一致的原安装包，核验每个资源哈希，仅补缺失文件；不能下载不明证书、关闭 TLS 验证或复制账号令牌。

长期安装改用 PyInstaller `--onedir`，将可执行文件与 `_internal` 目录一起部署在固定安装目录。保留原可执行文件完整路径、登录账号、凭据存储和任务参数，避免变更工作台桥接身份。

构建脚本为 `scripts/build-erp-client.ps1`。`SourceRoot` 必须包含已审核的 `tools/leedis_desktop` 源码；本次源码基线为 Git 提交 `3f1b283`。构建环境需已安装 PyInstaller、certifi 和 Windows keyring 后端，不由脚本自动联网安装。

```powershell
./scripts/build-erp-client.ps1 -SourceRoot '<客户端源码目录>' -Python '<构建虚拟环境>/Scripts/python.exe' -OutputDirectory '.runtime/erp-client-build'
```

输出包括 `dist/LeedisClient-Workbench/`、离线自检报告、逐文件 SHA256。自检使用模拟登录，不连接 ERP。部署前备份原程序；正常关闭客户端，等待退出，不能强杀正在处理资金动作的工作进程。完整替换程序和 `_internal` 后启动原登录任务，确认登录账号、临时授权及新一轮监控。回退使用备份程序，不能修改资金幂等记录。

## 旧人工待办的只读复核

2026-10-08新增已有待办的独立复核：拼多多未发货、仅退款、平台已退款且已有未尝试发送的模块3待办，每轮额外最多10笔只读查询，不再全部等待每轮一笔的资金执行队列。以独立 `module3_todo_recheck` 轮询状态按最久未查顺序处理，单笔间隔30分钟；登录或网络失败停止本轮额外查询并保留异常，下一周期继续。无需新环境变量，沿用模块3和ERP既有开启条件，不调整资金批量。

只读复核通过 `Module3ErpRefundService.run(reconcile_only=True)` 执行：READY仅保存当前核验状态，绝不调用ERP补单；COMPLETED须由适配器核实本单退款凭证、金额、欠货及应收，才能记录本地完成事实并取消从未发送的旧待办。证据不足保留核验；dry-run不启动额外复核；已发送、已尝试发送及其他模块待办不进入此批次。

“平台商家应收已核实补齐，等待重新核对 ERP 订单欠货和退款单状态”表示金额证据已补齐、旧核验尚待更新，并不表示平台退款失败。后台的模块3执行批量很小，大批金额修复后可能出现复核积压。

待处理列表未找到目标订单时，应继续查询 ERP **所有退货退款**，精确核对平台订单、售后单号及商家应收，然后区分：

- 快速退款未入 ERP：退款事实唯一且已归档，无原 ERP 订单和客户关联、无待处理动作。保存“无需 ERP 补单”证据及每日复查计划，不伪造取消欠货或退款平账记录。
- 原 ERP 退款已完成：原系统订单、对应售后和金额的退款收款单存在，欠货清零、客户累计应收在容差内归零。保存已有单据的只读确认，不再次退款或补开。
- 仍有核账差异：具体展示欠货、未归零的应收、缺失退款收款单等原因。客户归属不唯一或与退款记录不符属于业务待核验，继续阻止资金动作，不计作网络查询失败。网络错误、响应结构错误仍保留技术失败。

仅撤销已核实解除、尚未发送的本地模块3待办；已发送待办和其他模块的任务保留历史。未解决项更新为真实核验原因。批量核验不能调用补单执行入口，也不能提高资金执行批量来清积压。

个案订单、客户、查询证据、修改前后快照放在 Git 忽略的 `.runtime/audits/monitor-repair-20261001/`。本次不更改平台退款开关，不发送 ERP 待办或企业微信消息。

## 人工待办隐藏金额补齐后的旧提示

人工待办不再展示“平台商家应收已核实补齐，等待重新核对 ERP 订单欠货和退款单状态”这类等待后台复核的提示，包括已取消或已发送的历史任务。列表、搜索、分页、统计和业务员筛选使用同一过滤规则；后台任务、发送回执和原核验记录完整保留，不删除 ERP 已发送记录，也不修改订单状态。

识别时忽略空白，并依次采用 `reason_text`、`exception_message`、`content` 中首个非空当前原因。后来更新为实际欠货或退款收款单差异的待办继续显示；仅累计应收差异按下述 ERP 原有通知分工处理。该金额补齐提示过滤仅调整 Web 查询展示，不触发资金操作或任务重发。

## 快速退款查询旧错误不再生成新待办

未发货、仅退款、平台已退款，且无 ERP 客户、销售业务员和物流关联的“未入 ERP”候选，不再仅凭 `unavailable` 查询错误（包括历史缓存）生成或重新入队模块3人工待办。查询错误仍保留在后台核验和异常明细中，不能据此直接判定无需补单。查证后的具体欠货、缺单或退款金额差异才进入人工核对，不仅凭 `blocked`、`not_found` 状态生成提醒；下述三类待核验提示只放异常明细。

只读回查确认 ERP 唯一退款已归档、金额和售后号一致、无原订单及待处理动作后，沿用 `record_not_required` 保存证据并安排每日复查，撤销本单从未发送的模块3误报。人工待办统一隐藏这种带有明确核验撤销原因的记录，后台审计不删；曾尝试发送、已有外部回执或其他已取消任务继续保留。部署分别更新后台待办生成规则和 Web 展示规则，等待当前后台周期结束后切换版本，不调用退款、补单或第三方消息接口。

## 未发货已退款核账的小额尾差

用户于 2026-10-01 选择累计应收**绝对值小于 1 元**作为这类核账的允许尾差：正负余额均适用，正负 1 元及以上不通过。只在拼多多未发货退款已成功、退款记录唯一、售后号及商家应收金额一致、客户关联唯一、本单无欠货且已匹配对应退款收款单时适用；不是仅凭余额小就结案。

该规则独立于原来的 `0.01` 元金额核对：退款申请/退款收款单金额、补单前负应收、已发货退回及其他流程的校验不放宽。实现常量为 `UNSHIPPED_SETTLED_BALANCE_LIMIT`，不调整共享的 `ERP_RETURN_MATCH_RECEIVABLE_TOLERANCE` 环境配置。

核验通过保存 `erp_receivable_tail_accepted`、真实 `erp_receivable_amount`、上限和既有收款单号，页面显示“核账通过（小额尾差）”。不能写成 ERP 真实余额已归零，也不创建抹零或调账单。撤销并隐藏本单从未发送的模块3待办，保留原审计及已发送记录；缺单、欠货、退款金额不符继续人工核对。余额超出尾差范围不自动判定核账通过，通知分工按下节执行。历史核账状态必须逐笔只读重查后才更新，不能根据旧提示删除或放宽资金动作。

历史待办也可能仍保存“ERP 已同步退款事实，但待处理页暂无可执行的补开退款单动作”，不能仅按“累计应收”或新文案筛选回查范围。这句旧版本提示不再生成或重新入队人工待办，原 ERP 核验任务继续等待新版只读回查；已有待办仍须逐单核实退款单、金额、欠货与实际余额后才按核验结果处理。新版查出的缺单等退款问题正常进入人工待办。

## 累计应收差异由 ERP 原有通知负责

用户进一步明确：客户累计应收账不对已有 ERP 原系统通知业务员，售后工作台不重复提醒。模块3仅有“所有退货退款已找到、本单无待处理，仅客户累计应收尚未归零”或“累计应收不等于负的商家应收”的原因，不再生成、重新入队或发布人工待办；金额大小不影响这个通知规则。源核账状态、真实余额、补单前金额保护与小额尾差判定保持原样，不标记平账、不调账、不自动补单。

`services/module3_todo_policy.py` 对余额提醒严格匹配完整原因，生成、发送和 Web 查询共用规则；多项差异中包含欠货、缺退款收款单、退款金额不符的仍保留。当前原因优先于旧 content，避免把后来发现的退款问题一并隐藏。列表、搜索、分页和统计统一过滤余额提醒，包括历史项；审计及原 ERP 通知不删除。正常后台周期撤销仅因余额问题且从未发送的本地模块3待办，记录 `ERP_ACCOUNT_BALANCE_NOTICE_DELEGATED`，不把核账任务改为成功。已有发送尝试或外部回执不修改，仅阻止重复发布。

部署增量更新 worker 与 Web，保留正式环境其他补丁、配置、ERP 原有通知和计划任务；等待当前周期退出后切换并正常重启。核验目标订单待办不再展示，真实余额及源核账状态保持不变，并验证混合退款问题仍可入队。回退代码用原版本指针，本地撤销记录留审计，后续真实退款异常允许重新生成待办。

## 已平账退款单的 X 后缀编号

ERP 退款记录的系统订单号可能为 `DD-<数字>X`，但对应退款收款单的“订单编号”字段仍为内部数字 ID。过去逐字比较去掉 `DD-` 的编号会漏掉这类已存在的收款单，错误产生“未匹配到退款收款单”待办。

识别仅兼容已观察到的单个大写 `X` 格式，不任意删除其他后缀；仍必须同时满足唯一客户关联、平台订单及售后号一致、退款金额精确匹配、收款单备注明确包含完整 `DD-<数字>X` 单号且不误匹配更长单号，以及退款收款单唯一。本单欠货、真实余额和退款成功状态仍按原规则核验；余额为零本身不作为退款单存在的依据。

明确核验完成后，模块3保存真实退款收款单证据，撤销本单尚未发送的旧待办；零余额完成使用 `ERP_REFUND_VERIFIED_COMPLETE`，小额尾差沿用原标记，两者均不再进入人工待办列表。已有发送回执保留，不补开、不重退、不改 ERP 单据。worker 与 Web 增量部署后，用新的只读查询结果核验并回写本地状态，个案证据保存在 Git 忽略的 `.runtime/audits/`。

## ERP 待核验提示归入异常明细

以下三类模块3提示由后台继续只读核验，仅在“异常明细 → ERP 查询与补单”展示，不生成、重新入队或发布人工待办：

- ERP退款记录已有客户关联，不能确认无需补单。
- ERP 待处理和已处理退款列表均未找到该订单。
- ERP 订单查询已完成，但平台订单与退款记录中的客户关联不唯一或不一致，须核实归属。

上述待核验信息按下节的人工待办准入规则处理；附带已查实的欠货、退款金额不符等具体业务原因、且查询状态允许的待办继续保留。当前原因优先于旧 content，后来发现具体人工问题可重新生成待办。生成、发送前检查及 Web 列表、搜索、分页、统计共用同一分类规则。

后台仅撤销从未尝试发送、没有外部回执的本地待办，记录 `ERP_REVIEW_IN_EXCEPTION_DETAILS`，含义是“转异常明细继续核验”，不表示异常解除。已尝试或已发送的记录及回执完整保留，阻止再次发布，并从人工待办视图中移除。原 ERP 核验任务、异常原因、订单状态、资金状态、真实余额与复查计划保持原样，因此异常明细仍显示未解决；不以分类变更推断已平账，也不执行退款或补单。

增量部署 worker 和 Web，等待当前运行周期结束后切换，保留现有配置及其他补丁。应用前备份候选待办和源任务；应用后核验人工待办不再显示、异常明细仍能按订单找到原问题。个案审计仅保存在 Git 忽略的 `.runtime/audits/`。回退代码使用旧版本指针，撤销审计保留，真实新问题按正常规则重新入队。

## DNS 解析失败不生成业务人工待办

`ERP 未发货退款查询失败：[Errno 11001] getaddrinfo failed`（含同码 `WinError` 写法）是 DNS 解析故障，按上述“异常明细继续核验”规则处理。生成、发布、列表及统计统一排除该完整提示及标准待办包裹文本；尚未发送的本地待办撤销，源查询错误、复查计划和已有发送审计保留。

此变更仅调整提醒归类，不表示 DNS 已修复或 ERP 核验通过。异常明细继续显示实际查询错误，后台按原计划重试只读查询。后续人工待办准入规则进一步排除所有查询失败状态和未发货核验失败提示，技术错误中引用业务字样也不作为人工处理依据。

## 人工待办准入规则（取代逐条错误排除）

模块3不再把 `unavailable`、`blocked`、`not_found` 一概转换为人工待办。生成前、发送前、人工待办列表及统计共用 `module3_todo_policy` 的准入清单，分页前过滤。只有当前查询状态为 `blocked` 或 `not_found`，并且完整句段明确指出下列业务问题，才允许进入人工待办：

- 本单退款单号或退款金额与已查询的记录不一致。
- 已核对的型号、颜色、数量与欠货记录不一致，或本单仍有欠货。
- 已核对所有退货退款，但没有匹配到本售后及金额对应的退款收款单。
- 已发现发货销售单、退货运单或售后类型冲突，需要业务人员确定正确处理流程。

每条待办按实际问题给出对应处理动作，多个明确问题合并列出，不再统一发送“请核对商家应收、订单欠货和退款单状态”的泛化提示。退货认领、实收差异、客户协调等已有模块1/2业务待办沿用原流程。

以下情况留在异常明细，后台按既有计划复查：所有 `unavailable` 查询失败（超时、DNS、连接、授权、页面或响应解析失败等），以“ERP 未发货退款查询失败”或“ERP 未发货核验失败”开头的历史错误，等待同步/金额补齐/客户归属核验，以及没有匹配到上述具体业务原因的未知结果。新错误不必逐条加入排除名单。仅累计应收差异仍由 ERP 原系统通知，不在此重复提醒。异常进入人工待办或退出待办都不等于核账完成。

历史任务依次以 `reason_text`、`exception_message`、`content` 的当前非空原因判定，以 `exception_status`、`erp_refund_status`、`ERP_REFUND_*` 原因码补充状态；状态缺失时仅兼容已有明确业务原因的旧记录。当前业务原因覆盖旧 content；查询失败状态不得被旧业务文案放行。只有从未发送且无外部回执的本地误报会撤销，原核验任务、复查计划、资金记录及已发送审计保留；撤销记录继续使用 `ERP_REVIEW_IN_EXCEPTION_DETAILS`。

部署以正式版本为基线增量更新 worker 和 Web，先预览将移出的记录，待运行周期结束后切换。验证超时类待办从列表和发送候选中移除、原异常继续可查，且具体业务差异仍正常入队。未知错误默认保留在异常明细；新增业务准入原因时应同时补充具体处理动作和回归测试，再发布。

## 异常明细重复与过期结果修复

异常明细统计的是异常项，不是退款失败订单数。抖音模块3、天猫退货核账的同一次查询可能同时写入动作任务和轮询表。仅在店铺、售后号、已知来源对应的动作类型、当前原因完全一致且两项都未解决时，列表、搜索、分页和统计合并展示，保留主任务及关联来源键。原始观察历史不删除；不同原因、不同店铺、无唯一任务的轮询、独立资金账本均不合并。运行监控点击进入的指定周期明细继续按其精确来源定位。

ERP 退货查询过去只在技术失败时填写 `last_error`。后续查到退货单但仍有实收差异、待认领或核账问题时，该字段清空，导致异常页继续保留旧网络错误。现在用有核验时间的最新退货匹配/补单结果更新原因；认领仍阻塞时保留认领原因。没有新核验证据、只有字段清空时，不自动清除历史，更不能把“查询正常”当作退款或核账完成。

模块1退货复查去掉“先按运单截取前100条，再判断到期”的限制，按完整候选队列的核验时间优先处理从未检查和最久未查项，相同时间再优先查询失败。实际 ERP 查询仍受原批量限制，同运单核验沿用完整关联订单校验；模块2和正式环境已有的平台范围限制保留。已检查任务逐笔提交，新一轮会自然轮到其他旧记录，避免前几条长期占据查询名额。

已退款的退货任务可能因早期共享动作类型进入 `RETURN_WAITING_ERP_MATCH`，却同时被模块1类型限制和模块2状态限制排除。模块2现在接收这一状态且平台退款事实为 `SUCCESS` 的退货，保留原平台、店铺、同步隔离、人工争议和批量限制，用退货运单继续核验。历史任务补查发现实收差异时只保留核验问题，不补造仓库质检失败记录。旧共享任务的 `unavailable` 查询错误仅在有更新的模块2核验、且当前错误仍精确对应原查询时被替代；独立执行错误及未知资金结果不覆盖。

旧记录恢复须调用只读查询逐笔取得新证据，再核对本地源记录未被并发更新。已存在且核对完整的退款收款单可按原流程记录本地核账结果，快速退款未入 ERP 的保存无需补单证据及每日复查计划；发现可执行动作只记录待处理，不调用资金执行接口。真实缺单、归属冲突、实收分配不足等保留最新原因。本次多包裹抽查确有实收关联的历史售后未同步完整，不能忽略这些订单或仅凭平台已退款清除整批异常。

增量部署仍以正式 worker/Web 版本为基线，保留配置与独立补丁，正常等待后台周期结束后切换。回退使用部署前版本指针；已记录的只读核验事实和异常历史保留。抽查、批量复核及前后对比证据存放在 Git 忽略的 `.runtime/audits/exception-audit-20261001/`。

## 1688 已关闭售后的零金额快照（2026-10-02）

1688 在售后关闭后可能把申请货款、申请运费、实退货款、实退运费均返回为零。此前适配器仍要求正退款金额，导致已关闭记录被隔离，订单停留在旧状态，监控持续提示店铺存在异常单。
