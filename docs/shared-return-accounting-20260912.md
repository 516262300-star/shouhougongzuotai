# 共享运单继续整批核验（2026-09-12）

## 行为

模块2遇到“同退货运单关联多笔售后”时进入整批只读核验，不再直接返回通用异常。
先读取 ERP 客户销售/退货账页全部分页，再沿“原销售—实际退货包裹—同包裹其他销售”扩展相关范围。
本地关联查询不受当前候选页、店铺筛选或订单编号下限截断；实际状态回写仍限于本轮被选中的订单。

当前 ERP 适配器识别客户账页 RC 销售商品行、TH 退货商品行，税点单独排除。
用退货行客户编号追溯原销售内部ID，再由销售行客户编号定位平台订单；不凭客户昵称或相同 SKU 凑数。
保留稳定退货行ID、实际运单、完整型号、颜色及数量，允许有明确原销售证据的跨包裹匹配。
分页接口页码从0开始，页面显示从1开始；页数不一致、超过50页、重复行、无稳定行ID、数量冲销均保留具体原因。

各笔分别判断：

- 实收可唯一归属且数量一致、本地平台同步结果同时为售后成功10、订单退款4、资金成功，并有逐单 ERP SK 流水对应原销售 DD、商家应收金额、零应收及无欠货，记为“整批退款后核账已核实（非质检结论）”。
- 数量不符、缺少原销售或退款流水，显示具体缺口；独立订单的差异不阻止其他有唯一证据的订单核账。
- 未退款、非拼多多订单只记录核验结果，仍待独立质检或人工核验。自动轮询使用已有平台同步事实，不把本次 ERP 查询当作新的平台退款回查。
- 重复/重开售后、缺失本地售后、客户冲突、同步隔离、人工争议、资金结果未知，以及已有仓库分配/质检记录，保留明确原因等待复核；不会绕过已有占用或争议。

不生成虚构的一单一收货，不创建质检 PASS、退款、ERP 补单或消息任务，不修改客户填写的运单。
这次只扩展核验和已退款核账，不启用无人值守多包裹退款。

## 留档、重查与恢复

成功落账前复查本地整批订单及申请明细是否变化，并以 SQLite 事务建立实收行唯一占用。
审计位于 Git 忽略的 `.runtime/audits/module2-shared-returns.sqlite3`；同一售后重复核验幂等更新，其他售后或变更后的实收行不能覆盖已有占用。
该账本仅供退款后核账审计，不是新退款的授权或资金操作幂等记录。

继续使用模块2现有轮询和部署配置，不新增开关或定时任务；整批结果仅在本轮内复用。
ERP 查询失败后本轮停止继续发起共享运单查询，下一轮重新核验。
核验成功清除本笔 `module2_erp` 轮询错误，异常明细按原采集机制自动显示已恢复，保留历史。
失败仍记录待核原因，后续恢复证据后重新核验，不手工删除异常历史。

`dry_run=True` 只预演源数据核验，不回写订单和审计占用；已有占用冲突及本地状态复查在实际落账时再次强制校验。
个案证据、客户信息及订单号仅留在 `.runtime/audits/`，不能进入 GitHub。
