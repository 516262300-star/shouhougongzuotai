# 模块1：双接口无轨迹风险退款

2026-09-09，用户明确授权采用下列五条规则自动退款。这是一项接受物流回传延迟风险的业务策略，不是证明快递未揽收，不替代退款后的退仓、客户退货单和ERP平账。

## 五个同时满足的条件

1. 拼多多平台最新订单明确已发货，发货时间是**北京时间当天自然日**且不在未来，售后是全额仅退款。按买家实付判断全额，平台补贴不算部分补偿；金额、SKU、数量、售后身份继续按原资金预检核验。
2. 本售后对应运单及快递公司的企微拦截通知任务唯一且成功。不把待发送、SendPressed、发送结果不明当作成功，不重复发送拦截。
3. 快递100和拼多多均明确返回无轨迹。HTTP、签名、鉴权、限流、服务器异常、仅空对象或不可解释字段都不能放行。
4. 本订单及工作台已知同运单其他订单没有历史揽收、运输、派件、签收、退回、等待退回锁定或未能解释的非空物流响应。历史记录只增不清除，不因后来的空结果覆盖历史。只能依据可查询的历史，不能保证平台从未漏传记录。
5. 北京时间 **09:00（含）至21:00（不含）**，并与已有客服工作时间配置取交集；扩大原配置也不能把本风险策略扩大到夜间。隔天仍无轨迹的前一天发货单不再适用。

## 接口判据

- [快递100官方实时查询文档](https://api.kuaidi100.com/document/5f0ffb5ebc8da837cbd8aefc) 1.9：HTTP成功、`returnCode=500`、`result=false`、`message=查询无结果，请隔段时间再查`，无冲突的轨迹/身份/签收字段。这里的500是JSON业务码，不是HTTP 500；501/502/503/504/601等不放行。旧代码用于无轨迹分流的宽泛文本匹配、`status=201`、`data=[]`不作为本规则放款凭据。
- [拼多多官方物流API](https://open.pinduoduo.com/application/document/api?id=pdd.logistics.ordertrace.get)：通过`pdd.logistics.companies.get`把订单`logistics_id`唯一映射到官方公司`code`，再用`company_code`、`mail_no`、`cache=false`查询`pdd.logistics.ordertrace.get`。只接受`50001 + ISV_TRACK_ERROR`组合。已通过官方`https://open-api.pinduoduo.com/pop/error/solution`只读核对，该子码解释为轨迹不存在。其他50001子码不等同暂无轨迹。只读调用使用本店凭据，禁止跨店猜测。
- 不解析尚未验证的拼多多轨迹成功格式来直接退款；返回非明确无轨迹响应会保守锁存历史保护，交回常规物流核查。

## 配置与执行

新增`MODULE1_NO_TRACE_RISK_REFUND_ENABLED`，默认false。经业务风险授权后才可设true，并且仍需要原拼多多资金开关、模块1执行开关、店铺同步隔离通过。没有新增定时任务、密钥或企微出口；天猫等其他平台不使用本规则。

沿用后台物流闸门及执行器。风险判据通过后，物流仍保存`UNKNOWN`，任务使用`refund_gate=DUAL_NO_TRACE_RISK`；JSON中的`no_trace_risk_evidence`保存五条依据、两接口结果、平台发货时间、订单金额/SKU快照、拦截任务ID及复查时间。界面时间线注明风险规则；不能显示为确定待揽收、快递已拦截、验货通过或ERP已完成。

任务沿用同一`PDD_AGREE_REFUND`幂等键。资金请求前重新跑物流闸门（双接口再次核对），证据不得超过90秒；复查最新平台金额、SKU、状态、运单、发货时间和历史保护。业务请求前持久化`uncollected_request_started_at`，已有标记不重开任务、不自动重发资金请求；响应不明仅回查。

风险退款检查通过后物流定期复查设为30分钟；资金前的独立安全复查不使用持久化空轨迹缓存。本次不改变原正常轨迹查询的全局间隔。遇到官方频控只能退避，不能把频控错误当成无轨迹。既有无轨迹六次退出人工状态中，**当天新入工作台且仅因无轨迹退出**的订单允许重新评估；其他人工原因不解锁。仍不符合则保留本地原因，30分钟后按原后台重查，不因此发布业务员待办。

## 迁移、部署和回退

迁移`20260909_0025`新增`logistics_physical_seen_at`历史保护时间；名称表示历史保护锁存，未解释的非空响应也保守锁存，不代表已确认揽收。回填当前明确物流状态，以及历史任务里的`preflight_state/refund_gate`物流证据，不把拦截消息等同物流。

1. 用`scripts/module1-autostart.ps1 -Action StopWatch`停止守护；用`scripts/module1-worker.ps1 -Action Stop`等待后台自然结束，不强杀资金请求。
2. 备份本地.env；执行`.venv/Scripts/alembic.exe upgrade head`。
3. 保持风险开关关闭先测试；使用`Module1LogisticsGateService.run(dry_run=True, after_sales_sns=(目标售后号,))`只读预演。批量CLI默认预演：`.venv/Scripts/python.exe -m aftersales_workbench.workflows.module1_logistics_cli --limit 20`。`--apply`只写本地状态与队列，不代表资金调用已成功。
4. 经已授权范围验证后设置风险开关true，恢复后台与守护，回查真实平台状态。修改.env需要重新启动进程才能生效。
5. 回退必须先停后台，关闭新开关，冻结尚未执行且`refund_gate=DUAL_NO_TRACE_RISK`的任务。资金已发起的仅回查；保留历史保护字段，禁止直接降级删审计。

## 验证与隐私

`tests/test_no_trace_risk.py`覆盖五条条件、双接口错误分类、同包裹历史、自然日与工作时间边界、待执行证据变化、失败冻结、仅无轨迹人工状态恢复、资金幂等及只读预演。真实个案的授权、订单、运单、金额和回查结果仅保存在Git忽略的`.runtime/audits/`，不提交远端。

本次使用说明同步到仓库docs；Notion连接当前不可用，未声称更新Notion页面。代码和文档一起提交推送，远端结果以最终交接为准。

部署验证：仅包含本次暂存改动的独立快照 **825项测试通过**；新规则定向65项通过；本次修改Python文件Ruff全部通过。另有现有Starlette/httpx兼容性弃用警告，不影响测试结果。真实订单已做双接口只读预演，资金结果另以平台回查为准。

真实MySQL验收发现`DATETIME(0)`会四舍五入小数秒，而JSON保留小数秒；安全闸门正确在资金请求前拦住不一致。本策略已在生成证据和写入数据库前统一截断到秒，保持严格一致校验，并新增回归测试；未通过放宽90秒保护来绕过此问题。对这种明确未发起资金请求的个案，保留失败记录并复用原任务重新核验，不新增幂等任务。
