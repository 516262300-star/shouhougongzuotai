# 模块1：逐单退款流水与最终闭环校验

## 行为和范围

从本次版本起，ERP 客户名下退货单型号、颜色、数量匹配且余额在原容差内，仅返回 `refund_unverified`（退货已匹配·待核验退款流水），不再直接返回闭环。只有最终实际累计应收为零，并核实该订单退款流水后，才能进入 `closed_loop`。即使只有 0.01 元差额，也不能由新闭环校验直接抹平。

最终完成必须具备：

1. 明确的发货后仅退款订单，平台已退款。已知失败状态不能被遗留成功整数状态覆盖。
2. 退货已归正确客户，不在暂存；完整型号、颜色、数量匹配，有有效单价和运单。
3. 对应平台订单、售后单号及 ERP 订单的退款收款流水存在，金额与该订单商家应收一致；流水引用唯一、无欠货且累计应收为零。
4. 最终写入前再次读取当前本地订单。若退款状态、金额、运单、客户或明细变化，或者核验证据超过 5 分钟，继续等待，不登记完成、不取消待办。

退货商品单价和退款金额不是同一字段，不能强行设为相等。原价、整单退款（可能涉及优惠或运费）分别保留，实际流水必须按该订单应核对金额严格核验。本次不自动解释、调整或抹平差额。

目前复用的 ERP 退款查询适配器限定拼多多，因此新逐单闭环证据只放行拼多多。天猫等平台仍可查询退货事实，但显示等待退款流水核验，不借用拼多多查询页放行；这不影响其原有售后同步或平台独立退款权限。

## 调用链与防重复

- 常规 ERP 退货轮询、指定订单 CLI、历史单补记，以及模块1 ERP 补单后的完成判断，均接入同一证据校验。
- 同一运单多笔订单先核对合计退货明细，各订单再分别查询自己的退款流水；一笔流水不能复用给其他订单。未查到自己的流水的订单仍待核验。
- `apply_lookup` 即使收到 `CLOSED_LOOP` 字符串，也必须有本次类型化证据；旧任务 JSON、零余额或一张退货单号不能单独放行。数据库锁定读刷新退款状态和明细，逐笔提交释放锁，不跨下一笔 ERP 网络查询持锁。
- 找不到流水或查询失败：保留待核验，不调用补单接口、不自动认领、不取消已有待办；新“缺少证据”状态本身不追加面向业务员的待办。后台继续按原周期重查。
- 新证据在任务 payload 的 `erp_closure_evidence` 中留存平台订单号、售后号、ERP 订单、退款流水、核验金额和核验时间。已有历史完成记录不批量重写，仍需另行安排只读审计。
- 退货单证据查询与最终写入之间不是跨系统事务；无法保证 ERP 同时没有人员修改。采用新鲜查询和本地最终复核缩小窗口，不能宣称跨系统原子操作。
- 不新增认领自动化，不开放批量认领；一次人工授权认领成功不等于全局自动认领上线。模块2继续使用退货匹配结果作为收货证据，不把模块1的流水条件当作再次平台退款的理由。

## 使用、开关与恢复

无新环境变量、权限、数据库表或迁移。沿用 `ERP_WEB_LOOKUP_ENABLED` 和本地 ERP 登录凭据，只读查询；原模块1 ERP 补单写入开关不变。本次保持人工待办自动发布关闭。

后台沿用单笔 ERP 复查最短 1800 秒、每批 20 笔；这不是整队列每 30 分钟必定全部检查完的承诺。新状态可在原订单详情和 ERP 异常筛选中查看原因；监控计数新增 `refund_unverified`。

指定订单只读检查（不加 `--apply`）：

```powershell
.\.venv\Scripts\python.exe -m aftersales_workbench.integrations.erp.return_match_cli --platform-order-sn <平台订单号>
```

`--apply` 仍是本地状态写入操作，只有逐单核验通过才允许完成；不会调用 ERP 认领、平台退款或额外补单。结果无法确认时先读状态，禁止盲目重复外部写入。

升级前备份本地数据库及日志，等待后台当前周期安全退出，再更新 Web/后台；无需迁移或修改 `.env`。回退旧版本会重新使用缺少逐单流水的闭环判定，不建议在线直接回退；必要时先安全停止后台，保留数据和日志，不批量删除新证据字段。
