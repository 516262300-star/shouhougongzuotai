# 拼多多交易完成订单的拦截与人工待办分流

## 问题与修复范围

拼多多订单状态3被保存为DELIVERED，原模块1仅选择IN_TRANSIT，导致交易完成后新申请的全额仅退款在查询实际物流之前就被排除；即使包裹仍在驿站或继续派送，也既没有拦截任务、也没有签收人工待办。

只扩展拼多多模块1的通知候选：待检查、具有发货运单、正数全额仅退款、平台售后状态2且订单退款状态2、没有任何既有拦截任务。原店铺范围、同步异常隔离及其他平台条件保持。

新增入口先只读查询原店铺的实时订单与指定售后，核对身份、有效仅退款状态、申请金额与全额、发货事实、公司和运单。已关闭、撤销或改成退货退款的陈旧记录跳过，不能据此制造签收待办；未知或查询失败单独留在本轮`completed_trade_check_errors`，不阻断其他正常候选。不会在这个核验中改平台数据或把原订单改写成在途。

## 真实物流分流

- 有效运输/派件或未知非空轨迹：继续现有物流预检、整包裹保护、群映射及企微防重。派件和未知状态的退款保持HOLD。未知状态码不因文字像“派件”就自动变为资金放行。
- 真实签收且无退回证据：预检取消尚未发送的通知，转人工处理，按ERP原销售业务员生成待办；归属缺失或冲突按原规则保留本地待核实，不能猜人。远端回查确认待办存在后才表示已通知。
- 退回中或已退回：沿用原退回/ERP核验，不另发拦截。
- 物流技术失败：保留未发送并按原退避重查，不当作已签收或暂无物流。

平台发货/签收映射、真实退款前复核、资金幂等及整包裹保护不变。不能以进入通知队列或发群成功证明包裹已拦截，也不会因此给予交易完成订单自动退款资格。原已发、取消、人工处理或结果不明的任务不重建、不清账本。

## 运行与恢复

复用现有模块1正常后台周期，无新计划任务或开关。只有本轮对应平台同步通过后才按原范围扫描。异常可查看运行监控的建任务阶段、单笔任务、物流预检、原销售归属与发送凭证。

发布只从新挂机电脑实际Worker版本复制候选，替换本修复源文件并离线验证；保留其他最新平台功能。安全等待原周期结束、备份并验证后切换Worker指针，再由原守护恢复。Web和独立提醒不需要因本修复切换。

回退同样先安全结束周期并恢复上一Worker指针，保留新产生的业务任务、待办、资金和发送凭证，不能恢复旧数据库覆盖已执行结果。真实订单、API回查及发布审计仅保存在Git忽略的`.runtime/audits/`。

## 验证

回归使用内存数据库和模拟平台/物流：交易完成但仍派送、未知派件异常、真实签收分派原业务员、物流超时、金额/类型/店铺/同步隔离、实时售后关闭或变更、单笔查询异常不阻塞正常订单、相同通知和待办不重复，以及退款前仍拒绝交易完成状态。

同时执行现有模块1预检、人工待办、整包裹、全平台通知/无轨迹、天猫整单及未揽收资金保护回归。实际生产结果另在验收后记录，不以模拟测试宣称真实消息或退款成功。
