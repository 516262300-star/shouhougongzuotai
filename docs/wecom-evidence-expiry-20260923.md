# 企业微信输入前证据过期自动恢复

## 原因与修复

新正式机发生一次输入前暂停：同包裹核验约两秒完成，但准备输入时距证据起始时间已约212秒，超过原有80秒有效期。原订单快照一致、没有同包裹人工处理锁；输入前截图确认目标群正确、输入框为空、相同消息气泡为0，任务尝试次数为0。现有审计未覆盖全部窗口准备步骤，不能据此确定延迟来自哪一步。

原代码把证据过期和身份变化都抛为普通错误，留下无自动重试时间的 `PausedBeforePaste`，阻塞后续队列。本次仅把“任务仍待执行、订单快照一致、无同包裹人工锁、证据年龄大于80秒”区分为可重查的输入前过期。冷却60秒后由下一次正常通知周期重新取得完整平台和包裹证据，再核验群名、输入框及永久发送账本。

没有延长80秒有效期，也没有改写旧证据时间来放行。未来时间、缺失证据、订单身份或金额变化、取消任务继续拒绝输入。已进入 `PasteStarted` 或 `SendPressed` 的任务不能被该异常降级重发，仍沿用既有防重与回执处理。消息气泡成功即可确认发送，不依赖快递回复。

## 入口与现场恢复

入口仍为新正式机的 Module1 Worker 和 `Leedis Aftersales Module1 Watchdog`；不新增常驻任务或配置。到期重试由实际业务周期触发，并非保证60秒发出。

对本次旧格式暂停记录，先在发送锁内核对完整账本历史均未输入、任务仍待执行且尝试次数为0、原发送方案哈希未变、包裹无发送占用，以及原始证据与失败审计。只有全部满足才单独追加可重试暂停记录，保留旧历史；不按错误文本批量解锁，不使用“确认已发送”冒充成功。个案资料保存在 Git 忽略的 `.runtime/audits/wecom-repair-20260923/`。

发布基于新机当前正式 Worker，只替换 `notice_package_guard.py` 和 `desktop_sender.py`，保留人工待办、仓库验货、退款事务及宽屏企微修补。等待原周期自然退出、备份原发布指针与发送账本后切换，原交互桌面守护恢复运行。

## 验证

回归覆盖212秒超时但零输入、冷却到期前不恢复、恢复后重新完整核验且只发送一次、80秒边界、证据缺失/身份变化/取消/时钟异常不自动重试，以及已输入或已按发送键绝不降级重发。部署后的真实发送结果另行记录，离线测试不等同现场消息成功。
