# Windows 可选组件安装停滞时的临时部署入口

2026-09-23 新机安装 OpenSSH Windows 可选组件曾长时间停在 Running。临时连接 v3 已修复接入后的启动误判，并在新机通过完整安装包传输和 SHA256 核验。Python/MySQL、数据恢复演练与桌面预检已完成；正式任务仍禁用，旧正式机继续运行。最新迁移状态见[新机迁移](office-machine-migration-20260922.md)，下文保留早期断线调查过程。

早期 CBS 日志显示 10:35:45 下载完成，Windows Update 在 10:35:50 记录事件 41；随后远程读取的 CBS 记录在 11:44:50 报 `Finalize failed: 0x800700b7 ERROR_ALREADY_EXISTS`，但不足以确定内部冲突原因，不能将该错误直接当作临时 SSH 断线根因。

## 入口与边界

`scripts/office-portable-access.ps1` 提供独立的临时维护入口。使用微软 Win32-OpenSSH 官方 `10.0.0.0p2-Preview` ZIP，固定 SHA-256 为 `23f50f3458c4c5d0b12217c6a5ddfde0137210a30fa870e98b29827f7b43aba5`，并在启动前检查 sshd、ssh-keygen、sftp-server 的微软有效数字签名。该上游包标记为 Preview，仅用于有人值守的临时连接，不将它作为已验收的正式服务。

包在开发机预先下载，包含脚本、启停 CMD、官方原始 ZIP、公钥和说明；没有私钥、客户数据、正式配置。个性化地址与交付包保留在 Git 忽略位置，不提交远端。按 `sync-automation-docs` 规则同步本说明及代码。

新机以本地管理员账户启动，文件保存于 `%ProgramData%\LdsAftersalesPortableAccess`，权限仅 SYSTEM/Administrators。独立主机密钥、授权文件、配置和日志不写入 `%ProgramData%\ssh`。仅对指定开发机单个私有 IPv4 放行程序的 TCP 22222，SSH 同时限定当前本地账户及来源地址、公钥认证，禁止密码、交互密码、端口转发和 PTY。不安装 Windows 可选组件，不注册 SSH 服务，不改原服务、原 SSH 配置、原防火墙规则及原安装状态，不停止 DISM、TrustedInstaller 或 Windows Update。

```powershell
# 预演校验参数、公钥格式和官方 ZIP 哈希，无系统修改。
.\scripts\office-portable-access.ps1 -DevelopmentAddress <开发机IPv4> -PublicKeyFile <公钥路径> -Archive <官方ZIP路径> -WhatIf

# 新机管理员执行，默认60分钟，最多60分钟。
.\scripts\office-portable-access.ps1 -DevelopmentAddress <开发机IPv4> -PublicKeyFile <公钥路径> -Archive <官方ZIP路径>

# 同一管理员账户在另一个窗口关闭临时入口。
.\scripts\office-portable-access.ps1 -Action Stop
```

保持启动窗口打开。进程实际监听后才输出 READY、账户、端口和新主机 SHA256 指纹；必须通过用户提供的指纹核验新主机，使用独立 known_hosts 记录，不复用旧机指纹。调试模式一次接受一个连接，结束后重启监听器；这不自动重试远端命令或资金请求。

正常到期或异常退出会结束自建监听进程并移除本轮专属防火墙规则；Stop 还可在核对进程路径、启动时间后结束遗留监听器。强关窗口或断电不能保证 finally 清理，必须用停止入口核对并清理；不要只凭窗口消失认定已关闭。再次启动保留同一主机密钥，来源、公钥或账户不同则拒绝覆盖。已有端口占用、并发运行、哈希不符、签名无效、配置验证失败均停止，不接管其他进程。

通过临时入口连接后，先只读采集组件状态、安装进程、CBS/DISM/Windows Update 日志和重启状态，再修复或重建正式部署服务。临时连接不等于正式业务部署；仍按迁移说明完成停写、最终一致性备份、幂等账本迁移及唯一执行端切换。

## 新机首次连接与文件传输修正

用户提供 READY 和主机指纹后，已核对新机独立主机密钥并以原部署公钥实际登录；确认 Windows 11 家庭中文版、运行账户与用户截图一致，独立 D 盘空间充足。已创建受保护的正式部署目录，但没有安装或启动业务服务。

开发机内置 `ssh-keyscan` 在混合密钥交换时报告 unsupported KEX；使用本次已核验官方包中的 `ssh-keyscan.exe` 获取公钥并比对截图指纹，命令连接显式指定 `KexAlgorithms=curve25519-sha256` 后登录成功。没有关闭严格主机身份校验。

首次 SFTP 子系统请求得到退出码1，因此将 `Subsystem sftp internal-sftp` 改为独立目录中明确路径的 `sftp-server.exe`，并把其微软签名纳入启动校验。新机配置原文先备份，经实际 `sshd -t` 校验成功后供下一轮监听器读取；不变更认证、来源限制和端口。本地通用脚本同步此修正。

随后文件传输连接中断，开发机检查新机端口超时，旧正式机仍可连接。暂未取得中断的确切根因；绿色 READY 是初始成功提示，不能证明当前仍能通信。需用户通过包内 Stop/Start 入口恢复连接，再核验完整文件传输及当前网络。已有演练快照24张表、schema `20260919_0029` 和三份当前发布代码的本地归档校验通过；它们不替代最终停写快照。旧正式机未停写，新机未接管正式业务。

用户后续截图标题显示“选择”，确认该窗口进入文字选择状态。通用启动脚本现用 Windows `SetConsoleMode` 仅关闭本窗口的 QuickEdit，不改注册表或其他窗口默认设置。新机已在核对启动器身份后实施同一范围的修正，输入模式读回从503变为439，仅清除0x40标志。退出选择后重新登录成功，但大文件传输仍再次中断；不能将所有断线归因于选择模式，仍需取得失败当时的进程、端口和防火墙证据。微软依据：[SetConsoleMode](https://learn.microsoft.com/en-us/windows/console/setconsolemode)。

`scripts/office-portable-diagnostics.ps1` 为只读采集入口，在新机管理员窗口执行，默认在脚本旁生成 `connection-diagnostics-时间.txt`，也可用 `-OutputDirectory` 指定既有目录。报告包含IPv4、网卡状态、22222连接、白名单内状态字段、连接程序进程、受管防火墙规则、筛选后的近期SSH错误和当前休眠配置；不安装、启动、停止进程或改配置，不读取私钥、密码、业务环境文件。日志过滤掉执行命令和环境正文。断线后由用户双击诊断包中的入口并回传TXT，避免反复手输查询命令。当前仍未安装Python/MySQL业务运行环境，亦未停写或迁移正式业务。

## v3：修复接入连接后的启动误判

用户截图明确指向启动循环的 `Temporary listener failed`。本机使用同一官方 sshd 仅绑定 `127.0.0.1` 复现：`-d` 模式接入一个连接后关闭监听套接字，进程仍在处理会话，此时 `Get-NetTCPConnection -State Listen` 为0。旧脚本在首次检查前若已接入客户端，会超时误判启动失败，随后 finally 杀掉正在工作的进程并移除防火墙。这是脚本缺陷，不能要求使用者通过反复重启窗口解决。[上游 sshd 手册](https://man.openbsd.org/sshd.8)也明确说明调试模式仅处理一个连接。

v3 改用每次启动独立日志中的真实绑定成功记录判定启动；接入连接或短会话结束后该证据仍有效。退出进程先等待重定向日志写完再读取；实际绑定失败或8秒内没有成功记录仍报错。端口占用预检、来源/公钥限制、最多60分钟到期、Stop清理和只重启监听器的行为保留，绝不重放远程业务命令。并包含外部 SFTP 路径与本窗口 QuickEdit 修正。

`tests/test_office_portable_access.py` 共11项检查通过，包含真实 sshd 的快速接入、快速结束、端口已占用三种回环场景，其余为输入和 WhatIf 保护。集成测试需要将 `LDS_TEST_OPENSSH_DIR` 指向已独立校验的官方程序目录；未提供时仅跳过这3项。测试使用临时主机密钥，回环监听在 finally 中清理，不修改服务或防火墙。

另在开发机回环地址完成32 MiB真实公钥认证 SFTP 传输，刻意让客户端先接入再执行实际启动检查函数，结果为 ready=true；传输持续20.3秒，完整33,554,432字节的SHA-256一致。这验证了本地快速接入后的传输路径，不代表新机网络及正式迁移已验收。

交付文件为 `售后工作台-备用连接包-v3-20260923.zip`，用户完整解压后以管理员身份运行 `1-Start-Access.cmd`，保持窗口打开。原包已报错退出时可直接启动v3；如旧入口仍在运行，先用同包 `2-Stop-Access.cmd` 停止，不能同时启动两个入口。保留原主机密钥，修复包不含私钥或业务资料。新机实际传输、业务安装与切换仍须在修复包启动后完成验证。

## v3 新机验证与一次性重连

新机实测已完整接收 Python、MySQL、离线依赖及代码包，逐包 SHA256 与开发机相同，未再出现接入后误杀传输的问题。14:29 正常重启后，经核验的同一主机密钥登录成功，数据库服务已自动恢复。

为本次有人值守的重启排障，另在受保护的部署目录准备一次性登录重连任务：仅指定本地部署账户登录时执行，先核对自身 Action 并注销自身任务，再调用原 v3 入口开启新一轮最多60分钟的连接。来源 IP、公钥、主机密钥及禁止密码/转发等限制不变。它不是永久远程服务，也不循环续期；首次已核实任务自行注销。后续因系统组件排障需要的正常重启使用相同的一次性机制，最终收尾须再次确认临时任务及规则状态。

系统 OpenSSH 安装诊断、正常重启及 Windows Update 服务恢复均属于本次单独的受控排障操作，没有加入通用临时入口脚本。在线安装在下载结束后停滞；混合缓存目录作本地源返回 `0x800f0912`，因此另备仅含已校验 FoD CAB 的目录并使用 `LimitAccess`，安装结果须实际读取后再判断，不能只凭“下载完成”认定已安装。
