# 无轨迹仍须发出拦截通知

旧发送前预检会在快递100连续6次无轨迹后取消通知，即使订单已发货、客户已申请有效全额仅退款。发送队列暂停期间积累到阈值也可能触发取消，漏掉应通知快递的包裹。

按2026-09-22用户明确要求，正常查询无结果不再因次数达到6次或更多而取消尚未发送的拦截。原平台、已发货、仅退款、完整包裹范围、同步健康、快递群与运单防重仍需通过；同包裹只有部分订单退款继续转对应原销售业务员，不发群。平台尚未适配完整包裹核验时不直接放行。

## 运行规则

- 原后台发送前预检统一适用，不新增定时任务、权限、数据库结构或环境开关。
- 正常无轨迹保留待发任务，继续原退避复查，记录 `preflight_query_result=NO_TRACE`；当前物流仍为 `UNKNOWN`、退款仍为 `HOLD`，不伪造未揽收或物流已拦截。
- 网络、配置、鉴权等查询异常记为 `UNAVAILABLE`，预检不放行发送；原人工检查标记也不能作为发送凭证。后续有效轨迹重新写入 `TRACE` 并清除过时错误标记。
- 已知签收、退回中、退回签收或存在历史退回记录时，当前无结果不能冲掉原证据并发出新拦截。
- 原发送后物流和退款闸门保持，包括无轨迹退款限制、独立风险规则、同包裹保护、工作时间及资金幂等。仅允许发通知不等于允许自动退款。
- 历史因无轨迹取消的任务不批量重放。逐笔核对当前平台、完整包裹、永久发送账本和群内人工通知；已由业务员发群并获快递登记的，只补记人工处理及防重，不重发，不记作机器人真实发送。

## 验证与部署

本地86项相关测试及Ruff通过，覆盖第6次、已超过阈值仍保留通知、技术错误不冒充无轨迹、签收/退回证据保留、有效轨迹恢复，以及原全平台包裹保护、桌面发送与物流退款规则。

发布仅基于当前正式Worker复制候选并替换 `module1_preflight.py`，核对前后文件哈希并在候选复测；等待原业务周期自然结束，验证备份后切换原Worker指针。Web与独立揽收提醒、桌面发送实现保持当前正式版本；不夹带尚未上线的其他候选或工作区既有改动。

个案核验、群内业务员拦截与快递回复证据、部署及备份记录只存Git忽略的 `.runtime/audits/no-trace-intercept-20260922/`。正式验收完成后补充结果。对应旧说明为[无轨迹分流与退款冻结](logistics-no-trace-routing.md)。
