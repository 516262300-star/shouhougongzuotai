# 天猫模块3复用现有ERP（2026-09-11）

用户明确要求天猫与拼多多模块3采用同一业务流程：平台已退款 → 核实未发货及ERP原订单 → 缺退款单时补开一次 → 回查退款流水、欠货及余额 → 核实后完成。

## 本次纠正与改动

原ERP `AliController::executeDeleteProdlist` 已有天猫分支，和拼多多共用 `/leedis2/public/1688api/deleteprodlist/{id}?actionid=1`。该入口按平台及客户选择凭据，并在业务执行前检查订单启用、报价单编辑冲突及平台退款状态。不是没有ERP业务接口。

旧管理列表不显示原始 `detail` 字段，但 Voyager 只读详情页 `/leedis2/public/admin/refunds/{id}` 已提供 `Detail`。原先要求新增服务器只读接口是实现选择，不是必需条件。现有ERP账号已通过实际列表、详情读取验证，不要求用户再提供账号或服务器权限。

新增 `TMALL_MODULE3_ERP_READ_MODE=existing_admin`（新代码默认值）：

- 按完整父订单号在现有管理列表精确筛选；必须唯一记录、完整无分页表体、唯一详情ID。
- 获取只读详情，核对必需字段、父单/退款单身份及原始子单数量JSON，再与另一次列表读取交叉核对；缺字段、重名字段、错误页或截断都阻断。
- 兼容已实测的 Voyager “是否退货=否”显示，不将空值当作否或零金额。
- 后续原收款、SKU/颜色/数量、独立客户账、完整发货页、退款流水、欠货和余额核验保持不变。页面查询没有读取订单启用/编辑表，**不填造 `activating=false` 或 `editing=false`**；这两项冲突检查由现有共同补单入口在写入前执行，与原ERP操作一致。服务端拒绝、响应不明或核账不一致时保留资金未知记录，不自动重发。
- 不调用存在批量归档副作用的 `1688api/showlist` 做只读预检，不调用编辑、删除管理页面。实际补单依旧使用上述同一业务入口，保留持久化幂等及写前再次核验。
- `dedicated` 方式保留给已部署专用接口的环境；两种读取方式必须显式选择，不在错误时静默切换。核验证据记录所用读取方式，写前切换方式会被阻断。

## 运行与权限边界

模块3处理平台**已经退款成功**后的ERP账务，不是再同意一次平台退款，不依赖模块1/2的退款子账号白名单。现有候选仍仅适配天猫第1–5店独立单订单、单子单、整单等额退款；第6店、多包裹、部分退款和证据不足的情况不自动扩大范围。

保留 `TMALL_MODULE3_ERP_REFUND_ENABLED=false`，现有生产worker/Web版本及本机 `.env` 本轮未修改，未启动资金请求或修改历史任务。默认读取方式变化仅影响新代码，不代表线上旧运行副本已经启用模块3。

真实只读预演：当前116条天猫 `ERP_CHECK_FULFILLMENT/PENDING` 任务中，109条为 `UNKNOWN/PENDING_CHECK`，7条已有 `IN_TRANSIT`（分别为人工处理5条、拦截成功1条、待退货ERP核对1条）；均不能直接按明确未发货放行。预演 scanned/ready/applied 均为0。真实ERP页面抽样只验证读取与原始明细存在，样本无ERP原订单，不是正常补单样本。

因此下一步是核实未知发货状态任务的平台原始事实与ERP对应订单，找到满足条件的真实只读验收样本后，再基于明确提交独立发布并开启模块3；不能为了让队列运行而批量改成未发货。无需以索取服务器权限作为前置条件。

追加只读抽查3条UNKNOWN任务：退款状态均为SUCCESS，退款中的原订单状态和当前交易状态均为TRADE_CLOSED，未返回发货时间。交易关闭及没有发货时间本身不能证明从未发货，未据此更新本地发货状态或执行补单。

## 验证、部署与回退

131项模块3、现有管理页面、发货保护、资金幂等及天猫单包裹相关回归通过。新增测试覆盖现有页面完整读取、一次补单与回查、重复调用阻断、字段/金额/身份不符、缺页、重复记录、服务端拒绝后禁止重试，全部使用合成数据。

部署时只将本次相关文件及既有模块3候选依赖带入独立运行副本，不混入其他未提交开发改动；无数据库迁移。后台继续按既有模块3批量与复查间隔运行，开关须同时满足天猫接入、模块3总开关及ERP写开关。先只读验证，实际写入前确认旧ERP其他执行器没有并发处理目标订单。

回退先关闭天猫模块3开关并等待worker当前周期安全退出，恢复原独立发布指针；保留资金账本及所有UNKNOWN记录，不重置失败任务。可以保留读取模式配置，它本身不授权补单。
