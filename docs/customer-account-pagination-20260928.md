# 客户历史账页超过30行时的ERP补单核验

原客户商品账读取器只接受一页。天猫已实现的同父订单、多个已退款子售后分组补单，即使当前订单证据齐全，也会因客户其他历史记录使账页超过30行而停止。本次补齐该共用读取器的完整分页能力。

## 行为与边界

- 使用原客户ID和原只读商品账接口，从第一页读取至末页；每页必须具有唯一连续页码、稳定总页数、完整唯一表格，非末页必须返回完整30行，末页必须1至30行。
- 最多200页，完整读取和复核合计60秒。超限、缺页、重复整页、权限或网络错误、页面截断及字段缺失均继续待核验，不能返回部分结果。
- 多页全部读取后，反向逐页再次读取并比较完整行内容，包括原销售、退货关联、数量及价格。任一页变化都丢弃本次证据，下一轮重新读取；不只复查首页，不长期缓存账页。
- 读取成功不表示允许补单。沿用各自调用者的原销售、实收、客户余额、原收款、已有退款流水、资金幂等和执行前复核。天猫分组补单仍要求整组已退款成功、唯一原销售RC和正式TH、完整商品及金额一致，每周期最多新补一笔ERP退款单。
- 不扩大平台退款范围，不开启多订单多包裹自动资金执行，不自动认领抖音暂存单。共用读取器用于抖音或淘宝已有核验时，仍受各平台原资格及写开关限制。

## 入口、验证与发布

沿用现有模块1后台及天猫退回认领/分组补单阶段，没有新增定时任务、环境变量或数据库迁移。输入仍是ERP客户ID，输出为全部商品账行；失败继续由原任务记录原因并按原周期重查。

测试覆盖86页和200页历史、完整读取及逐页复核、末页目标记录、其他页关联冲突、分页漂移、重复/截断/权限页及60秒截止；分组执行模拟验证仍每周期最多一笔，不调用平台退款。

发布须基于新正式机当前Worker副本，仅替换本次读取器和测试；候选回归通过后，等待原周期自然结束、验证备份，再切换Worker指针。保留Web、独立揽收提醒、资金开关及已有记录。只读预演不调用资金接口，也不冒充真实补单成功。

回退只恢复发布指针，保留发布后已经发生的资金及幂等事实；不能恢复旧数据库或删除记录。旧版会重新拒绝多页账单。

## 本轮尚未解决的其他缺口

长客户历史导致拦截核验超时是另一条查询路径。只提高分页上限仍要查询大量平台订单，无法解决发送前证据时限。当前已找到ERP由原发货单查询运单的只读接口，但尚未确认“按运单完整反查全部销售订单”的契约，未据此修改包裹范围或解除已经发布人工待办的记录。

部分退货数量来源、复杂合包自动退款、抖音暂存认领以及优惠/运费差额自动核账仍需分别适配、验证；本次不将它们标记为完成。
