# 模块1：自动识别待揽收

> 2026-09-10 审计修复：资金请求防重、异常响应、独立质检和发送回执规则已有调整；以[安全修复与部署说明](audit-safety-fixes-20260910.md)为准。代码准备不代表生产已部署或已验收。

2026-09-09起，拼多多已发货全额仅退款增加自动待揽收判断，不以逐单人工确认为常规前置。

后续业务授权新增[双接口无轨迹风险退款](dual-no-trace-risk-refund.md)。它与本文的接口明确102待揽收是两个独立分支：无轨迹风险放行仍保留UNKNOWN，不冒充待揽收物流事实。新分支有独立默认关闭开关和历史保护迁移。

## 自动运行依据

快递100实时查询请求增加 `resultv2=4`、`order=desc`，保留高级物流状态。按[快递100官方实时查询文档](https://api.kuaidi100.com/document/5f0ffb5ebc8da837cbd8aefc)，`102` 表示待揽收，`101` 仅表示已下单，`103` 表示已揽收。

自动分支必须同时满足：

1. 最新有效轨迹明确返回 `statusCode=102`；响应运单和快递公司与查询目标一致，顶层状态不冲突。
2. 整票没有已揽收、在途、派件、签收等冲突记录；轨迹时间有效且按倒序排列，最新记录在24小时内，不能来自未来。
3. 拼多多订单为已发货全额仅退款，发送账本中对应运单/快递公司的拦截任务已成功；同步隔离、金额/SKU和防重复保护继续生效。
4. 客服工作时间内，资金动作前再次核对最新物流，证据有效期90秒；再读平台最新售后状态、金额、型号数量、运单、快递公司和24小时内发货时间。业务时间仍使用现有配置，默认09:00–21:00。

满足后使用现有 `PDD_AGREE_REFUND` 和同一幂等键自动退款，无需人工登记确认。任务JSON保存 `auto_uncollected_evidence`：接口来源、状态码、轨迹/查询时间、订单快照和成功拦截任务ID。页面显示“待揽收（自动识别）”。不是伪造快递已拦截、已经归仓或ERP平账。

## 不会当成未揽收的情况

- 空轨迹、查询无结果、订单刚标发货、ERP揽收字段为空，都不单独证明未揽收。原无轨迹退避与异常分流规则继续有效，不能承诺所有真正未揽收的订单均会返回102。
- 网络超时、鉴权/签名错误、响应身份不符、字段不足、状态矛盾、过期轨迹：冻结退款，保留原因。
- 仅101或其他未知状态：冻结当前退款但继续原轮询，后续取得明确102或正常在途证据可推进。曾经进入派件/签收而锁存“等待退回”的订单，不因后来出现102而放开，仍需退回记录。
- 部分退款只同步记录，不触发模块1拦截退款；其他平台不新增待揽收退款权限。

## 调度、失败和恢复

沿用现有模块1后台、物流预检、发送、退款闸门和执行器，不增加新定时任务、密钥或数据库迁移，不修改发布开关。查询间隔沿用当前配置；官方文档提示频控，若账户返回频繁查询应按频控处理，不以空响应放行或增加密集重试。

资金调用前持久化 `uncollected_request_started_at`，已有标记不重开任务；请求失败或结果未知仅允许只读回查，禁止盲目重发。待执行任务复查成派件、签收、夜间或查询异常时取消；变成正常在途则转回常规闸门并保留自动判断审计。

退款成功后仍需按实际货物流转和ERP单据平账，不伪造退货单。历史人工确认工具仅保留为另行明确授权的应急处理方式，见[人工确认文档](confirmed-uncollected-refund.md)，不为新订单自动生成 `USER_CONFIRMED`。

部署前暂停守护、请求后台自然停止；验证后恢复原后台和守护，不强杀进行中的退款。回退前必须停后台并冻结待执行的 `refund_gate=UNCOLLECTED` 任务，旧代码不认识该分支，不能直接恢复执行。真实个案资料只保存在忽略的 `.runtime/audits/`。
