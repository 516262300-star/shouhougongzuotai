# 各平台统一的无轨迹拦截通知规则

2026-09-22用户要求：已经发货、具有明确运单、有效全额仅退款的订单，不能仅因为没有物流信息、尚未揽收或多次正常查询无结果而停止快递群拦截通知。该规则不按平台区别处理；同包裹只有部分订单或商品退款仍转对应原销售业务员人工待办。

## 通知与实际接入范围

公共发送前预检、桌面发送计划及备用Webhook过滤入口共用同一物流规则。拼多多、天猫、淘宝、1688、京东、抖音的通知任务进入该入口时，正常无轨迹或等待揽收均保留通知；超过6次或更多也不自动取消。已签收或进入退回流程的真实证据仍阻止无意义的在途拦截，网络、鉴权、响应不完整等异常仍保留任务并自动重查。

|平台|无轨迹通知规则|当前实际接入边界|
|---|---|---|
|拼多多|统一保留通知|已启用自动拦截，仍须完整包裹及实时退款核验|
|天猫|统一保留通知，含多子单合计全额|已启用自动拦截，仍须完整包裹及实时退款核验|
|淘宝|同一公共规则|完整包裹保护已适配，但普通自动建拦截任务入口未启用|
|1688|同一公共规则|未完成完整包裹及自动拦截适配；进入发送入口时转人工核实|
|京东|同一公共规则|未完成完整包裹及自动拦截适配；进入发送入口时转人工核实|
|抖音|同一公共规则|未完成完整包裹及自动拦截适配；进入发送入口时转人工核实|

六个平台的公共规则测试通过，不代表六个平台的真实自动拦截均已接通。新增平台仍须具备有效退款、真实发货运单及全部包裹订单核验，不能绕过用户之前要求的同包裹部分退款保护。该规则只决定通知资格，不改变自动退款权限。

## 补齐天猫合计全额的独立入口

先前天猫多子单路径优先查询原生物流；明确无记录业务码或身份一致的空列表会被当作一般错误，未继续统一预检，可能造成普通全额单与合计全额单规则不一致。

现在仅在通知预检中，原生接口明确无记录，或者已核对交易、运单、快递公司一致后返回真正空列表时，继续调用快递100公共预检。原生节点显示等待揽收也沿用该路径；第三方明确无结果则保留通知与`HOLD`，已签收或退回则停止发送。缺失列表、身份不符、无效节点、网络或鉴权异常不冒充空轨迹。

`TradeInspector.trace_events`的资金调用默认仍不接受空轨迹。新选项只在通知预检使用，不影响原生物流资金闸门、普通订单20小时揽收提醒、已退款追退回以及原金融幂等。

## 验证与发布

本地210项相关回归通过，外部平台、物流、ERP及群发送均使用替身。新增六平台的公共预检、桌面计划与Webhook筛选矩阵，覆盖第6次及超过次数、等待揽收、查询异常和历史签收证据。天猫合计全额额外验证两种无记录码、身份一致空列表、待揽收均可经过真实发送服务的模拟网关，同包裹只发送一次；资金默认路径、错误身份和不完整响应保持阻断。

发布基于当前正式`no-trace-intercept-worker-20260922`，仅替换预检与天猫整单轨迹读取两个源文件，候选复测后等待原周期正常结束，验证备份再由原守护恢复。Web、独立揽收提醒、桌面发送实现与现有平台开关沿用。历史取消任务须逐笔核验，不批量重放，不专门发送真实测试消息。

审计目录为Git忽略的`.runtime/audits/all-platform-no-trace-20260922/`，不在仓库或外部说明保存真实订单、客户、运单或群聊证据。上一轮规则见[无轨迹仍须发出拦截通知](no-trace-intercept-20260922.md)。
