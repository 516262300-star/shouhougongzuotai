# 拦截退回核账待办：先核验、后转人工

## 使用规则

客户名下已有退货单，但客户累计应收不为零，不再单独触发业务员待办。累计应收是客户总账，不是该笔平台订单的差额；可能受其他订单影响。不能仅凭余额不为零认定缺退款单，也不能仅凭余额为零认定售后闭环。

后台继续沿用已有循环：匹配退货 → 自动补单预检/处理 → 生成待办 → 发布前复查。不新增定时任务，不改变店铺、资金和企微开关。退货匹配沿用 `ERP_RETURN_MATCH_REFRESH_SECONDS`（默认 1800 秒）及现有批量限额；后台周期由 `MODULE1_WORKER_INTERVAL_SECONDS` 控制，不保证每笔在一个周期内完成查询。

- 退货归属、型号颜色数量已匹配且符合已有拼多多金额及防重条件时，先执行原有 ERP 自动补单流程。
- 修正“在途退回补单误用未发货退货运单限制”：仅在已发货退回预检允许存在退货运单；未发货预检仍禁止。原售后身份、类型、金额、客户、销售关联、幂等账本及未知结果保护不变。
- 正常等待、接口超时/鉴权失败、商家应收未知、客户总余额不相等、不支持的平台，不生成“余额未归零请补单”的业务员通知。技术故障继续在运行监控核验，不伪装为业务差异，不标记已解决。
- 仅当逐单预检明确找到待处理记录，并确认金额不符、售后身份不符、退款类型不符或原销售关联不明，才生成有具体处理要求的核账待办。预检证据须在最近 30 分钟内，且退货快照未变化。30 分钟是证据有效期，不是强制延迟发送时间。
- 发布前及领取发送任务后都重新读取当前状态。旧的“余额未归零”积压待办也不能绕过新规则：无人工依据时不发送、不消耗尝试次数；已闭环的未发送待办取消。

## 页面怎么查

售后工作台 → 人工待办 → 搜索平台订单号。

保留“发送状态、业务员、发送时原因、实际原文、ERP 待办 ID、时间和尝试次数”，同时单独显示当前问题状态：

- **问题已解除**：已核实本笔退货、对应 ERP 退款流水和零应收，无需再按旧通知补单。保留原文和发送记录；不表示远端管理系统的待办已自动点击完成。
- **系统核验中**：目前没有有效的逐单人工处理依据；不要按旧余额提示重复补单。技术失败或待同步不等于已解决。
- **需人工处理**：展示具体差异和处理要求，客户累计应收不再作为本单差额写入通知。
- 其他退货异常在没有完整闭环证据时显示“待核验是否解除”。同包裹其他订单联系客户的待办不因本单平账而自动解除。

已经发送的消息不撤回、不改写、不再发一条“已解除”消息；只在工作台当前状态中区分。平台状态再次变化、闭环证据失效时，不继续展示问题已解除。

## 天猫只读闭环

新增天猫已平账核验，不启用天猫自动补单。仅支持已成功的已发货全额仅退款。

按平台订单精确查询 ERP，要求唯一的天猫退款记录、同一售后号、相符金额及客户原销售关联。客户名下需要独立的原收款和对应退款流水，退款单与原销售 ID 绑定，且无欠货、累计应收为零；退货型号、颜色、数量仍通过原匹配器核验。

商家应收缺失时，仅对退款金额、买家实付、平台商品金额完全一致的全额退款尝试只读核验，并要求 ERP 原收款金额及退款金额均相符；优惠金额口径不明、跨订单、多条退款或重复流水继续阻断。不得据此扩展无人值守多包裹退款。
