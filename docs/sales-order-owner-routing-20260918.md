# 待办按发货销售订单归属分派（2026-09-18）

客户档案的归属业务员可能与具体销售订单不同。人工待办必须读取原发货销售单每笔订单的“归属业务员”，不能回退客户档案归属。普通模块1、2、3待办和同包裹待办均适用；待办发布开关、资金授权和同包裹人工锁保持原规则。

## 取值与发送

- ERP 网页查询先通过平台订单号定位唯一客户、验证客户ID，再读取发货销售单全部分页，精确匹配目标平台订单的商品行。客户ID用于定位，不用于确定收件人。只查询归属时允许客户历史中存在其他平台订单，但不放宽整包裹退款核验的跨平台保护。
- 同一订单多行须全部为同一非空业务员；归属缺失、冲突、漏页、重复页或读取失败时保留本地待核实。旧SQL适配器仅读取销售订单业务员；退货匹配不再用客户档案人员覆盖销售归属缓存。
- 发布待办前再次只读核验销售订单归属，覆盖旧排队任务中的错误收件人。读取失败不领取发送任务、不消耗发送次数，保存原因并冷却5分钟，由后续后台周期重查。待办列表仍可看到未发送状态及原因。
- 同包裹只对有效退款申请所对应的销售订单业务员分组；同一人合并一份，申请订单对应不同人员则每人一份。未申请退款订单用于说明业务阻断，不单独通知其业务员。
- 正文列出“您负责的退款申请订单”。同包裹使用客户、快递公司、运单、业务员和归属来源构成v2幂等键及独立外部标识；迁移旧任务时不沿用旧收件人的外部查重标识。发送前发现归属变化则重新分组，避免迁移走的订单又被合回原人。
- 只修改待发送任务；已发送历史记录保留接收人、正文、ERP待办ID和成功凭证。指定个案需要纠正接收人时，先只读复核当前申请及归属，备份后新增正确人员待办，并在旧记录追加关联说明，不能把原记录改成“早已发给正确人员”。

## 运行与维护

沿用正式机 `Leedis Aftersales Module1 Watchdog` 登录触发和每5分钟守护；现有worker循环负责同步和发布。没有新增定时任务、数据库迁移或配置项。依赖现有 `ERP_WEB_BASE_URL`、`ERP_WEB_USERNAME`、`ERP_WEB_PASSWORD` 只读销售查询及原ERP待办发布权限；不要将账号、订单或审计资料提交Git。

查不到业务员时先核对该订单是否已在ERP发货销售单、商品行归属是否完整，再查看任务 `owner_routing_status` / `owner_routing_retry_after` 和 `last_error`。更正ERP资料后下一轮到期核验会重新分派。禁止直接把客户档案人员填入队列绕过核验。
