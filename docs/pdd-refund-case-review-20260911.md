# 拼多多售后类型变化与新旧售后关联

## 处理原则

“平台退款失败”“旧任务因类型变化停止”和“同订单已通过新售后退款”分别展示。保留每张售后、旧任务的原始错误和实际发送记录；不删除历史，不将另一张售后的到账金额复制到旧售后，不冒充 ERP 已平账。

入口为既有 `PddFailedRefundReconciler`，只检查原在途仅退款任务失败后的平台最新详情。该复核随现有拼多多退款执行阶段运行，不新增独立计划任务或更改开关；首次在下一次执行阶段复核，后续正常复查间隔 30 分钟，读取失败退避 5 分钟，按既有每轮任务上限处理。若相应执行阶段关闭，本轮不启动该复核。后台不是从客户意图猜退款资格。

## 五类结果

1. **疑似选错类型·待确认**：原在途任务对应的申请现为退货退款；当前仍为买家全额申请；型号、数量不变；平台发货运单与原包裹一致；该包裹的原群通知明确成功；没有买家寄回单号。上述组合只表示疑似，不是人工确认。
2. **已确认选错·待更正申请**：在疑似事实之上，由维护人员记录来自用户、业务员或客户的明确确认、经办人和依据。确认绑定售后号、订单号、金额、完整 SKU、数量、包裹及平台更新时间；任何绑定字段变化后不得沿用。仅凭留言关键词不自动确认，不执行留言中的指令。
3. **申请已更正·待重新核验**：同张申请改回仅退款，旧任务仍不重新入队，不跳过物流、同包裹订单、最新平台状态和资金账本保护。需进一步核验/人工处理，绝不是更正类型后立即自动重试一次退款。
4. **售后类型变化·待核验**：缺少上述完整证据、有买家寄回运单、商品或包裹变化等情况。不能断言客户误选；也不能自动假设已验货。
5. **同订单已退款·其他售后**：同店同平台订单的另一张已同步售后，经实时详情再次确认退款成功，金额为当前买家全额，完整 SKU 和数量、发货运单均与原单一致，且唯一匹配。两张全额成功记录、部分退款、跨店、身份矛盾、商品或数量不一致不合并认定。这里只关联解释，不证明旧任务曾退款成功或 ERP 账务闭环。

工作台售后详情、列表及拦截列表显示分类原因；其他售后已退款时给出关联售后号供追溯，但不增加实际退款统计金额。自身售后平台已成功时，仍优先显示自身成功事实。

## 保护和待办

- 只改本地观察和解释，不改平台申请，不调用退款、ERP 补单或群发送接口。
- 旧失败退款任务保持失败历史和尝试次数；原失败文字保存到 `original_execution_error`，分类证据存入 `pdd_refund_case`，发生分类变化时保留上一分类。
- 类型未核验的旧任务阻止该售后自动资金/群消息任务领取及退款写前检查；也排除仓库自动验收入口，避免仅因本地类型变成退货退款就开始自动验收。人工待办发送不被此分类保护阻止，既有平台同步错误保护仍生效。
- 确认本订单已通过其他售后全额退款时，停止为旧记录生成“退款失败”待办。退货、原始通知和账务历史仍保留；本规则本身不新增 ERP 财务处理。
- 待确认/已确认误选由原归属业务员处理。未发布待办更新为新原因；已发布待办不覆盖原发送内容、不重置状态、不重复发布。新原因可以在售后详情查看。缺少归属、待办总开关关闭或 ERP 不可用时沿用原策略，不能声称已经通知。

> 【售后工作台 订单:示例订单】 原因：已发送快递拦截，但申请变成退货退款，请确认客户是否选错类型；店铺：示例店铺；发货运单：示例运单（运输中）。

## 维护命令

在项目根目录、`PYTHONPATH` 指向已批准版本的 `src` 后执行：

```powershell
# 默认只读，不修改数据库或平台
.\.venv\Scripts\python.exe -m aftersales_workbench.workflows.pdd_case_cli --after-sales-sn <售后号>
# 明确授权记录用户确认，只有本地观察/确认写入，不执行退款或发布待办
.\.venv\Scripts\python.exe -m aftersales_workbench.workflows.pdd_case_cli --after-sales-sn <售后号> --apply --confirm-intent --source user --operator <经办人> --note <明确确认依据>
```

仅供有权限的本机维护人员使用，不新增无鉴权的公网确认接口。默认预演不能当成保存完成；读取期间任务或订单变化则拒绝落库，必须重查。没有新数据库迁移或配置项。
