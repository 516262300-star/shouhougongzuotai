# 同客户、多订单、多包裹退货核验方法

记录日期：2026-09-08。适用于客户有较多订单、部分订单申请退货退款，退回多个包裹，平台填写运单可能与实际装箱商品交叉的情况。

## 核心原则

先按同一客户、本批订单及相关全部退货包裹建立核对范围，再追溯到每笔原销售订单。快递单号是包裹线索，不是商品归属的唯一依据。某商品在平台填写的那一票未找到，不代表客户没有退回；必须检查本批其他包裹。也不能因两票总件数相同就认定全部订单正确。

这里记录的是核验及人工授权后的处理方法。2026-09-12 模块2已接入共享运单整批只读核验及已退款核账，详见 [共享运单核账说明](shared-return-accounting-20260912.md)。未改变自动化开关、定时计划或多包裹退款授权要求。以后遇到同类情况应按此流程核查，不能自动套用某个历史客户的退款名单、金额或状态。

## 1. 确定范围并完整取数

1. 由目标平台订单查询 ERP 客户档案，确认平台、店铺、客户唯一归属及本批订单范围。客户昵称相同不能证明是同一客户。
2. 读取客户原销售与退货明细的全部分页，记录页数、查询时间及商品行数。税点、运费等非商品行单列，不计入退回商品件数。
3. 汇总本批所有相关 ERP 退货单、运单、开单时间和实收明细；必要时核查暂存、客户档案、作废或冲销记录。不能把“平台已填单号”“物流已签收”或“开了退货单”单独当作具体商品验收通过。
4. 根据原销售记录找出本批全部平台订单，逐笔实时查询订单及售后详情，包括已退款、待处理、关闭、未知状态和没有售后的订单。查询失败不能当作没有售后。
5. 记录无法访问的页、单据或字段；范围未覆盖完整时不要给出“整批全部一致”的结论。

## 2. 用原销售关联逐项核实

本项目当前 ERP 客户发货销售表中，经本次核实的关联关系为：

`退货商品行的客户编号 → 原销售商品行的订单编号（内部销售ID）→ 原销售商品行的客户编号（平台订单号）`

这些列名容易混淆；必须先用真实明细确认语义，不能推广到未经验证的其他 ERP 页面或平台字段。优先使用可用的稳定行ID与明确订单关联，禁止只凭同型号凑数。

每笔需要逐项确认：

- 平台/店铺、客户、平台订单号及售后号一致，原销售关联唯一。
- 完整型号、孔距或规格、材质、颜色一致。例如单孔与96孔距、铬与铜拉丝、是否含胡桃木不能互换。
- 比较售后申请退回数量与可分配实收数量，不用原订单总数量替代部分退货数量。
- 记录平台填写运单及实际收货运单，允许证据充分的跨包裹匹配，不修改客户填写的单号来掩盖差异。
- 多笔相同SKU、同原销售ID多行、缺少销售关联或数量不足时，必须查清归属；不随意将某一件实收分给其中一笔。
- 型号数量一致不自动证明质检合格；有质量、破损、缺配件或收货有效性争议时单列核实，不伪造“验货通过”。

## 3. 建立实收分配和差异清单

保留逐项台账：平台订单、售后号、申请SKU和数量、退款金额及状态、原销售ID、ERP退货单/行ID、实际运单、实收数量、本笔分配数量、分配唯一键、已消耗数量、剩余数量、核验时间及证据。

同一退货行或同一实物数量只能使用一次。已退款订单对应的实收也必须占用，不能再次分配给待退款订单。并发处理必须先持久化唯一分配与退款幂等记录，不能仅靠内存里“已检查”的名单。

分别列出：

- 型号颜色数量有独立实收依据且当前允许处理的订单。
- 已退款订单（只核账，不重复退款）。
- 实收但未查到售后、售后状态未知/关闭/不可操作的订单。
- 已退款但缺少实收、退回不足、商品不符、关联不唯一的订单。
- 实收剩余商品及没有对应申请的商品。

整批有差异不必阻止具有独立、无争议实收证据的其他订单；但若差异影响这些订单的数量分配或客户归属，就不能先退。对不确定项说明缺什么证据，不笼统回答“全部没问题”。

## 4. 用户授权后的退款步骤

1. 将已核实可操作名单、每笔金额及总额固定为本次范围。“核实/能否退款”不是实际资金操作授权；用户明确要求先退正确订单后，在该范围内执行，不扩展到异常订单。
2. 默认先只读预演。执行前重新查询 ERP 和平台，确认收货未作废、关联未变化，平台售后仍允许退款，类型、金额、SKU、数量不变。写开关、店铺权限必须已有效，不擅自启用其他平台或全局退款权限。
3. 检查已有成功、运行中、失败或结果未知的退款任务及实收占用。失败不等于未退款，不能清空任务后重做。平台已成功的只做核对与必要的本地事实回写。
4. 不把合并收货拆成虚构的一单一收货记录来绕过保护。现有自动流程要求一对一验货记录时，保持该保护；证据充分且有明确授权的人工个案，应保留真实合并核验及分配证据，不冒充自动验货通过。
5. 外部退款请求前，持久化限定售后号/订单号的唯一幂等任务和实收分配。资金请求每笔只发送一次；请求超时、回包不明或平台更新延迟时，只能只读回查，禁止盲目重试。不得并行运行同一批退款。
6. 逐笔回查平台详情。确认身份、实际状态及金额符合成功证据后，才记录“退款成功”；仅收到请求响应不等于完成。回查可以短间隔有限重试，仍不明则保留任务、暂停后续资金操作并报告待核实项。
7. 本地更新必须基于平台事实，不将本机查询时间或旧申请时间伪造成退款完成时间；平台更新时间仅在已确认采用该统计口径时使用，并标明不是精准到账时间。平台退款成功、仓库质检通过、ERP财务闭环是不同事实，不互相替代。
8. 返回每笔结果、成功金额、未处理项及原因。未获授权不新增 ERP 退货/退款单、认领、改客户运单、发企微消息或建第三方待办。

## 留档与后续维护

- 本地 `.runtime/audits/` 保存完整个案证据、授权范围、只读预演、外部请求次数及回查结果；数据库动作记录保存实收分配和幂等依据。保留最小必要客户资料，禁止上传客户订单、运单和凭据。
- 本文与根目录 `AGENTS.md` 是后续同类核验的入口；没有新增定时任务或通用自动退款命令。
- 个案脚本仅供该次已授权名单使用，不能把历史 `--apply` 命令当作下次处理模板。恢复时先只读核验既有任务与平台状态，不重发已发送或结果未知的资金请求。
- 若以后将本方法实现为无人值守功能，需要另外设计持久化的跨包裹分配模型、并发唯一约束、部分退货及售后重开规则、异常隔离与验收测试，并获得对应实施授权；不要直接解除当前共享运单保护。
- 本次通用方法文档随项目提交到 GitHub；没有提供 Notion 页面目标，不宣称已同步 Notion。
